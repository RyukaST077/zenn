# 実践タスク: 旧世代のtsconfigをTypeScript 5.9 → 6.0 → 7.0 に通して、警告がハードエラーに変わる境界を見る

## このタスクの前提

- 出典レポート: `research/search-topic-20260727-0402.md`
- 元テーマ: 候補1（最優先 / 「最初に試すべき1本」）「TS6時代のtsconfigをTypeScript 7に通したら、既定値の変更で何がエラーになったか」
- 対象技術: TypeScript 7.0（Go実装ネイティブ tsc）の tsconfig 互換性。比較対象として TypeScript 6.0 / 5.9
- 記事の方向性（記事タイプ）: 検証ログ・詰まった点まとめ（「わざと踏んで出力を採る」型）
- 想定筆者 / 想定読者: Web系の新人エンジニア / 新人〜実務2年目、TS7への移行判断を控えている人
- 検証に使える想定時間: **1日（約7時間）** ← 引数で時間指定がなかったため、デフォルト前提「半日〜1日」の上限を採用
- 判断方針: 引数で指定されたのは対象レポートのパスのみ。テーマ・時間・スキルレベルはデフォルト前提を採用
- 実行環境の担保: `npm install` と `node node_modules/typescript/bin/tsc` だけで完結する。ブラウザ・Docker・クラウド・認証・課金キーすべて不要。Playwright も不要（CLI出力のみで完了判定可能）。当環境の既知制約（Docker VM の egress 不通 / Playwright 同梱 Chromium の版遅れ）に一切触れない

### 出典レポートからの重要な軌道修正（この計画で変更した点）

Step 3 の裏取りで、レポートの前提に**事実誤認**が見つかったため検証設計を組み替えた。記事の骨子にも直結するので先に明示する。

| レポートの記述 | 裏取りで判明した事実 | この計画での扱い |
|---|---|---|
| 「TS7 で `strict` が既定ON、`module` が `esnext`、`rootDir` が `./`、`types` が `[]` になった」 | **これらはすべて TypeScript 6.0 で導入された既定値**。TS7 は引き継いだだけ | 「TS7の変更点」として書くと誤り。**TS6→TS7 の差分は別**（下段）として切り分ける |
| 「`baseUrl` は削除、`target: es5` と `moduleResolution: node` は廃止」 | TS6 では **deprecation 警告**（`ignoreDeprecations: "6.0"` で抑制可）。TS7 で**ハードエラー**に昇格 | 検証の主軸を「**警告 → ハードエラーの境界**」に置く |
| 検証は TS6 → TS7 の2段 | 既定値変更は 5.9→6.0、廃止は 6.0→7.0 で起きる。2段では原因を切り分けられない | **5.9.3 → 6.0.3 → 7.0.2 の3段ラダー**に変更 |

つまり本当の TS7 固有の変更は「TS6 で警告だったものが起動不能になる」ことと、`esModuleInterop: false` / `alwaysStrict: false` が禁止になったこと。ここを一次ログで示すのが差別化になる。

出典: [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) / [Announcing TypeScript 6.0](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/)

## 完成イメージ（成果物）

- **作るもの**: 1つの「旧世代 tsconfig + それに依存する `src/`」fixture を、TypeScript 5.9.3 / 6.0.3 / 7.0.2 の3つの独立ディレクトリで型チェックし、**同一入力に対する3世代の出力差分**を採取した検証ログ一式（`logs/` にエラー全文・版情報・所要時間、最終的な before/after tsconfig diff）
- **「できた」と言える完了条件**:
  1. 3ディレクトリすべてで `node node_modules/typescript/bin/tsc --version` が**期待した版を出力**する（版ゲート通過）
  2. 同一 fixture に対し、5.9 = 通る / 6.0 = 警告付きで通る or 警告 / 7.0 = エラーで落ちる、の**3世代の出力全文が保存されている**
  3. 「どの設定が、どの版で、警告なのかハードエラーなのか」の対応表が埋まっている
  4. TS7 で `tsc --noEmit` が**終了コード0で通る**最終 tsconfig に到達し、初期版との diff が取れている
- **完了確認の方法**: すべて CLI 出力（`--version` / `--noEmit` の stdout+stderr と終了コード）。Playwright は不要
- **記事タイトル案（そのまま使える形）**:
  1. TypeScript 6で「警告」だった設定が、7で何個ハードエラーになったか数えてみた
  2. 旧世代のtsconfigを5.9→6.0→7.0と順番に通して、どこで壊れるかを見た記録
  3. `baseUrl`も`target: es5`も通らない — TypeScript 7移行で新人が踏んだ設定の壁

## 経験談として書くときのコツ

- 「新人が試した範囲」を明示し、専門家として断定しすぎない。特に「TS7に上げるべき」とは書かない（公式も埋め込み言語利用者にはTS6継続を推奨している）
- **予測を外したことを隠さない**。フェーズ1で立てた仮説と実測の差が、この記事で一番読まれる部分になる
- エラー出力は要約せず全文で貼る。エラーコード番号は検索流入に効く
- 件数を語るときは数え方（設定エラーと型エラーを分けた）を明記する
- 型チェック時間は題材規模を添え、公称値と比べて乖離があればそう書く
- 版情報（`node -v` / `npm -v` / 3つの `tsc --version`）とOSを冒頭に置き、再現性を担保する

## 想定リスク・注意点

- **コスト**: 全工程無料。課金トリガーなし。ネットワーク利用は npm registry からの install のみ
- **ライセンス / 規約**: TypeScript は Apache-2.0。fixture は自作コードのみで、他者コードを転載しない
- **セキュリティ**: APIキー・トークンを一切使わない。`--ignore-scripts` を付けて install スクリプトを実行しない。記事に貼る出力に絶対パス（ホームディレクトリ名）が混じらないよう、作業ディレクトリは `mktemp -d` 配下にしてパスを置換する
- **グローバル環境を壊さない**: `npm i -g` は使わない。すべてプロジェクトローカルの devDependencies で隔離する
- **撤退ライン**:
  - 版ゲート（3つの `--version`）が15分試して通らなければ、その時点の観測事実（symlink先・依存グラフ）を記録して**フェーズ4のside-by-side検証だけを落とす**。本編は版ごとに独立ディレクトリなので継続できる
  - フェーズ3のエラー潰しが45分で終わらなければ、「未解決のまま残ったエラー」として全文を記事に載せて締める（完走できなかったこと自体を書く）
  - フェーズ4は全部が任意。時間が尽きたら丸ごと省略して記事は成立する
