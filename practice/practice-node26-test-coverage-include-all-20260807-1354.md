# 実践タスク: Node 26.7 の `--test-coverage-include-all` を付けたら、カバレッジ率が何%下がったか測ってみた

- 対象技術: Node.js 26.7.0 の `node:test` コードカバレッジ（`--experimental-test-coverage` + `--test-coverage-include-all`）
- 記事の方向性（記事タイプ）: 試してみた・検証ログ（数値の前後比較）

### 事前の裏取りで分かったこと（重要 / このプランの前提）

Step 3 で公式一次情報を確認した結果、レポート段階では見えていなかった事実が2点あった。**これが記事の差別化の核になる。**

1. **新しくなったのは「CLIフラグ」であって、機能そのものではない。**
   Node.js v26.7.0 リリースノートには `test_runner: (SEMVER-MINOR) add support for --test-coverage-include-all` とある（PR [#64830](https://github.com/nodejs/node/pull/64830)、commit `a646319f61`、author avivkeller）。
   一方 `run()` API の `coverageIncludeAll` オプションは**それ以前から存在していた**（元issueは [#58887](https://github.com/nodejs/node/issues/58887) “Report 0% coverage for untested files in a project”）。
   つまり 26.7 の新規性は「プログラム経由でしか使えなかったものが、CLIフラグで使えるようになった」点にある。出典レポートの検証手順7（`run()` API でも同値か確認）は、単なるおまけではなく**記事の主張を支える対照実験**になる。
2. **ドキュメントの "Added in" 表記が実態とズレている可能性がある。**
   `nodejs.org/api/test.html` の記述では `--test-coverage-include-all` が **Added in: v23.0.0** と読める。しかし 26.7.0 のリリースノートは同フラグを SEMVER-MINOR の新規追加として挙げている。どちらが正か、**手元の 26.5.0 と 26.7.0 で実際にフラグが通るか試して確定させる**（フェーズ1タスク3）。これはそのまま「詰まった点」になる。

未確認のため断定しない点（記事でも「要確認」と書く）:

- 絞り込みフラグの正式名が `--test-coverage-include-globs` / `--test-coverage-exclude-globs` なのか、`--test-coverage-include` / `--test-coverage-exclude` なのか、参照した情報源で表記が割れている。**手元の `node --help` で確定させる**（フェーズ1タスク3）。
- `--experimental-test-coverage` が 26.7 時点でまだ必須か（Stability 1 の記述は確認済みだが、実機で確定させる）。

## 完成イメージ（成果物）

- **作るもの**: `src/` に小さな純関数を6ファイル、`test/` にそのうち3ファイル分だけテストを持つ、依存ゼロの最小Nodeプロジェクト（`coverage-lab/`）。これに対しフラグ有無でカバレッジを取り、出力を全文保存して差分表にする。
- **「できた」と言える完了条件**:
  1. `node --version` が `v26.7.0` を返す
  2. `node --test --experimental-test-coverage` の出力全文が `logs/without-flag.txt` に保存され、**テスト無しの3ファイルが表に現れない**ことを確認できている
  3. `--test-coverage-include-all` 付きの出力全文が `logs/with-flag.txt` に保存され、**同3ファイルが 0% 行として現れる**ことを確認できている
  4. 2つの総合カバレッジ%（all files 行）を並べた差分表が `logs/diff.md` にある
  5. `run()` API の `coverageIncludeAll: true` の出力が `logs/run-api.txt` にあり、3と一致するか不一致かを判定できている
- **完了確認の方法**: すべて **CLI出力のテキスト保存**で判定する（`| tee` でファイルに残す）。ブラウザ表示は無いため Playwright は使わない。スクショの代わりに**ログ全文が一次情報**になる。
- **記事タイトル案（そのまま使える形）**:
  1. `Node 26.7 の --test-coverage-include-all を付けたら、カバレッジ率が XX% から YY% になった`（実測後に数値を埋める）
  2. `カバレッジ100%だと思っていたら、そもそも数えられていないファイルがあった話（Node 26.7）`
  3. `--test-coverage-include-all は「新機能」ではなかった — CLIフラグ化されただけ、と分かるまでの検証ログ`

## 経験談として書くときのコツ

- 「新人が試した範囲」を明示し、専門家として断定しすぎない。特に**ドキュメントとリリースノートの食い違いは「自分の環境ではこうだった」に留める**
- うまくいった点だけでなく、詰まった点と解決過程を書く。特にフェーズ3-2で「フラグを付けたのに変わらない」に当たった場合、その試行錯誤が本文の中心になる
- 実行ログとコードを残して貼る。**この検証は画面が無いので、ログ全文が唯一のエビデンス**。省略せずに貼る
- 公式ドキュメント（リリースノート / `node:test` / PR #64830 / issue #58887）へのリンクを入れる
- 手順の再現性（Node のパッチバージョン、OS、`src`/`test` のファイル構成と行数）を明記する
- **カバレッジ機能自体がまだ experimental であること**と、**測定値はこの検証プロジェクト固有で一般化できないこと**を必ず書く

## 想定リスク・注意点

- **コスト**: ゼロ。課金要素・外部サービス・APIキーは一切無い。ネットワーク通信は `nvm install 26.7.0` のダウンロードのみ
- **ライセンス / 規約**: 検証コードはすべて自作の小さな純関数。第三者コードを転載しない
- **セキュリティ**: 秘密情報を扱わない。ただし**ログ全文を記事に貼るため、絶対パス（`/Users/<ユーザー名>/...`）が混入しないよう公開前に確認する**。相対パス表記に置換するか、実行ディレクトリを浅くしておく
- **既出記事との重複**: `articles/node-test-randomize-seed-extraction.md` が同じ `node:test` 領域にある。対象機能が異なる（あちらは実行順のシード、こちらはカバレッジ集計）ことを冒頭で明示する。また `node26-*` の既出記事が多いため、本稿が **26.7 のカバレッジ**であることをタイトルで区別する
- **撤退ライン**:
  - フェーズ1-3で **26.7.0 にも 26.5.0 にもフラグの挙動差が無かった**場合 → 「新機能ではなかった」ことを主題に切り替える（記事は成立する。むしろ差別化が強まる）
  - フェーズ3-2で**フラグを付けても出力が1文字も変わらず、詰まりポイント表#3の対処を全部試しても解決しない**場合 → 90分で見切り、「再現できなかった記録」として `run()` API 版（フェーズ3-5）に主軸を移す
  - **`nvm install 26.7.0` 自体が失敗する**場合 → 本テーマは成立しないため、出典レポートの候補2（TypeScript 7 移行ログ）へ切り替える
