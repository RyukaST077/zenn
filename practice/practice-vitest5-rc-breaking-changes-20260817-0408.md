### 公式移行ガイドから抜き出した破壊的変更（検証対象）

`https://main.vitest.dev/guide/migration` で確認した原文ベースの記述。

| # | 破壊的変更 | 公式の記述（要旨） | 検証可否 |
|---|---|---|---|
| A | 未await の非同期assertion | `resolves` / `rejects` / `toMatchFileSnapshot` は await されないとテストを失敗させる（4.1 までは自動awaitして警告） | ⭕ 数行で再現 |
| B | `clearMocks` 既定 true | 各テスト前に `vi.clearAllMocks()` を呼ぶ。実装は残るが**呼び出し履歴が消える** | ⭕ |
| C | `-t` の区切り変更 | `testNamePattern` は suite チェーンとテスト名を `' > '` で連結したフルネームに対して照合 | ⭕ |
| D | `vi.mock` トップレベル必須 | `vi.mock` / `vi.unmock` / `vi.hoisted` を関数・ブロック・テストコールバック内で呼ぶと**警告ではなくエラー** | ⭕ |
| E | `test.sequential` 削除 | `test.sequential` / `describe.sequential` は削除。`{ concurrent: false }` を使う | ⭕ |
| F | `toThrow('')` の意味変更 | 空文字は「任意のエラーメッセージに一致」（全文字列が空文字を含むため）。4.1 までは空メッセージのみ一致 | ⭕ |
| G | 成果物ディレクトリ | プロジェクトルートの単一 `.vitest` ディレクトリを共有アーティファクトルートに使う | ⭕ |
| H | worker/pool ID が1始まり | `VITEST_POOL_ID` / `VITEST_WORKER_ID` が `0` ではなく `1` から | ⭕ |

> 「Prerequisites: Vitest 5.0 requires Vite >= 6.4.0 and Node.js >= 22.12.0」も同ガイドに明記。

## 詰まりそうなポイントと対処の指針

| # | 詰まりそうな点 | なぜ起きるか | 最初に試すこと | 記事での活かし方 |
|---|---|---|---|---|
| 1 | Vitest 5 にした瞬間 Vite のバージョン要件で落ちる | 5 は `vite ^6.4.0 \|\| ^7 \|\| ^8` が peer。4.1 は `^6.0.0` から許すので、`vite@6.0.x` を掴んでいると 5 で不適合になる | `npm ls vite` で実バージョンを確認 → `npm i -D vite@latest`（現行 `8.2.1`）に上げる | 「上げる前に peer を見ろ」という具体的な手順として書ける。`npm view vitest@rc peerDependencies` の出力をそのまま貼る |
| 2 | Node のバージョンで起動すらしない | 5 は `node ^22.12.0 \|\| ^24 \|\| >=26`。22.11 以下や odd メジャーだと弾かれる | `node -v` を先に実行して要件と照合。足りなければ nvm 等で 22.12 以上へ | 「要件チェックを最初のタスクにした理由」として、フェーズ1-3 の照合表を見せる |
| 3 | 項目Fの fixture を 4.1 で緑にできない | `toThrow('')` は 4.1 では「空メッセージのみ一致」なので、素直に書くと 4.1 で落ちる。「4.1 で全部緑」という前提が崩れる | 4.1 側は `expect(fn).not.toThrow('')` を緑の形とし、5 でその `not` が落ちることを確認する（意味の反転を見る） | 「ベースラインを緑にする」という制約自体が設計の工夫。読者が同じ fixture を作るときにハマる |
| 4 | 項目Bで `clearMocks` の差が出ない | `vitest.config.ts` に `clearMocks` を明示していると既定値の変化が観測できない。また `beforeEach` で呼び直していると履歴が復活して差が消える | config に `clearMocks` を書かないことを確認し、モック呼び出しは `beforeAll` に置く（`beforeEach` にしない） | 「既定値の検証は、設定を書かないことが条件」という気づき。地味だが再現性の話として価値がある |
| 5 | 項目C の `-t` で常にマッチ0件になる | 5 は suite チェーンを `' > '` で連結したフルネームに照合する。`describe` を付け忘れると suite チェーンが無く、両パターンとも同じ挙動になって差が出ない | `describe('math', ...)` で必ずネストさせる。マッチ0件時の出力文言も記録する | 4.1 / 5 × 2 パターンの 2×2 表がそのまま図表になる |
| 6 | RC 特有の不安定さを「破壊的変更」と誤認する | `5.0.0-rc.1` は安定版前。バグ由来の失敗と、意図された破壊的変更の失敗が見分けにくい | エラーが移行ガイドに載っている項目かを必ず突き合わせる。載っていなければ「RC の挙動、要確認」と書く | 「どこまでが仕様で、どこからが RC の揺れか分からなかった」は正直な新人視点として刺さる |
| 7 | 項目 G/H が pool 設定に依存して再現しない | `VITEST_WORKER_ID` は pool（threads / forks / vmThreads）や `isolate` 設定で挙動が変わりうる | 既定 pool のまま実行し、変えた場合は設定を必ずログに残す | 「環境を書かないと再現しない」ことの実例。再現条件の明記は検証記事の基本 |

## 経験談として書くときのコツ

- **RC の挙動であることを本文で明示する**（安定版で変わる可能性がある）。断定しすぎない
- 「新人が試した範囲」を明示する。20項目以上あるうち **8項目に絞った**と、絞った理由込みで書く
- 落ちなかった項目を「落ちた」と書かない。再現しなかったものは再現しなかったと書く
- エラーは全文を貼る。要約すると検索で辿り着けなくなる
- バージョン（Node / npm / Vite / Vitest）と OS を必ず明記する。結論がバージョン依存のため
- 公式（移行ガイド・リリースノート・Discussions）へのリンクを入れ、「なぜ変わったか」まで触れる
