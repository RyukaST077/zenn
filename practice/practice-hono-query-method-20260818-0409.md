> **この検証の核心**: 手元の Node 22.17.0 が同梱する undici は **6.21.2** で、QUERY 対応が入った PR #5459
> よりはるかに古い。つまり「Hono 側は書けるのに、Node の `fetch` からは送れない」という
> ギャップが手元で再現できる見込みが高い。ここが記事の一番おいしい部分になる。
> ただし**実際に落ちるかどうかは実行して確かめる**（undici 6 系が method 文字列を素通しする可能性も
> あるため、予断を持たず結果をログに残す。これは「要確認」項目）。

- 完了確認の方法:
  - サーバー/CLI 側は `curl -v` の生出力とサーバーの標準出力（ログファイルに保存）

  3. RFC 10008 の QUERY は実装が簡単だった。難しかったのは「送る側」だった

## 詰まりそうなポイントと対処の指針

| # | 詰まりそうな点 | なぜ起きるか | 最初に試すこと | 記事での活かし方 |
|---|---|---|---|---|
| 1 | Node の `fetch` で QUERY が送れない／エラーになる | 手元の Node 22.17.0 が同梱する undici は **6.21.2** で、QUERY 対応（PR #5459）が入る前のバージョン。issue #5454 の状況そのもの | `process.versions.undici` を印字して同梱版を特定する → `npm i undici@8.10.0` を入れて `import { fetch } from 'undici'` で再実行し、差が出るか見る | **記事の主題**。「サーバーは書けるのに送れない」を、バージョン番号とエラー全文つきで示す。フェーズ4-2 の比較表がそのまま結論になる |
| 2 | `app.query is not a function` / `hono/method-not-allowed` が解決できない | インストールされた Hono が 4.13 未満（`@latest` を使わず古い lockfile を拾った等）。`methodNotAllowed` は 4.13.0 で追加された | `npm ls hono` で実際の解決バージョンを確認 → `npm i hono@4.13.2` で固定し直す。`node -e "import('hono').then(m=>console.log(Object.keys(m)))"` でエクスポートを見る | 「新機能を試すときは、まず入っているバージョンを疑う」という定番の詰まりを、実際のエラー文で書ける |
| 3 | ブラウザから QUERY を送るとCORSで落ちる（同一オリジンでは落ちない） | QUERY は **CORS safelisted method ではない**ため、クロスオリジンではプリフライト(OPTIONS)が必須。サーバーが `Access-Control-Allow-Methods` に QUERY を返さないと本リクエストが飛ばない | 同一オリジン（フェーズ3-6）とクロスオリジン（フェーズ4-1）を分けて実行し、`page.on('request')` でOPTIONSの有無を見る → Hono の `cors()` を入れる（#5115 で既定に QUERY が入っている） | 「同じコードがオリジン次第で結果が変わる」を、ネットワークログとスクショ2枚で見せる。既存の国内記事が触れていない領域 |
| 4 | `curl -X GET --data` を投げてもボディが届かない／勝手に POST になる | curl や中継の実装依存で GET+body の扱いが不安定。`--data` は既定でメソッドを POST にする（`-X` で上書きしても挙動が揃うとは限らない） | サーバー側ハンドラで**実際に届いたメソッドとボディ**をログ出力しておき、クライアント側の意図と突き合わせる | 「GET+body で代用すればいい」という素朴な発想が崩れる場面。QUERY が必要とされる理由の実演になる |
| 5 | ポート3000/3001 が既に使われて起動できない（`EADDRINUSE`） | ローカルで他の dev サーバーが動いている。クロスオリジン検証で2ポート使うので衝突しやすい | `lsof -i :3000` で占有プロセスを確認 → 空きポート（3100/3101 等）に変え、**ログとコード中のポート番号を統一**する | 環境構築の詰まりとして短く書く。記事では「ポートは環境に合わせて読み替えて」と明記できる |
| 6 | Playwright のブラウザ起動に失敗する／スクショが真っ白 | ブラウザバイナリ未取得、または `fetch` の完了前にスクショを撮っている | `npx playwright install chromium` を実行。スクショ前に `page.waitForSelector('#result')` など**描画完了を待つ**条件を入れる | 「自動確認の落とし穴」として1節。撮り直し前後のスクショを並べると分かりやすい |
| 7 | `Accept-Query` ヘッダが返ってこない | Hono が自動付与するかは**リリースノートから未確認（要確認）**。RFC 上はサーバーが宣言するヘッダ | `curl -v` のレスポンスヘッダを見て有無を確認 → 無ければハンドラで `c.header('Accept-Query', 'application/json')` を手で付けて差分を見る | 「仕様にはあるが、フレームワークがどこまでやってくれるか」の実測。断定せず「手元では付かなかったので自分で付けた」と書く |

## 経験談として書くときのコツ

- 「新人が試した範囲」を明示する。**プロキシ・CDN・HTTP/2以降の中継は未検証**とはっきり書く
- 「QUERYを使うべき」と断定しない。「今の手元ではここまで通った」という書き方に徹する
- エラーは要約せず全文で貼る。QUERY のようにバージョン依存が強いテーマでは、**すべてのバージョン番号**が記事の価値になる
- 予想を先に書き、結果で答え合わせをする構成にすると、詰まった経験がそのまま読み物になる
- 公式情報（RFC 10008 解説、Hono リリースノート、undici issue #5454）へのリンクを必ず入れる

- コスト: **ゼロ**。OSSパッケージのローカル実行のみ。課金トリガーとなる操作は含まない

  ログを記事に貼る前に、ホスト名や絶対パスに個人情報が混ざっていないか確認する
- 結果のバージョン依存: 本検証の結論は `node v22.17.0` / `undici 6.21.2` に強く依存する。
  記事では必ず「この環境での結果」と限定する
- 撤退ライン:
  - フェーズ2-4（curl での疎通）が **60分**かかっても通らない場合 → サーバー実装を `app.on('QUERY', ...)` など
    別APIに切り替え、それでも駄目なら「Hono の QUERY 対応を動かすまでに詰まった記録」として記事を成立させる
  - Playwright のブラウザ起動が **30分**で解決しない場合 → ブラウザ経路は「起動できなかった事実」として記録し、
    curl / Node fetch の2経路で結果表を完成させる（記事の骨格は保てる）
  - undici 差し替え（4-2）で結果に差が出なかった場合 → 結論を「もう通る」側に振り、
    検証の重心をフェーズ4-1（プリフライト）と 4-3（ETag/キャッシュ）へ移す
