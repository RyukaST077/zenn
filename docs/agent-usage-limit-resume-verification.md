# Claude利用上限後の会話継続: 実装と検証

実施日: 2026-11-10（Asia/Tokyo）。仕様は[合意した修正方針](agent-usage-limit-resume-plan.md)を参照。

## 実装

- 終端の構造化エラー `usage_limit_reached` と新旧の上限文言を認識する。成功本文・ツール出力・過去のエラーや通常の429は区別する。JSONとJSONLを解析する。
- Claudeのsearch / plan / analyze / draft / review / reviseで会話を保存する。初回起動前にUUIDと工程状態を保存し、利用上限後は同じIDへの `--resume` と明示的な再開指示を送る。
- 同じ親プロセス・worktree・排他ロック・初回マーカー・レビュー履歴・修正予算を保持する。完了済みの実験を再実行せず、成果物検証を通ってから次工程へ進む。
- 状態ファイルと初回プロンプトは0600で保存する。上限理由・元の応答ファイル・表示リセット時刻・待機方針・再開予定時刻を残す。上限前後の応答は別ファイルに保存する。
- 再開不能・返されたIDの不一致・時刻解析失敗・再開上限では停止する。上限回復中に別会話へ置き換えない。通常再レビューの既存fallbackは別の経路として維持する。
- launchdの固定5時間待機を維持する。直接実行では表示リセット時刻に30秒を加える。Mac再起動・親プロセス終了後の自動復旧は追加していない。

## 認証済みCLIによる小規模検証

Claude Code 2.1.321、`claude-sonnet-5` / medium、隔離した一時ディレクトリ、ツール無効で実施。初回だけにランダムな検証用文字列を含め、別の呼び出しで以前の会話から取り出せるか比較する。検証用文字列や認証関連の応答フィールドをリポジトリへ保存しない。

09:48 JSTの初回呼び出しは、事前指定したIDを返し、実際の `usage_limit_reached` で終了した。CLIの保存履歴には初回のユーザー指示が残っていた。表示された解除予定は10:00 JST。

10:00:30 JSTに同じIDを指定して明示的な再開指示を送った。10:00:35 JSTにexit 0、`is_error: false`、同じsession ID、`terminal_reason: completed`で完了した。再開指示には検証用文字列を含めず、以前のユーザー指示だけにある値を正しく取り出せた（比較一致）。

最小化した実測記録はローカルの `logs/agent/diagnosis-claude-usage-resume-20261110/authenticated-session-resume.json` に保存した。初回は `--session-id`、再開時は `--resume` を用い、再開時にはJSON schemaも指定した。認証関連のフィールド・検証用文字列・応答全文は記録から除いた。実測ログは公開コミットに含めない。

この検証は小規模な会話継続の確認であり、記事パイプライン全体や5時間待機の実証とは分ける。利用枠を意図的に使い切る操作は行っていない。

## 運用への適用

実装直後の検証時点では、修正は未コミットで定期実行へ未反映だった。その後、利用者から定期実行への反映指示を受けた。恒久採用は、最新mainを基にしたコード改修PRの検証・マージを経て、クリーンな定期実行入口へ適用する。

このリポジトリはfetchした基準ブランチのSHAから制御コードを実行し、共有checkoutの未コミット制御コードを拒否する。作業ファイルの修正だけでは反映完了と扱わない。元の共有checkoutには未コミットの下書き等があるため、それを保持し、同じGitリポジトリのクリーンな定期実行用worktreeを入口にする。Git共通ディレクトリ・運用ストア・排他ロックは共有する。登録済みの実行時刻・待機設定は維持する。

適用SHA・PR・元のlaunchd設定・切り替え後の確認結果は、Git管理対象外の `<git-common-dir>/article-runtime/adoptions/claude-usage-resume-20261110/` に保存する。採用時はモデルを使わない通常モードのdry-runで選択SHAを確認し、実際の記事実行は次回のrunログと照合する。

### 必須CIの解除と自動マージの維持

反映時にGitHub Actionsが課金問題のアカウントロックで起動できず、必須CIがマージを阻んだ。利用者の指示により `article-pipeline-tests` の必須マージ条件を解除した。CI workflow自体と、それ以外のブランチ保護は維持する。

利用者は記事の自動マージ維持も指定したため、公開処理に明示設定 `AGENT_QUEUE_MERGE_TRANSPORT=base-lease` を追加した。定期実行用LaunchAgentでこの設定を使い、必須CIに代えて検証済みmainと承認済みPR headの両方をatomic pushのleaseで照合する。既定の `github` 方式は変更しない。詳しくは[必須CIなしの自動マージ](article-runtime.md#必須ciを使わない運用での自動マージ)を参照。

追加の回帰検証は、必須CIなしの正常マージ、base更新時の再検証、競合回数上限、PR headの変更・巻き戻し、baseの巻き戻し、検証直後の記事本文変更、atomic非対応サーバー、push応答喪失、GitHubのマージ状態反映遅延後のreceipt再開を対象とする。ローカルbare remoteと模擬GitHub CLIを使い、公開記事の実マージはテストに使わない。

記事の生成・公開を伴う本番パイプラインの起動、公開キューへの実追加、スケジュール変更は行っていない。
