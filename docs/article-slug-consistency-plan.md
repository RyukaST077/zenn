# 記事slugと登録済み契約の一致を保証する修正方針

## 現行実装の不足

調査スキルは契約の事前登録を要求する一方、執筆スキルはslugを新しく選ぶ指示になっている。執筆プロンプトも登録済みslugと出力先を固定していない。

`scripts/agent-stage-result-contract.mjs` は記事ファイル名と工程応答の `metadata.slug` が一致するかを検証するが、調査時の契約との一致は検証しない。修正スキルもslug変更時の画像・記事パス更新だけを扱い、契約との整合性を要求していない。

公開ヘルパーの登録チェックは必要な防止策として機能した。ただし、問題の検出が執筆・レビュー完了後まで遅れた。

## 修正方針

### 1. 調査完了時に正式なslugを確定する

調査レポートの契約からslugを取得し、`analytics/contracts/<slug>.json` を登録の正本として照合する。実行状態に正式なslugと契約パスを保存し、後続工程に明示的に渡す。

- レポート内の契約を検証し、登録ファイルの存在、内部のslug、割り当て済みの `arm`・`experimentId` との一致を確認する。
- slugの文字種と長さを、記事生成側の規則と共通化する。既存記事との衝突も執筆前に確認する。
- `register-article.mjs --check --from-research` は入力契約の妥当性を調べるだけで、登録ファイルの存在・一致までは保証しない。登録状態を確認する検証を追加する。
- 登録済み契約を `--force` で上書きしたり、別slugで追加登録したりして不整合を隠さない。

### 2. 執筆・修正工程のslugを固定する

執筆プロンプトに正式なslug、契約パス、出力先 `articles/<slug>.md` を指定する。執筆・修正スキルには、登録済みslugを引き継ぎ、タイトル変更ではslugを変更しないことを明記する。

登録済み契約がある場合、台帳の有無だけに依存せず、契約の正本を参照する。台帳は派生データであり、実行環境によって欠けても登録内容が失われた扱いにはしない。

真にslug変更が必要な場合は通常の執筆処理から切り離し、記事、画像参照、契約、派生台帳、レビュー・公開キュー参照を整合させる専用の移行として扱う。今回の再発防止のために自動改名機能を必須にはしない。

### 3. 工程の境界で機械的に照合する

執筆直後、各修正直後、再開時、公開キュー追加直前に共通の検証処理を呼ぶ。

```text
調査レポートのslug
  = 実行状態の正式なslug
  = 登録ファイル名と内部のslug
  = 記事ファイル名のslug
  = 工程応答のmetadata.slug（当該工程に存在する場合）
```

不一致はその工程の失敗として記録し、正式なslugを明示して同じ工程を上限付きで修復する。修復できない場合は成果物を保存して停止し、レビューや公開処理へ進めない。エラーには期待値、実際の値、参照した契約パスを含める。

公開ヘルパーの最終チェックも維持する。登録ファイルの存在だけでなく、内部slugと正式なslugとの一致を検証し、ヘルパーの直接実行でも不一致を検出できるようにする。

### 4. 再開時も同じ登録を使う

保存済みの実行状態と契約から正式なslugを復元し、再開時に照合する。既存runに新しい状態ファイルがない場合は、そのrunの明示的な調査レポートと登録ファイルから対応を確認する。「最新の契約」や似た名前を推測して選ばない。

対応を確認できなければ明確な理由で停止する。再開に伴って契約を重複登録したり、登録日時や実験の割り当てを変更したりしない。

### 実装した構成

- 共通ヘルパーは `scripts/article-identity.mjs`。slug規則を登録処理・工程応答・記事チェックで共有する。
- `logs/agent/pipeline-*/arm-allocation.json` に調査前の割り当てを保存し、シェルに保持した値とも一致を確認する。
- `logs/agent/pipeline-*/article-identity.json` に正式なslug、記事パス、調査レポート、契約パス、実験割り当て、レポートと契約のSHA-256を保存する。
- 成功した実験のディレクトリにも `article-identity.json` を保存し、`--resume-after-run` で読み戻す。旧runは指定された実行ログ→manifest→調査レポート→登録済み契約の対応を確認して一度だけ状態を作る。現在の実験割り当てへの変更や再登録は行わない。
- 執筆・修正・レビューのslug不一致は既存の `MAX_AGENT_STAGE_CONTRACT_REPAIRS`（既定1回）内で同工程を修復する。契約や調査レポート自体の改変は修復で書き戻さず停止する。
- 公開ヘルパーは `--identity-state` を受け取り、正本と記事を照合する。単独呼び出しでも、契約があればファイル名と内部slugを検査する。
- 初回実行では現在のworktreeに加え、共有成果物のスナップショット内の記事との衝突も検査する。
- 他の通常記事パイプラインには共通の登録slug規則・記事チェック・公開時の内部slug検証が適用される。今回の工程間状態と自動修復の対象はAI記事パイプラインであり、通常記事パイプラインの工程制御を置き換える変更ではない。

## 回帰テストと受け入れ条件

外部AIやGitHubに接続しない既存の模擬CLI・隔離リポジトリ方式で検証する。

| ケース | 期待結果 |
| --- | --- |
| 登録・執筆・修正が同じslug | 公開キューへ進み、記事と契約が同じ変更に含まれる |
| 執筆だけ別slugを返す | レビュー前に検出し、同じ工程で修復する。未解消なら停止する |
| 修正でslugを変える | 次のレビュー・公開処理へ進む前に検出する |
| レポートに契約はあるが登録ファイルがない | 実験・執筆前の登録確認で検出する |
| 登録ファイル名と内部slugが異なる | 工程間検証と公開ヘルパーの双方で拒否する |
| 登録内容と割り当てた実験群が異なる | 別の契約として流用せず拒否する |
| 正常なrunを再開する | 同じslugと契約を使い、登録・実験件数を増やさない |
| 再開時に契約が欠ける・対応が曖昧 | 推測で補完せず、証拠を残して停止する |
| 9/28と同じ52文字のslugで登録する | 登録時に拒否する。後段で短縮させない |

不一致が残るケースではpush・PR作成へ到達しないことも確認する。対象テストとリポジトリで必要なチェックを通した後、正式な運用コードへの採用は [article-runtime.md](article-runtime.md) の手順に従う。

## 2026-09-28の記事を復旧する手順

以下は実施予定の手順であり、復旧済みの記録ではない。

1. 保存済みrunの本文、契約、レビュー、ログを保持して、対象runを明示して復旧する。
2. 元の保存runを変更せず、復旧用のコピーを作る。既存記事の短いslug `claude-doctor-prompt-audit-checklist` を移行先とし、同名の記事・契約・公開キューとの衝突がないことを確認する。52文字の旧slugには戻さない。
3. 復旧コピー内で契約ファイル名・内部slug・調査レポート内のslug・存在する派生台帳や関連参照を揃え、旧名の契約を有効な登録一覧に残さない。元の契約内容・登録日時・実験割り当ては保持し、新規登録や `--force` による再登録は行わない。変更対象、旧→新の対応、元ファイルのハッシュを移行記録に残す。過去のレビューや実行証拠を合格扱いに書き換えない。
4. 記事の決定的チェックとslugの一致検証を実施し、変更後のファイルを対象とするレビューを取り直す。過去の合格記録は書き換えない。
5. 合格した成果物と契約を公開キューへ渡し、PR・マージ・公開の各結果は実際に確認した範囲で別途記録する。

## 検証と運用への反映

`scripts/test-article-identity.mjs` は実際の登録コマンドを使い、登録の欠落・不一致、文字数、記事衝突、契約改変、再開、二重登録の防止を検証する。`scripts/test-agent-review-continuity.mjs` はClaude/Codex両方の模擬CLIで執筆・修正の改名、修復不能、契約改変、新規実行、再開時の欠落を通す。`scripts/test-agent-practice.mjs` は公開ヘルパーが内部slug不一致をpush・PR作成前に拒否することを検証する。

定期実行はコミット済みコードを採用するため、ローカル実装だけでは定期実行の修正完了を意味しない。テスト後のコード採用は [article-runtime.md](article-runtime.md) の手順に従う。コードの検証と9/28の記事の移行・再公開は別々に記録する。

2026-09-29の検証結果: `npm test`（全スイート）、`node scripts/test-article-identity.mjs`、変更した3スキルの `quick_validate.py`、`git diff --check` が成功した。テストは模擬CLIと隔離Gitリポジトリを使用し、実記事の公開は行っていない。[原因・修正・検証のナレッジ](../knowledge/2026-09-29-agent-article-slug-contract-mismatch.md)も参照。
