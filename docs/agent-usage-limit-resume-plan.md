# Claude利用上限後の会話継続方針

作成日: 2026-11-10。合意した修正仕様。実装済み。検証結果と運用への適用手順は[検証記録](agent-usage-limit-resume-verification.md)を参照。

## 達成する動作

AI記事のClaudeオーケストレーターが利用上限で終了したら、親スクリプトが待機し、同じ工程の保存済み会話に再開指示を送る。人による追加チャットを必要としない。別工程へ進むときは、その工程用の会話を使う。

「会話を引き継ぐ」は、保存された履歴を読み込んで次の指示を実行する意味であり、終了したプロセスやモデル内部の未保存状態をそのまま復元する意味ではない。

## 変更仕様

### 1. 上限エラーの分類

- Claudeの終端エラー応答の `api_error: usage_limit_reached` を優先する。旧メッセージと `5-hour limit` は互換用に認識する。
- 成功した本文・ツール出力・過去の上限説明を走査して上限扱いしない。429だけでも利用枠切れと断定しない。
- 現在使用するJSON出力を確実に扱う。JSONLを受け付ける場合は、イベントを個別に解析して終端結果を選ぶ。JSONL全体への正規表現検索で代用しない。
- 「対象外」と「利用上限だがリセット時刻を解析できない」を分離する。後者は原因を明示して停止し、テーマ変更による再試行に流さない。
- 同じ検出器を使う通常記事の待機処理との互換性を確認する。

### 2. 工程ごとの会話保存

- 対象はClaudeで呼ぶsearch / plan / analyze / draft / review / revise。`--no-session-persistence` を外す。
- 初回起動前にUUIDを生成し、工程の状態へ原子的に保存してから `--session-id` で渡す。完了応答が出ない初回中断でも対象IDを失わない。
- セッションID、pipeline・記事identity、工程・round、初回開始時刻、入力と指示の識別情報、試行回数、上限理由、表示リセット時刻、実際の再開予定時刻、状態を記録する。
- 出力にsession IDがあれば予定IDと照合する。異なるIDへ黙って切り替えない。
- reviewの同一記事内の継続は既存方針を維持する。別工程・別記事・別roundの修正作業を誤って混ぜない。
- 保存を無効にする環境設定などが有効な場合は、再開可能と表示せず診断する。

### 3. 上限後の再開

1. 上限応答と工程状態を保存し、状態を `waiting_usage_limit` にする。
2. 親スクリプトは同じworktreeと排他ロックを保持して待機する。テーマ試行回数・修正回数・通常の障害連続回数を消費しない。利用上限専用の再開回数上限は維持する。
3. 待機終了後、同じ工程を `--resume <session_id>` と明示的な再開指示で呼び出す。`--continue` による「直近セッション」の推測は使わない。
4. 再開指示には、対象工程・入力・必要な出力契約を明示する。既存成果物と会話を確認して未完了部分を進めるよう指示し、完了済みの外部操作を無条件に繰り返させない。
5. CLIの成功だけでは次工程へ進めない。既存のschema、成果物、記事identity、レビュー履歴の検証を通ったときだけ工程完了とする。

初回の例:

```bash
claude -p "$stage_prompt" --session-id "$session_id" --output-format json
```

再開の例:

```bash
claude -p "$resume_prompt" --resume "$session_id" --output-format json
```

実装では両方に必要なschema、モデル、effort、権限、ツール制限などを渡す。例は引数の要点のみ。

上限応答の出力と再開後の出力は別ファイルに残す。工程の初回マーカーとreviewスナップショットを保持し、中断前に作られた有効な成果物を単に再開時刻より古いという理由で棄却しない。ただし完了検証は省略しない。

同じ会話を復元できない場合は `resume_unavailable` として診断情報・成果物を残して停止する。今回の上限回復経路では、新しい会話への切り替えを「再開成功」と扱わない。既存の通常再レビュー用fallbackとの違いをコードとテストに明示する。

### 4. 待機時間

今回の既定は現行launchdの「上限到達から5時間待つ」を維持する。今朝の例なら再開予定は12:16ごろで、表示されたリセット時刻10:00とは別になる。

ログでは「検出した上限」「表示リセット時刻」「待機方針」「実際の再開予定時刻」を分ける。現状の `test override` 表示で本番の固定5時間待機を説明しない。

リセット時刻が取得・解析できないときは、今回は固定待機へ推測で進まず停止する。週間上限など、5時間で解除すると確認できない種類へ対象を広げる際は待機方針を別途決める。

### 5. 実験と公開の扱い

run工程は `run-experiment.mjs` による直接実行であり、記事オーケストレーターの会話再開と分ける。認証済み実験CLIを同じ仕組みで自動再試行したり、完了した実験を上限回復のために再実行したりしない。

今回の実装・検証では記事の公開やキュー追加を行わない。既存のレビュー合格・成果物検証・公開条件は維持する。

## 検証と合格条件

| 層 | 確認すること | 言える範囲 |
| --- | --- | --- |
| 検出器の単体検証 | 今回の応答、新旧文言、構造化コード、時刻欠落、通常429、成功本文への言及、過去エラー後の成功 | 分類と待機情報の解析が正しい |
| 模擬CLIによる統合検証 | 初回中断を含む6工程で同じIDへ再開指示を送る。終了コード0でもerror応答を検出する | スクリプトの引数・状態遷移・再開先が正しい |
| 状態維持の検証 | round・修正予算・identity・初回マーカーを保持する。再開不能やID不一致で停止する。実験・公開の重複実行がない | 工程の制御と成果物検証が正しい |
| 認証済みCLIの小規模検証 | 隔離fixtureで事前指定IDの保存、同じIDでの再開、以前の会話にだけ含めた情報の保持を確認する | 当該CLI版・設定での通常の会話継続が動く |
| 中断と実際の上限 | 制御した中断と実際の利用上限を区別する。SIGTERMは上限の代用と断言しない。次の自然な上限で自動待機・同一ID再開・工程完了を記録する | 実上限からの復帰は、その記録が得られた範囲で確認済みとする |

模擬CLIと実機検証の証拠を混ぜない。上限を再現するために利用枠を意図的に使い切らない。待機を0秒にする設定はテスト専用に明示する。

既存の `test-agent-practice.mjs`、`test-agent-review-continuity.mjs`、通常記事側の `test-claude-limit-resume.sh` を更新し、必要に応じて会話状態の独立テストを追加する。関連テスト後に `npm test` を実施する。

## 実装の順序と適用

1. 今回の応答の回帰fixture、上限分類、解析不能時の分岐を修正する。
2. 工程の会話保存と起動前ID記録、同一工程への再開指示、成果物検証との整合を実装する。
3. 模擬CLIの統合検証と全体テストを通す。
4. 隔離fixtureで小規模な実機検証を行い、確認できた範囲と未確認の実上限復帰を報告する。
5. 既存のSHA固定worktree運用に従って採用する。作業ファイルを編集しただけでは定期実行への適用完了としない。適用後の実行SHAとログを照合する。

## 今回の範囲外

- Mac再起動や親スクリプト終了後の無人復旧。状態ファイルの保存だけで、この復旧まで実装済みとは扱わない。
- 今朝終了済みの会話の復元。保存を無効にしていた工程を後から復元できるとは約束しない。
- Codexオーケストレーターおよび実験内部のセッション方式変更。
- テーマ選定、検証不足、reviewレポート不整合、起動時刻の設定不一致の修正。

計画の方針は「利用上限の検出 → 会話と工程状態を保存 → 待機 → 同じ会話へ明示的な指示 → 成果物検証 → 次工程」である。
