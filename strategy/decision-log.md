# 方針決定ログ

`strategy/topic-selection-policy.json` を変えた／変えなかった理由を残す。
方針は人間がPRをマージしたときだけ変わる。ここは「なぜそう決めたか」の履歴。

## 2026-09-05 — policyVersion 2026-09-05.1（ループ導入）

### 何を観測したか

| 観測 | 値 | 取得元 |
|---|---|---|
| 自分の公開記事 | 57本 | `/api/articles?username=clopy` |
| いいね合計 / 平均 / 最大 | 42 / 0.74 / 3 | 同上 |
| 5いいね以上（hit） | 0本 | 同上 |
| ブックマーク / コメント | ほぼ0 / 0 | 同上 |
| 公開ペース | 2026-07: 20本, 2026-08: 31本 | 同上 |
| 市場（claudecode 新着48本） | 中央値0いいね・0いいね60%・p90=4・5+到達6% | `/api/articles?topicname=claudecode&order=latest` |
| 市場の最上位 | 657「202608個人的claude code設定」/ 241「minitypeを公開しました」/ 175「なぜ非推奨か」/ 78「トークン2000分の1」 | `/api/articles?order=liked_count` |

### 何を決めたか

1. **不人気の主因は「粗いテーマ選定」ではなく「価値の型と粒度」と診断した。**
   Claude Code / Node / TypeScript というカテゴリ選択は市場と合っている。問題は、その中で
   「Read denyがリダイレクトを塞ぐか」のような単一の境界条件を1記事にしていて、
   読者の持ち帰りが無く対象読者が極小になっていること。

2. **投稿頻度は主因から外した。** 月20〜30本出して57本すべてが低反応なので、
   頻度を上げても同じ結果になる。頻度は独立した実験として後回しにする。

3. **改善ループの主駆動輪を「市場観測」にした。**
   自分の記事は最大3いいねで分散がほぼ無く、記事単位の勝敗判定はノイズしか返さない。
   よって仮説は市場の上位記事から取り、自分のデータは「適用失敗の早期検知」と
   「劣化検知」にのみ使う。

4. **判定指標から「平均いいね」を外した。**
   いいねはゼロ過剰・裾が重い分布で、平均は1本の当たりに支配される。
   短期の主指標は「年齢を揃えた同トピック市場コホート内のパーセンタイル」にした。
   平均・非ゼロ率は劣化検知のみ。

5. **hit（5いいね以上）で方針を昇格させないことにした。**
   市場のhit率は約6%。12本のバッチで期待hit数は0.7本なので、1本出ても勝ち型の証拠にならず、
   0本でも失敗の証拠にならない。hitは追試候補を示す発見シグナルとしてのみ扱う。

6. **同時期A/Bをやらず、過去57本を歴史的対照群にした。**
   現行型に新規6〜8本を割くのは、5いいね以上が0本の型に生産枠を捨てる行為。
   交絡（Zenn全体のトレンド変動・季節性）は同時期・同トピック市場コホートとの相対順位で補正する。
   対照群のD30値は復元できないため現在値を保守的な上限として扱う（対照群に有利な向きの誤差）。

7. **`boundary-verification` と `incident-log` を deprecated にした。**
   ただし検証内容そのものは捨てない。asset / migration / decision 型の記事を裏づける
   証拠として3〜5本束ねて使う。

8. **policy の書き換えは人間のPRマージに限定した。**
   このリポジトリには「publish PRを人間がマージ＝公開ゲート」という前例があるので、
   方針変更も同じゲートに乗せる。自動更新に上限を付ける案（±5ポイントまで等）は、
   反復でドリフトするため採らなかった。

9. **GA4を接続したが、判定には使わないことにした。**
   `evaluate-policy.mjs` はGA4を一切読まない。GA4は到達（PV）を観測して
   「いいね0の原因が上流か下流か」を診断するためのもので、方針の昇格・撤回は
   `experiments/EXP-GA4-DIAG-001.json` に事前登録した判定線を人間がPRで判断する。
   主指標を市場パーセンタイルからPVファネルへ移す案は採らなかった。目的が
   「Zenn内で上位に入る」である以上、直接対応するのは市場順位であり、
   PVは「なぜ入れなかったか」を分解する指標。1つの合成点にはしない。

10. **PVが増えても必要本数は減らないと判断した。**
    実験単位は記事であって閲覧者ではないので、1記事の1000PVを1000標本と数えられない。
    最初の10〜15本でできるのは分散推定とボトルネック診断まで。policy昇格の
    24本・2バッチ条件は維持する。

11. **GA4由来の記事別数値を公開リポジトリに置かないことにした。**
    このリポジトリはPUBLICで、`--pr` は `git add analytics` する。記事別PV・
    ユーザー数・流入元がそのままPRに乗る構造だった。`analytics/private/` に分離し
    （`.gitignore` 済み・worktree同期対象外）、コミットされるレポートには帯と本数と
    比率だけを出す。サービスアカウント鍵も `~/.config/zenn-ga4/` に移した。
    このツリーは無人の自律エージェントが読み書きするので、`.gitignore` だけでは
    鍵の読み取り経路が閉じない。

12. **データを見る前に撤回条件を固定した。**
    「テーマの粒度と価値型が主因」という診断のうえに EXP-001 と deprecated 判断が
    乗っているので、GA4が来た時点でこの診断は初めて反証可能になる。事後に
    判定線を動かして物語を作らないよう、`R=100` / `R=300` / `impliedRate=0.005`
    まで含めて `EXP-GA4-DIAG-001.json` に事前登録した。
    比較群を使う設計（Codex提案）は、比較対象になる価値型の記事がまだ公開されておらず、
    過去記事のD30いいね率が原理的に作れないため、段階2に回した。
    段階1は比較群不要の絶対値判定にした。過去記事の分子（`current-upper-bound`）は
    真のD30いいね率の**過大評価**なので、「率が低い」だけは片側で結論に使える。

### 何をしなかったか

- **Zennの露出（インプレッション）の取得**: 非公開。GA4で取れるのは「記事ページへの到達」で、
  フィードや検索結果での表示回数ではない。「到達が低い」までは言えるが、その原因を
  テーマとタイトルに分けることはできない。
- **過去記事のD30いいね率の復元**: D30到達は復元できるが、D30時点のいいね数は
  復元できない。分子が揃わない率は作らない（`likeRateBasis: numerator-not-aligned`）。
- **タイトル長の最適化**: 57本中55本が35文字以上で、短いタイトルは2本しかない。
  効果を判定できるデータが無いので、独立した実験にはせず、契約側で
  「検証行為ではなく読者の利得を主語にする」という定性ルールだけ課した。

## 2026-09-05 — 実験群への割り付けを自動化した（policy変更なし）

`strategy/topic-selection-policy.json` は変えていない。変えたのは、方針を実際に
実行に移す配管のほう。

### 何を観測したか

`analytics/article-ledger.jsonl` の契約登録ぶん（`classification.source == "contract"`）:

| arm | 本数 |
|---|---:|
| `B-payload`（EXP-001 の実験群・目標12本） | **0** |
| `exploration` | 2 |
| `legacy-transition` | 1 |

**EXP-001 は登録から一度も実験群に記事が割り当てられていなかった。**
方針は「新規記事は全て新方針に振る」と書いてあるのに、実際に割り付ける仕組みが
どこにも無く、契約を書くエージェントが毎回自分で `arm` を選んでいた。結果として
2本とも `exploration`（`mental-model`）に流れ、実験は永久に判定に届かない状態だった。

もう一つ、`scripts/auto-agent-practice.sh` の検索プロンプトが
`Prefer a boundary, failure mode, ...` と書いており、**deprecated にしたはずの
`boundary-verification` をパイプラインが名指しで要求し続けていた**。
スキル側（`zenn-agent-search-knowhow`）は policy を読んで正しく制約していたが、
シェル側のプロンプトがそれを上書きする位置にあった。57本が同じ型に偏った理由の
機械的な部分はここにある。

### 何を決めたか

1. **`arm` の決定を研究ステージから取り上げた。**
   `scripts/analytics/next-arm.mjs` が台帳から次の1本の `arm` を決め、
   検索プロンプトに注入する。記事のテーマを見る前に群が決まる。
   自己申告に任せると、書きやすい型に寄るのは今回の2本で実測済み。

2. **割り付けは乱数ではなく決定的にした。**
   12本のバッチで乱数を引くと、実験群が数週間埋まらない引きが普通に起こる。
   探索枠（25%）は後回しではなく等間隔で挟む（B,B,B,E,B,B,B,E）。
   後回しにすると candidate 型の証拠がいつまでも溜まらない。

3. **満杯・終了した実験には13本目を入れない。**
   `treatment.n` に達したら以降は `exploration` に回し、D30判定を待つ。

4. **検索プロンプトから「単一の境界を選べ」を消した。**
   境界検証は記事ではなく記事の中の証拠、と明示した。

### 何をしなかったか

- **policy の重み・ゲートは変えていない。** 今回の問題は方針ではなく実行経路。
- **`explorationShare` の値は動かしていない。** 0.25 のまま。
  今回入れたのは「その比率を実際に守る仕組み」であって比率の見直しではない。
- **過去2本の `exploration` を `B-payload` に付け替えていない。**
  契約は選定時に凍結する規則があり、後から群を付け替えるのは事後の割り付けそのもの。
  割り付け器はこの2本を「探索枠は先に使い過ぎている」と読み、次の12本を実験群に寄せる。

## 2026-09-07 — ループを git に載せ、契約を割り付けの入力に固定した

### 何が起きていたか

パイプラインは 09-06 と 09-07 に `arm allocation failed` で即死していた。
`strategy/` `analytics/` `experiments/` `scripts/analytics/` が共有チェックアウトの
未追跡ファイルでしかなく、`origin/main` から作る worktree に存在しなかった。
09-05 以降、記事は1本も生産されていない。

### 何を決めたか

1. **ループのファイルを main にコミットした。** オーバーレイのコピー一覧を増やす対症処置は取らない。
2. **観測の3ファイル（台帳・市場インデックス・観測レポート）は worktree から書き戻さない。**
   日次ループが毎朝共有側で書き換えるので、両側が触ると衝突判定で実行ぶんの成果物が丸ごと破棄される。
   代わりに **shared → worktree の一方通行で毎回渡す**（`import-analytics`）。
   再開時だけでなく通常実行でも渡す。渡さないと、最後に analytics/ をコミットした時点の
   古い台帳で群を決めてしまう。
3. **契約（`analytics/contracts/<slug>.json`）を権威にした。** 割り付け・登録済み判定・収集の
   優先順位をすべて契約ファイル側に揃えた。台帳は派生。
4. **契約は記事と同じコミットで main に載せる。** `enqueue-reviewed-article.sh` が
   記事・キュー・画像に加えて契約もステージする。これが無いと、共有側へ契約を書き戻せても
   翌日の worktree は origin の契約しか見えず、**実験は永久に 0/12 のまま**で
   全記事が実験群に流れ続ける（探索25%も機能しない）。

### 既知の制約（次の実験を開くときに決める）

`next-arm.mjs` は実験群の本数を現在の実験に限定して数えるが、探索枠は全期間ぶんを数える。
EXP-001 の1バッチ内では問題にならない。EXP-002 を開いた時点で、
前実験の探索枠が「先払い済み」と読まれ、新しい12枠が全て実験群に寄る。

いま直さないのは、2026-09-05 の決定が現在の2本（EXP-001 開始前の 09-04 登録）を
「探索枠は先に使い過ぎている」と読ませる挙動を明示的に選んでいるためで、
集計期間を揃えるとその決定を黙って覆すことになる。次の実験を開くときに、
探索枠を実験ごとにリセットするのか通算で持つのかを決めてから直す。

## 2026-09-08 — 「成功したのに実験が進まない」経路を塞ぎ、ループを漏斗として可視化した

Codex に独立した相談役として4問（手動実行の是非・書き直し8本の投入・最も価値のある作業・幽霊契約の削除）を
投げ、その回答をコードで検証してから対応した。回答のうち2件は実際に成立する欠陥だった。

### 何を観測したか

`loop-status.mjs` を作って初めて見えた状態。

```
B-payload         登録   0 → 記事   0 → キュー   0 → 公開   0 → D30実測   0
exploration       登録   1 → 記事   1 → キュー   0 → 公開   0 → D30実測   0
legacy-transition 登録  11 → 記事  11 → キュー   0 → 公開   0 → D30実測   0
queue: 6 pending / 0 blocked / 6 pending without a contract
```

登録12本は全て未公開かつキュー外、キューの6本は全て契約なし。
ループの両輪が**完全に別の記事集合**を指していた。「12本登録済み」という単一の数字がこれを隠していた。

### 何を決めたか

1. **arm を割り付けた実行は、契約が main に届かない限り push させない。**
   `enqueue-reviewed-article.sh` は契約を「あればコピー」していただけで、
   登録を失った実行が exit 0・PRマージ・Zenn公開まで進み、実験は 0/12 のままになりえた。
   `auto-publish.sh` と `auto-publish-codex.sh` は契約を登録しないので一律必須化はできない。
   agent パイプラインだけが `--expect-arm <arm>` を渡し、契約欠落と arm 不一致を push 前に止める。
   再開実行は前回が割り付けているので `--require-contract` のみ。

2. **キューの諦め時間を 156h → 168h に直した。**
   `publish` の時点で `attempts` が 1 になり `block` 判定は backoff より**前**にあるため、
   `attempts` が N に達するのは N-1 窓後。`14 × 12h` は 168h に見えて実際は 156h で、
   Zenn 実測 p90（168h）の内側で諦めていた。`maxAttempts` を 15 にし、
   テストガードを「回数の積」から**状態機械を1時間刻みで回して経過時刻を検証する**方式へ差し替えた。
   校正の主張は時間についてのものなので、時間で検証する。

3. **ループを漏斗として報告する（`scripts/analytics/loop-status.mjs`）。**
   `next-arm.mjs` は**登録**で arm を埋めるが、EXP-001 が判定に達するのは
   **公開されて D30 計測された**記事だけ。この2つは別の数で、差を報告する仕組みが無かった。
   arm 別に 登録／記事／キュー／公開／D30実測 と、契約を持たないキュー項目数を出す。

4. **05:00 の launchd 実行を待ち、手動実行はしない。** 検証したいのは本番経路そのもので、
   手動実行は変数が増えるうえロック競合を招く。成功条件は「完走」ではなく
   **最終記事と一致する B 契約が main に入り、次回の同じ入力条件で B=1 になること**。

5. **書き直し8本をいまキューに入れない。** キューは常に先頭1本だけを扱い実験群の優先機能が無いので、
   8本を先に入れると後から完成する B 記事がその後ろに回る。
   legacy は実験記事の供給が切れた枠へ少量ずつ入れる。

### 既知の制約（孤児契約が枠を焼く）

`run-article-pipeline-worktree.sh:135` の `sync` は `PIPELINE_RC` に関係なく実行され、
`import-analytics` は共有チェックアウトの契約を次回 worktree へ渡す。
よって **arm を登録した直後に失敗した実行は、記事の無いまま treatment 枠を永久に消費する契約を残す**。

`next-arm.mjs` 側で数えないのが筋だが、**05:00 の実行3時間前に割り付け意味論を変えるのは危険側の賭け**。
焼けた枠は検出可能でファイル1つの削除で回復するが、壊れた allocator はパイプラインを止める
（直前に3日間それをやった）。よって当面は `loop-status.mjs --strict` で報告に留め、
意味論の変更は最初の成功実行を見てから判断する。

回復手順: `node scripts/analytics/loop-status.mjs --strict` が孤児を名指ししたら、
その `analytics/contracts/<slug>.json` を共有チェックアウトから削除する
（main に無いことは同ツールの `reachedMain` が示している）。

### Codex の指摘のうち採用しなかったもの

- 「契約必須化を enqueue 全体に適用」→ `auto-publish*.sh` 2経路を壊すため、arm 割り付け経路限定にした。
- 「共有側に旧契約と ledger 行が残っている」→ Codex のスナップショット時点の情報。
  指摘を受けた 09-07 に削除し、実際の `import-analytics` 経路で `exploration=1` を確認済み。

### 別件で見つかったこと

共有チェックアウトのローカル `main` が `origin/main` より75コミット遅れている。
`scripts/analytics/` などがローカルでは未追跡に見えるため、`loop-status.mjs` の初版は
`git ls-files` で全12契約を誤って孤児と報告した（ベースブランチの tree を読むよう修正）。
パイプラインは `origin/main` から worktree を作り制御スクリプトは作業ツリーから上書きするため
実行には影響しない（制御スクリプト60件は origin/main とバイト一致を確認）。
作業ツリーに40件以上の変更がある状態で実行直前に統合するのは risk が高いので、いまは触らない。
