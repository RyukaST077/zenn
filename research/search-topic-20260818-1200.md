## 上位候補の詳細

### 1. TypeScript 7.0 GA に上げて、typescript-eslint を生かしたまま `tsc` だけ10倍にする

#### 概要

TypeScript 7.0（`typescript@7.0.2`）はGoネイティブのコンパイラでGAしたが、**プログラマティックAPI（`ts.createProgram` / `ts.factory` 等）を同梱していない**。そのため typescript-eslint / ts-jest / ts-morph / Vue・Svelte・Astro のテンプレート型チェックは7.0では動かない。公式の回避策が `@typescript/typescript6`（`tsc6` バイナリ＋6.0 API再エクスポート）と npm alias による併存構成。これを小さなプロジェクトで実際に組み、「どこまで速くなり、何が壊れ、aliasでどう戻るか」を測る。

#### なぜ今よさそうか

- 2026-07-08 GA、gihyo・Publickey・InfoQ が揃って扱っている直近トピック
- 「上げたら速い」より「上げたらlintが死ぬ」の方が実務で先に来る問題で、日本語の検証記事がまだ薄い
- 自分の過去記事 `typescript7-tsc-bin-collision-log` は **`tsc` の bin 衝突で検証が止まった記録**。GA版と公式回避策で「あの続き」を書けるので、シリーズとして自然

#### 新人が検証しやすい理由

`npm install` と `package.json` の編集、`tsc --version` / `time tsc --noEmit` / `eslint .` の実行だけで完結する。壊れ方がエラーメッセージとして明確に出るので、詰まった点をそのまま素材にできる。

#### 想定読者

TypeScript を日常的に使っていて、7.0への上げ方と「上げると何が止まるか」を知りたい新人〜実務2年目。

#### タイトル案

1. TypeScript 7.0 に上げたら tsc は速くなったが、typescript-eslint が動かなくなった
2. TypeScript 7 と 6 の併用、前回は bin 衝突で止まった。GA版と `@typescript/typescript6` で再挑戦した
3. `tsc` だけ10倍、lintは6.0のまま——TypeScript 7.0 の公式併用構成を新人が試してみた

#### 検証でやること

- 小さなTSプロジェクト（`typescript@6.0.x` + typescript-eslint + 数十ファイル）を用意し、型チェック時間のベースラインを測る
- `typescript@7.0.2` に単純アップグレードして `tsc --noEmit` の時間差を測る
- 同じ状態で `eslint .` を実行し、壊れ方（エラー全文）を記録する
- 公式推奨の alias 構成（`"typescript": "npm:@typescript/typescript6@^6.0.2"` ＋ `"@typescript/native": "npm:typescript@^7.0.2"`）に切り替える
- `tsc` / `tsc6` / `npx tsc` がそれぞれどの実装を指すか（`--version`）を確認し、前回踏んだ bin 衝突が解消されているかを見る
- `--checkers` / `--singleThreaded` を振って計測差を出す

#### 検証手順

1. `npm view typescript dist-tags` と `npm view @typescript/typescript6 dist-tags` で当日の版を固定する
2. fixture プロジェクトを作成（React などの型が重いコードを含めると差が出やすい）。`tsconfig.json` は `strict: true`
3. TS 6 で `time npx tsc --noEmit` を3回、`npx eslint .` を1回実行しログ保存
4. `npm i -D typescript@7.0.2` に上げ、同じ計測。lint のエラー全文を保存
5. alias 構成に書き換え、`node_modules/.bin` を `ls` して `tsc` / `tsc6` の実体を確認
6. TS7 で型チェック、TS6 API で lint、が同時に成立するかを確認。`--checkers 1` と既定でも計測
7. 失敗した組み合わせ（yarn 併用時の既知issue #4368 など）は再現できた範囲だけ記録

#### 記事構成案

1. はじめに（前回は bin 衝突で止まった）
2. なぜ TypeScript 7.0 を試すのか
3. 事前に調べたこと（7.0にAPIが無い、7.1で入る予定）
4. 環境構築とベースライン計測
5. 単純に上げてみる → 速い、しかし lint が落ちる
6. 詰まった点（エラー全文と原因）
7. 公式の alias 併用構成にする
8. 数字の比較表（TS6 / TS7 / TS7+alias）
9. どんな人が今上げてよさそうか（7.1待ちの判断軸）
10. まとめ

#### 差別化ポイント

「10倍速い」という数字紹介ではなく、**GA直後の移行期に実際に壊れる箇所と公式回避策の再現**に絞る。さらに過去記事で失敗した検証の続編という文脈がある。

#### 注意点

- 速度は マシン依存。CPUコア数・キャッシュ有無・実行回数を必ず明記する
- 「10倍」は VS Code 規模のコードベースの話。小さなfixtureで同じ倍率が出なくても、それ自体が正直な結果として価値がある
- alias 構成はパッケージマネージャで挙動が違う（yarn の既知issueあり）。使ったマネージャと版を明記する

### 2. `initialize` が消えたMCPサーバを、ステートレスHTTP＋curl＋Inspector 2.2 で確かめてみた

#### 概要

MCP 仕様 2026-07-28 で `initialize`/`initialized` ハンドシェイクと `Mcp-Session-Id` が廃止され、各リクエストが自己完結するステートレス方式になった。TypeScript SDK は `@modelcontextprotocol/server` / `client` が **2.0.0 でGA**。`createMcpHandler(factory)` でHTTPサーバを立て、`Mcp-Method` / `Mcp-Name` ヘッダの様子を curl で観察し、Inspector 2.2.0 から叩く。

#### なぜ今よさそうか

- 2026-07-28 の仕様公開直後で、Publickey・gihyo も一次ニュースとして扱っている
- 自分の過去記事は **beta.5 / stdio / 旧仕様**。GA・HTTP・新仕様で対象が3点変わる
- 「セッションが無くなる」は概念だけだと分かりにくく、curl のリクエスト/レスポンスを並べる記事が刺さりやすい

#### 新人が検証しやすい理由

npm install とローカルサーバ起動、curl、`npx @modelcontextprotocol/inspector` だけ。認証もクラウドも不要。

#### 想定読者

### 3. Next.js 16.3 の `instant()` で「即時表示」をPlaywrightのアサーションにしてみた

#### 概要

Next.js 16.3 は Instant Navigations を打ち出し、`@next/playwright`（16.3.1）の `instant()` ヘルパーで「ネットワークを待たずに何が見えているか」をE2Eでアサートできるようになった。あわせて DevTools の Navigation Inspector でローディングシェルを目視できる。小さなアプリで、シェルに何が入っているかをテストとして固定する。

#### なぜ今よさそうか

- 2026-08 に The Register などが取り上げた直近リリース
- 「体感速度をテストで守る」という発想自体が新しく、Playwright を使う読者に刺さる
- ローカルで完結し、Playwright があるのでAIエージェント単独検証と相性が良い

#### 新人が検証しやすい理由

`create-next-app` → 遅いデータ取得を1つ挟む → `instant()` でアサート、という短い導線。失敗時のメッセージも読みやすい。

#### 想定読者

Next.js App Router を触っていて、E2Eは書いたことがある/これから書く人。

#### タイトル案

1. Next.js 16.3 の `instant()` で「一瞬で出る部分」をE2Eに固定してみた
2. 体感速度をテストで守る：`@next/playwright` を初めて使ってみた
3. Navigation Inspector でローディングシェルを見てから、`instant()` を書いた

#### 検証でやること

- Next.js 16.3 系アプリを作り、意図的に遅いサーバ処理を入れる
- 遷移時に何がシェルとして出るかを Navigation Inspector で確認しスクショ
- `instant()` を使ったテストを書き、シェルに含まれる要素/含まれない要素でアサートが通る・落ちるのを両方作る
- prefetch を切った場合との比較

#### 検証手順

2. `create-next-app` でアプリ作成、`@playwright/test@1.62.1` と `@next/playwright@16.3.1` を導入
3. 遅延を仕込んだページを2つ用意し `next dev` で挙動確認（Playwrightでスクショ）
4. `instant()` を使ったテストを書いて green にする
5. わざとシェル外の要素をアサートして red にし、エラーメッセージを記録
6. `next build && next start` でも同じテストが通るか確認

#### 記事構成案

### 4. `pnpm change` / `pnpm lane` / `pnpm doctor` をローカルworkspaceで一周してみた

- **半日〜1日で終わる**: fixture作成＋3パターンの計測＋alias切り替えで収まる
