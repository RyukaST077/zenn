## 上位候補の詳細

### 1. Playwright 1.62 の stories & galleries でコンポーネントテストを作り直してみた

#### 概要

Playwright 1.62（2026-07-24）でコンポーネントテストのモデルが全面的に変わった。従来の「テストファイル内で JSX を直接 mount する」方式から、`*.story.tsx` に名前付き export でシナリオを書き、自分の dev server が配信する gallery ページ（`window.mount()` / `window.unmount()` を公開する単一ページ）に Playwright が遷移して story id を指定して mount する方式になった。`mount()` の戻り値は gallery root にスコープされた Locator。React / Vue が公式サポートで、実体は framework-agnostic。

#### なぜ今よさそうか

- リリースから1か月弱、日本語の実践記事がほぼ無い
- 公式が「find & replace では移行できない」と明言するレベルの破壊的変更で、既存資産を持つ人ほど知りたい情報
- 1.62.0 には回帰が3件あり **1.62.1 が推奨版**という、実際に踏みうる落とし穴が公開されている

#### 新人が検証しやすい理由

Vite + React の最小アプリに Button 相当のコンポーネントを2〜3個置くだけで足りる。`npx playwright init-skills` がフレームワーク/バンドラを検出して gallery と設定と初期 story/spec まで生成するので、ゼロから組む必要がない。すべて localhost で完結。

#### 想定読者

コンポーネントテストを書いたことがある/これから書く新人〜2年目。Storybook は聞いたことがあるが Playwright CT は知らない層。

#### タイトル案

1. Playwright 1.62 のコンポーネントテストが別物になっていたので、最小構成で作り直してみた
2. `*.story.tsx` と gallery って何？ Playwright の新コンポーネントテストを初めて書いてみた
3. Playwright CT を旧方式から stories & galleries へ移して詰まった点

#### 検証でやること

- Vite + React + `@playwright/test@1.62.1` で最小プロジェクトを作る
- `npx playwright init-skills` が何を生成するかを差分で記録する
- `Button.story.tsx` に複数 story（Primary / Disabled / WithTitle）を書き、`mount('components/Button/Primary')` から操作・アサーション
- props 付き mount と `component.update({...})` で状態が保持されるかを確認
- story 名を意図的にリネームして「実行時文字列なのでコンパイルエラーにならない」制約を実測
- 1.62.0 と 1.62.1 の挙動差（回帰）を踏めるか確認

#### 検証手順

1. `npm create vite@latest` で React + TS の最小アプリを作り、コンポーネントを2つ用意
2. `npm i -D @playwright/test@1.62.1` → `npx playwright install chromium`
3. `npx playwright init-skills` を実行し、生成物（gallery、playwright.config.ts の baseURL、初期 story/spec）を `git diff` で記録
4. `npm run dev` を起動したまま `npx playwright test` を実行、成功ログとレポートを保存
5. story 追加・props 渡し・`update()` を順に試し、各段階でスクリーンショットを取る
6. story id をリネームして失敗メッセージを記録、`@playwright/test@1.62.0` に落として差分も確認

#### 記事構成案

1. はじめに
2. なぜ Playwright 1.62 の CT を試すのか（何が変わったか）
3. 事前に調べたこと（公式 docs / リリースノート / 1.62.1 推奨の経緯）
4. 環境構築（Vite + React + init-skills）
5. 実際に試したこと（story を増やす / props / update）
6. 詰まった点（baseURL、dev server 依存、story id が文字列であること）
7. 触ってみて分かったこと
8. 既存の CT・Storybook と比べて感じたこと
9. どんな人に向いていそうか
10. まとめ

日本語の実践記事が見当たらない領域を、**生成物の diff と失敗メッセージ付き**で埋める。「概念解説」ではなく「init-skills が何を作るのか」「id をミスるとどう落ちるのか」の一次情報を残す。

#### 参考リンク

#### 注意点

- gallery は「自分の dev server」に依存するため、dev server を起動しないと全落ちする。webServer 設定を含めて記録する

### 2. MCP TS SDK v1 サーバーを公式 codemod で v2 に移行し、セッションが消えたことを curl で確かめた

#### 概要

MCP 2026-07-28 仕様が正式リリースされ、`initialize`/`initialized` ハンドシェイクと `Mcp-Session-Id` ヘッダが廃止された。リクエストは1本ごとに完結し、プロトコルバージョン・クライアント情報は `_meta` に載る。`Mcp-Method` / `Mcp-Name` ヘッダが必須になり、ゲートウェイが body を読まずにルーティングできる。TypeScript SDK は v2.0.0 が正式版になり、`@modelcontextprotocol/codemod` と `server-legacy` が同梱されている。この codemod に v1 サーバーを流し、どこまで自動で通り、どこが手直しになるかを実測する。

#### なぜ今よさそうか

- 仕様確定が7/28、SDK v2.0.0 が7/27。国内記事は「仕様解説」が数本出ているが、**手を動かした移行ログは見当たらない**
- 既存の MCP サーバーを持つ人全員に移行作業が発生する
- 「セッションが本当に不要になったか」は curl だけで検証でき、証拠が残しやすい

#### 新人が検証しやすい理由

ツール2つ程度の最小サーバーで足りる。stdio ではなく HTTP トランスポートにすれば curl 単体で確認でき、Inspector も不要。認証は不要な範囲（ローカル・トークンなし）に限定できる。

#### 想定読者

MCP サーバーを一度でも書いた人、これから書く新人。v1 の記事を読んで真似したら動かなかった人。

#### タイトル案

1. MCP の公式 codemod で v1 サーバーを v2 に移してみたら、直る所と直らない所がはっきりした
2. セッションが消えた MCP を curl で叩いて、本当にステートレスか確かめた
3. MCP 2026-07-28 仕様、最小サーバーを移行して詰まった点

#### 検証でやること

- v1（`@modelcontextprotocol/sdk@1.30.0`）で HTTP の最小サーバーを書く
- `Mcp-Session-Id` を使う旧クライアント相当の curl 手順を記録（ハンドシェイクあり）
- `@modelcontextprotocol/codemod` を実行し、変換された差分を全部載せる
- v2 サーバーを起動し、`initialize` なしの単発 curl で `tools/list` / `tools/call` が通ることを確認
- `Mcp-Method` / `Mcp-Name` ヘッダを外したときのエラーを実測
- 同じサーバープロセスを2つ立てて交互にリクエストを投げ、状態共有が不要なことを確かめる

#### 検証手順

1. `npm view @modelcontextprotocol/server @modelcontextprotocol/sdk dist-tags versions` で版を確定
2. v1 で `add` / `echo` だけの HTTP サーバーを作り、curl で疎通（ハンドシェイク込みのログを保存）
3. `npx @modelcontextprotocol/codemod` を実行、`git diff` を保存
4. 変換後にビルド・起動を試み、失敗したら手直し内容を記録
5. 単発 curl（ヘッダあり/なし）で挙動差を記録
6. 2プロセス起動 → ラウンドロビン的に交互投入して結果が同一か確認

#### 記事構成案

1. はじめに
2. なぜ今 MCP の移行を試すのか（7/28 仕様で何が消えたか）

4. 環境構築（v1 の最小サーバー）
5. 実際に試したこと（codemod 実行と diff、curl での検証）
6. 詰まった点
7. 触ってみて分かったこと（ステートレス化が実装に何をもたらすか）
8. v1 と比べて感じたこと
9. どんな人に向いていそうか

### 3. oxlint の type-aware lint が stable になったので、typescript-eslint と検出差を突き合わせた

#### 概要

2026-07-22 に oxlint の type-aware linting が stable 化。`oxlint-tsgolint@7`（tsgolint v7.0.2000 / TypeScript 7.0.2 追従）で typescript-eslint の型認識ルール61本中59本をカバーし、`typeCheck: true` を足すと lint と型検査が同じ TS program を共有する。TypeScript 7.0 は programmatic API 未提供で typescript-eslint が動かないため、TS7 環境での型認識 lint の現実解になりうる。

#### なぜ今よさそうか

- stable 化がちょうど1か月前
- TS 7.0 GA（7/8）で typescript-eslint が動かない問題と直結していて、読者の切実さが高い
- 「61本中59本」「12〜18倍」という公称値を、自分の手元で突き合わせられる

#### 新人が検証しやすい理由

既存の小さな TS プロジェクトに `oxlint` + `oxlint-tsgolint@7` を入れて `--type-aware` を付けるだけ。比較対象の typescript-eslint も TS 6 側に残せば同じコードで両方回せる。

#### 想定読者

ESLint しか使ったことがない新人。TS7 に上げたい/上げたが lint が止まった人。

#### タイトル案

1. TypeScript 7 で typescript-eslint が動かないので、oxlint の type-aware lint（stable）に頼ってみた
2. oxlint の型認識 lint を stable で試して、typescript-eslint との検出差を数えた
3. `oxlint --type-aware` と `tsc` を1回にまとめられるか試した（`typeCheck` オプション）

#### 検証でやること

- 型エラーを含む小さな TS プロジェクトを用意（`no-floating-promises` などに引っかかるコードを仕込む）
- typescript-eslint（TS6 環境）と `oxlint --type-aware`（tsgolint v7）の検出結果を1件ずつ突き合わせる
- `typeCheck: true` を有効にして tsc 診断が混ざる挙動を確認
- 実行時間を計測して公称の12〜18倍と比べる
- 未実装の2ルールが何で、実務でどう困るかを確認

#### 検証手順

1. 検出対象を仕込んだ最小プロジェクトを作成
2. `npm i -D oxlint oxlint-tsgolint@7` と typescript-eslint 側の環境を用意
3. 両者を実行し、検出件数・ルール名・メッセージを表にする
4. `typeAware` / `typeCheck` の組み合わせで出力差を記録
5. `time` で複数回計測して中央値を取る
