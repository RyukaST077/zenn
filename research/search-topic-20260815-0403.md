## 上位候補の詳細

### 1. Agent Plugins 1.0.0 の仕様どおりにプラグインを作り、複数クライアントで読めるか試す

#### 概要

2026-08-06 に Amazon / Microsoft / OpenAI / Vercel / Cursor が発表し、同日 Google がコアメンテナに加わったベンダー中立の仕様 **Agent Plugins 1.0.0** に沿って、最小プラグイン（plugin.json ＋ skills/ ＋ mcp.json）を自作する。そのうえで、公開されている JSON Schema で検証し、手元の Claude Code に読み込ませて「本当にそのまま持ち回れるのか」を確かめる。

#### なぜ今よさそうか

- 発表から約1週間の超一次ネタで、日本語の検証記事がまだ見当たらない
- 仕様が極小（`{"$schema": ..., "name": ...}` だけで最小構成が成立）なので、新人でも仕様書を最後まで読み切れる
- 一方で **Claude Code は `.claude-plugin/plugin.json`、Agent Plugins 1.0.0 はルート直下の `plugin.json`** と配置が違う。この「標準なのに読めない」ズレがそのまま記事の山場になる

#### 新人が検証しやすい理由

作るものはテキストファイルだけ。ビルドもデプロイも課金も不要で、JSON Schema による検証はローカルで完結する。

#### 想定読者

Claude Code / VS Code / Cursor のいずれかを使っていて、設定やスキルを他のエージェントに持ち回りたいと思ったことがある新人〜実務2年目。

#### タイトル案

1. Agent Plugins 1.0.0 の仕様どおりにプラグインを作って、Claude Codeに読ませたら配置が違った
2. 6社が決めた「エージェントプラグイン標準」を新人が最小構成で作ってみた
3. plugin.json はどこに置くのが正解か — Agent Plugins 1.0.0 とクライアント実装のズレを確かめた

#### 検証でやること

- Agent Plugins 1.0.0 の仕様と JSON Schema を読み、必須フィールドを特定する
- 仕様準拠の最小プラグイン（skills/hello/SKILL.md ＋ plugin.json）を作る
- `plugin.schema.json` でマニフェストをバリデーションする（ajv 等をローカル実行）
- MCPサーバーを1つ含む版（mcp.json）に拡張し、こちらもスキーマ検証する
- 同じプラグインを Claude Code の期待するレイアウト（`.claude-plugin/plugin.json`）にも置き、読み込み結果を比較する
- スキーマにわざと違反させ（name欠落、skills を .claude-plugin 配下に配置など）、エラーメッセージを記録する

#### 検証手順

1. `github.com/agentplugins/agent-plugins-spec` の README と schemas を取得して読む
2. `hello-plugin/plugin.json` と `hello-plugin/skills/hello/SKILL.md` を作成
3. `npx ajv-cli validate -s plugin.schema.json -d plugin.json` で検証、結果を記録
4. `mcp.json` を追加して MCP サーバー（stdio・ローカル）を1つ登録し、再度検証
5. `claude plugin`（または `~/.claude/plugins/` への配置）で読み込みを試し、成功/失敗を記録
6. `.claude-plugin/plugin.json` 形式に置き直して再試行し、差分をスクリーンショットとログで残す
7. 失敗パターン（name欠落・skills配置ミス）のエラー全文を収集

#### 記事構成案

1. はじめに（8月に6社が出した標準の話）
2. なぜこの仕様を試すのか（設定の持ち回り問題）
3. 事前に調べたこと（仕様の最小構成と JSON Schema）
4. 環境構築（ファイルを置くだけ）
5. 実際に作った最小プラグイン
6. スキーマ検証で分かったこと
7. 詰まった点（クライアント実装との配置のズレ／エラーメッセージ）
8. 「標準」と「クライアント独自形式」の現在地
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

「発表されました」というニュース紹介ではなく、**仕様準拠で作ったものが実クライアントで読めるかどうかを実際に確かめた**点。ズレが出ればそれ自体が最大の価値になり、読めれば「持ち回れた」実証になる。どちらに転んでも記事が成立する。

### 2. TypeScript 7.0 GA を npm alias で 6 と併用し、前回詰まった bin 衝突が解消したか確かめる

#### 概要

2026年8月に GA した TypeScript 7.0（Goネイティブコンパイラ）を、公式推奨の npm alias 構成（`"typescript": "npm:@typescript/typescript6@^6.0.2"` ＋ `"@typescript/native": "npm:typescript@^7.0.2"`）で TypeScript 6 と併用する。過去記事でプレビュー版の `tsc` bin 衝突により検証が止まった案件の**続報**として、GA版で公式手順が用意された今どうなるかを確かめる。

#### なぜ今よさそうか

- GA 直後（2026年8月）で情報が新しく、移行手順を探している読者が多い
- 7.0 には**プログラマティックAPIが無い**（7.1予定）ため、typescript-eslint / ts-morph / Vue・Astro が動かない。この制約に実際にぶつかる記事は価値が高い
- 筆者が前回まさに bin 衝突で止まっており、**「止まった原因に公式回答が出たので再挑戦する」**という自然な物語になる

#### 新人が検証しやすい理由

やることは package.json の devDependencies を書いて `npm install`、`tsc` / `tsc6` を叩くだけ。小さなサンプルプロジェクトで完結する。

#### 想定読者

TypeScript を業務で使っていて、7 への移行を「そろそろ見ておきたい」と思っている新人〜2年目。

#### タイトル案

1. tscのbin衝突で止まったTypeScript 7検証を、GA版のnpm aliasで再挑戦した
2. TypeScript 7.0 と 6.0 を npm alias で併用して、typescript-eslint が動くところまで確かめた
3. TypeScript 7.0 が速いのは分かった。では ESLint はどうなるのか

#### 検証でやること

- 小さな TS プロジェクトを用意し、TS 6 単体で `tsc` とビルド時間を測る
- 公式推奨の npm alias 構成に切り替え、`tsc`（7）と `tsc6`（6）が衝突せず共存するか確認
- 同一コードで 7 と 6 の型チェック時間を比較（`--singleThreaded` あり/なしも）
- typescript-eslint を 6 側の API で動かし、7 のみの構成では何が起きるか確かめる
- TS 6 で非推奨だった設定（`target: es5`、`baseUrl`、node10解決）が 7 でハードエラーになることを実際に踏む
- `--declaration` emit や `--build` モードの現状を試し、未対応なら出力を記録する

#### 検証手順

1. TS 6 でビルドが通る最小プロジェクト（数十ファイル程度）を作り、`tsc` の所要時間を計測
2. package.json を npm alias 構成に書き換え `npm install`
3. `npx tsc --version` / `npx tsc6 --version` で両方が引けるか確認（前回の衝突箇所）
4. `tsc` で型チェックし、時間と差分を記録
5. `--checkers` / `--builders` / `--singleThreaded` を変えて再計測
6. typescript-eslint を実行、成功/失敗ログを保存
7. 非推奨設定を tsconfig に入れてエラー全文を収集

#### 記事構成案

1. はじめに（前回止まったところの振り返り）
2. なぜ今もう一度試すのか（GAと公式手順）
3. 事前に調べたこと（tsc6 と npm alias、APIは7.1待ち）
4. 環境構築
5. 実際に測った型チェック時間
6. 詰まった点（ESLint / 非推奨設定のハードエラー / declaration emit）
7. 触ってみて分かったこと
8. 前回の検証との差分
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

移行ガイドの要約ではなく、**過去に自分が詰まった具体的な失敗（bin衝突）が公式手順で解けるかを追試する**構成。連載的な続報になり、単発の紹介記事と差がつく。

#### 参考リンク

- https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
- https://www.infoq.com/news/2026/08/typescript-7-released/
- https://nx.dev/docs/technologies/typescript/guides/typescript-7
- https://github.com/microsoft/typescript-go/issues/4368

#### 注意点

- 過去記事 `typescript7-tsc-bin-collision-log` と **必ず差分を明示する**（プレビュー版 → GA版、手順なし → 公式npm alias手順）
- 速度比較は環境依存。マシンスペックとキャッシュ状態を明記し、公式の「8〜12倍」を鵜呑みにして断定しない
- yarn では `@typescript/typescript6` のインストールが失敗する既知issueがある。npm で検証する

### 3. vlt 1.0 の `:malware` / `:cve` セレクタを npm audit と書き比べる

#### 概要

npm の作者陣が作った**セキュリティ優先のnpmドロップイン代替** vlt が 2026-08-06 に 1.0 GA。`vlt query ':malware'` のような CSS ライクなセレクタで依存グラフを検索できる。既存プロジェクトに対して `npm audit` と `vlt query` を同じ依存ツリーに当て、何が見えて何が見えないかを比べる。

#### なぜ今よさそうか

- 1.0 GA 直後で日本語記事がほぼ無い
- 筆者は npm の `allowScripts`、pnpm の `minimumReleaseAge` を既に記事化しており、**「サプライチェーン対策シリーズの3本目」**として自然に繋がる
- `:malware` `:cve` `:eval` `:fs` `:license` `:unmaintained` など、セレクタ名がそのまま記事の見出しになる

#### 新人が検証しやすい理由

curl でCLIを入れて、既存プロジェクトでクエリを打つだけ。認証もアカウントも不要（公開レジストリ利用）。

#### 想定読者

npm audit は打ったことがあるが、それ以上のサプライチェーン対策は知らない新人。

#### タイトル案

1. npm audit しか知らない新人が vlt 1.0 の `:malware` セレクタを試してみた
2. vlt 1.0 の依存グラフクエリで、npm audit が教えてくれないものを探した
3. `vlt query ':eval'` で自分のプロジェクトの依存を覗いてみた

#### 検証でやること

- vlt CLI を導入し、既存プロジェクトで `vlt install` の所要時間を npm と比較（公称最大38%高速）
- `npm audit` の結果を記録
- `vlt query ':malware'` `':cve'` `':vuln'` `':unmaintained'` `':eval'` `':fs'` `':license(...)'` を順に実行し出力を比較
- 意図的に古い/脆弱なバージョンを1つ入れて、両者の検出差を見る
- lockfile の扱い（npm の package-lock.json と共存できるか）を確認

#### 検証手順

1. `curl -fsSL https://install.vlt.sh | bash` → `vlt setup` → `vlt --version`
2. 検証用プロジェクトを2つ用意（クリーン版／古い依存を混ぜた版）
3. npm で clean install、時間を記録。キャッシュを消して vlt でも同様に計測
4. `npm audit --json` の出力を保存
5. セキュリティセレクタを順に `vlt query` で実行し、出力を保存
6. 両者の検出項目を表にして突き合わせる
7. lockfile の差分と互換性を確認

#### 記事構成案

1. はじめに
2. なぜ vlt を試すのか（npm audit の限界）
3. 事前に調べたこと（vlt 1.0 とセレクタ）
4. 環境構築（curl導入で詰まった点）
5. install 速度の実測
6. セレクタを順に打ってみた
7. npm audit との検出差
8. 詰まった点
9. どんなプロジェクトに向いていそうか
10. まとめ

#### 差別化ポイント

「新しいパッケージマネージャが出ました」ではなく、**既に使っている `npm audit` との具体的な検出差分**を表で出す点。過去2本（npm allowScripts / pnpm minimumReleaseAge）と並べてシリーズ化できる。

#### 参考リンク

- https://www.vlt.io/blog/1-0
- https://socket.dev/blog/vlt-debuts-new-javascript-package-manager-and-serverless-registry
- https://www.publickey1.jp/

#### 注意点

- `curl | bash` でのインストールになるため、記事では**スクリプトの中身を確認したことを明記**し、読者にも注意を促す
- ホスティングレジストリ（vsr）は商用でアカウントが必要。**CLIと公開レジストリの範囲に限定する**と冒頭で宣言する
- 脆弱性データはフィード取得時点で変わる。検証日時を必ず記録する

### 理由

- **トレンド性**: 2026-08-06 発表、Publickey が 8/10 に報じたばかり。Amazon / Microsoft / OpenAI / Vercel / Cursor / Google という顔ぶれで注目度が高い
- **新人でも検証できる**: 成果物はテキストファイル数枚。仕様が極小で、最小構成が `{"$schema": ..., "name": ...}` だけで成立する
- **Zenn読者に刺さる**: Claude Code / Cursor / VS Code のプラグインを書いている読者が多く、「その設定は他のエージェントでも使えるのか？」は共通の関心
- **半日〜1日で検証できる**: ファイル作成 → スキーマ検証 → 読み込み確認 → 失敗パターン収集、で1日以内に収まる
- **完成イメージ**: 「標準どおりに作った → スキーマ検証は通った → でもクライアントに読ませたら配置が違って読めなかった（あるいは読めた）」という、結論がはっきりした検証ログ
- **どちらに転んでも記事になる**: 読めれば「持ち回れる実証」、読めなければ「標準と実装のズレの記録」。失敗が価値になる構造
