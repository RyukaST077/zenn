## 上位候補の詳細

### 1. TS6のプロジェクトをTS7 GAに上げ、tsconfig既定値の変更で出たエラーを潰した記録

#### 概要

小さなTypeScriptプロジェクト（Express風APIか、型定義を含むユーティリティ群）を TypeScript 6 で作り、`typescript@7` に上げてビルドが通るまでを記録する。速度も測るが、主役は **tsconfig の既定値変更で何が壊れるか**。

#### なぜ今よさそうか

- 2026-07-08 に GA。国内外で7月〜8月の最大トピック
- 記事の多くが「10倍速い」の紹介止まり。実務の山場は `strict` 既定true / `types` 既定 `[]` / `rootDir` 既定 `./` / `baseUrl`・`target: es5`・`downlevelIteration` の廃止という設定側の破壊的変更
- programmatic API が 7.1 待ちで、Vue / Svelte / Astro / Angular 系はまだ載せられない、という「今やるべきか」の判断材料が出せる

#### 新人が検証しやすい理由

`npm i -D typescript@7` と `npx tsc --noEmit` の往復だけで進む。エラーメッセージが具体的なので、1件ずつ直す過程がそのまま記事になる。

#### 想定読者

TypeScriptを日常的に書いている新人〜2年目。「7に上げていいのか、何が壊れるのか」を知りたい人。

#### タイトル案

1. TypeScript 7に上げたら、コードではなくtsconfigが先に壊れた
2. 新人がTypeScript 6→7 GA移行を最小プロジェクトでやってみた（strict既定true・types既定[]の話）
3. TypeScript 7の「8〜12倍」を小さなプロジェクトで測ったら何倍だったか

#### 検証でやること

- TS6 で通る小さなプロジェクトを用意（`baseUrl` によるパスエイリアス、`strict: false`、`target: es5` をあえて含める）
- `typescript@7` に上げ、`tsc --noEmit` のエラーを全文記録
- 既定値変更ごとに「何を書き足したら直ったか」を対応表にする
- TS6 と TS7 の型チェック時間を同じコードで3回ずつ計測
- `@typescript/typescript6` を併用して6と7を並べられるか確認（過去記事のbin衝突が解決しているか）

#### 検証手順

1. `npm i -D typescript@6` で最小プロジェクトを作り、`tsc --noEmit` が通る状態を作る
2. 計測スクリプトで TS6 の型チェック時間を3回測る
3. `npm i -D typescript@7` に上げ、`tsc --noEmit` の出力をそのまま保存する
4. エラーを1件ずつ、tsconfig 側の対処（`rootDir` 明示、`types` 明示、`baseUrl` → `paths` 単独、`target` 引き上げ）で潰す
5. 型エラー（`strict` 既定true由来）はコード側で直し、件数を数える
6. TS7 の型チェック時間を3回測り、TS6 と比較表にする
7. `@typescript/typescript6` を追加インストールし、6と7を切り替えられるか確認する

#### 記事構成案

1. はじめに
2. なぜTypeScript 7を試すのか（GAと公称8〜12倍）
3. 事前に調べたこと（変わった既定値の一覧）
4. 検証プロジェクトの構成
5. 上げた直後のエラー全文
6. 設定エラーを1件ずつ直す
7. strict既定trueで増えた型エラー
8. 型チェック時間を測った結果
9. TS6と併存できるか
10. どんなプロジェクトなら今上げてよさそうか
11. まとめ

#### 差別化ポイント

解説記事が多い中で、**あえて古い書き方（baseUrl / target es5 / strict false）を含めたプロジェクトを壊しにいく**。エラー全文と対処の1対1対応表を出す。過去記事 `typescript7-tsc-bin-collision-log`（ベータ時にbin衝突で止まった）の続きとして、GA＋公式互換パッケージで解決したかを書けるのも自分だけの文脈。

#### 参考リンク

- https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
- https://gihyo.jp/article/2026/07/typescript-7-0
- https://www.infoq.com/news/2026/08/typescript-7-released/
- https://techplay.jp/column/2113

#### 注意点

- 「10倍速い」を断定しない。小さなプロジェクトでは差が出にくいことも含めて書く
- 計測は同一マシン・同一コード・複数回。1回計測で結論を出さない
- 過去記事2本（TS6の非推奨tsconfig / TS7ベータのbin衝突）との違いを冒頭で明示する

### 2. pnpm 11 で「新しすぎるパッケージ」がinstallできない — minimumReleaseAge 既定24hを踏む

#### 概要

pnpm 11 が既定にした `minimumReleaseAge: 24h`（公開から24時間経っていないバージョンを入れない）と `blockExoticSubdeps: true` を、実際に踏んで挙動とエラーメッセージ、回避方法を記録する。

#### なぜ今よさそうか

- 2026-04-28 の pnpm 11、2026年後半の npm 12（install scripts 既定無効）と、サプライチェーン既定強化が今年の共通テーマ
- 「昨日リリースされたバージョンが入らない」は CI が落ちて初めて気づく類の変更で、事前に知っている価値が大きい
- ストアの SQLite 化で `pnpm install` のホットキャッシュ挙動も変わっている

#### 新人が検証しやすい理由

`corepack` か公式インストーラで pnpm 11 を入れ、公開直後のバージョンを持つパッケージを指定して `pnpm add` するだけ。設定を `.npmrc` で戻す/緩める操作も1行。

#### 想定読者

pnpm を使っている新人〜2年目。CIで急に install が失敗した経験のある人。

#### タイトル案

1. pnpm 11にしたら「昨日出たバージョン」が入らなくなった話（minimumReleaseAge既定24h）
2. 新人がpnpm 11の新しいセキュリティ既定を全部踏んでみた
3. pnpm 11のminimumReleaseAgeとblockExoticSubdepsを、わざと引っかけて確認する

#### 検証でやること

- pnpm 10 と 11 を用意し、同じ `package.json` で install 結果を比べる
- npm レジストリのAPIで「24時間以内に公開されたバージョン」を探し、それを指定して `pnpm add` する
- エラーメッセージ全文と終了コードを記録する
- `.npmrc` の `minimum-release-age` を 0 にして通ることを確認する
- `blockExoticSubdeps` に引っかかる依存指定（git / 独自プロトコル）をローカルfixtureで再現する
- SQLiteストアの位置と、キャッシュあり/なしの install 時間を計測する

#### 検証手順

1. Docker か `corepack` で pnpm 10 / 11 を切り替えられる環境を作る
2. 公開直後のバージョンを registry API（認証不要）で特定する
3. pnpm 11 で `pnpm add <pkg>@<新バージョン>` を実行し、失敗ログを保存する
4. pnpm 10 で同じことをして差を確認する
5. `.npmrc` で `minimum-release-age=0` にして再実行する
6. git 依存を含む fixture を作り `blockExoticSubdeps` の挙動を確認する
7. ストアを消した状態と温めた状態で `pnpm install` を各3回計測する

#### 記事構成案

1. はじめに
2. pnpm 11 で変わった既定値
3. 検証環境
4. 「新しすぎるバージョン」を入れようとした結果
5. エラーメッセージの読み方
6. 設定で緩める方法と、その是非
7. blockExoticSubdeps を踏む
8. SQLiteストアでinstall時間はどうなったか
9. CIで気をつけたいこと
10. まとめ

#### 差別化ポイント

紹介記事は多いが「**実際に弾かれるところまでやったログ**」は少ない。過去記事 `npm12-allowscripts-local-fixture` と同じ「サプライチェーン既定を無害なfixtureで踏む」流儀だが、対象ツールも設定項目も別。

#### 参考リンク

- https://pnpm.io/blog/releases/11.0
- https://www.infoq.com/news/2026/04/pnpm-11-rc-release/
- https://thehackernews.com/2026/07/npm-12-disables-install-scripts-by.html

#### 注意点

- 実在パッケージを「危険な例」として扱わない。あくまで公開日時だけを条件に選ぶ
- 設定を緩める方法を書くときは、緩めることのリスクも併記する
- pnpm 11 は Node 22+ / pure ESM。Nodeバージョンの前提を明記する

### 3. Browserslistの `baseline 2026` と html-eslint `use-baseline` で新しいCSSを自動で弾かせてみた

#### 概要

`.browserslistrc` に `baseline widely available` / `baseline 2026` を書き、html-eslint の `use-baseline` ルールと合わせて、「まだ使ってはいけないCSS/HTML機能」がlintで落ちる状態を作る。

#### なぜ今よさそうか

- Baseline が「読み物」から「Browserslist本体のクエリ」「lintルール」へ降りてきた段階
- 国内でもサイボウズなどが運用に組み込んだ事例を公開しており、実務テーマとして温度がある
- 過去記事で CSS Anchor Positioning / Gap Decorations を扱っており、「使える判断をどうするか」への自然な接続になる

#### 新人が検証しやすい理由

npm パッケージを2〜3個入れて設定ファイルを書き、`npx eslint` を叩くだけ。ブラウザ確認が必要な部分は Playwright でスクリーンショットを撮れる。

#### 想定読者

フロントの新人。「この新機能、業務で使っていいのか」の決め方を知りたい人。

#### タイトル案

1. 「このCSS使っていい？」をlintに判断させる — Baseline × Browserslist を新人が試した
2. baseline widely available と baseline 2026 で、同じCSSがどう判定されるか比べてみた
3. Baselineをツール設定に落とし込むまでにやったこと

#### 検証でやること

- `.browserslistrc` を `baseline widely available` / `baseline newly available` / `baseline 2026` で切り替え、`npx browserslist` の対象ブラウザ差分を出す
- html-eslint `use-baseline` を有効にし、新しめの機能を書いたHTML/CSSがどう報告されるか確認する
- 過去記事で扱った Anchor Positioning などが各クエリでどう判定されるか表にする
- Playwright で実際の描画も確認し、lintの判定と実挙動を突き合わせる

#### 検証手順

1. 最小のHTML/CSSプロジェクトを作る
2. browserslist / html-eslint を入れる
3. 3種類のクエリで `npx browserslist` の出力を保存し差分を取る
4. 新しめの機能を含むCSSを書き、lintの結果を記録する
5. しきい値を変えるとどの機能が通る/落ちるかを表にする
6. Playwright で描画をスクリーンショットし、判定と実際を比較する

#### 記事構成案

1. はじめに
2. Baseline とは（Newly / Widely / 年次）
3. Browserslist のクエリに書いてみる
4. クエリごとの対象ブラウザ差分
5. lint で弾かせる
6. 弾かれた機能を実際に描画してみる
7. どのしきい値を選ぶか
8. まとめ

#### 差別化ポイント

Baselineの概念解説は多いが、**3種類のクエリを切り替えて出力差分を実測し、lintの判定と実描画を突き合わせる**記事は少ない。

## 最初に試すべき1本

### 推奨テーマ

**TS6のプロジェクトをTypeScript 7 GAに上げ、tsconfig既定値の変更で出たエラーを1件ずつ潰した記録**

### 理由

- トレンド性: 2026-07-08 GA。国内外の技術メディアが7〜8月にわたって扱い続けている最大トピック
- 新人でも検証できる: 操作は `npm i -D typescript@7` と `tsc --noEmit` の往復のみ。エラーが具体的で、直し方が調べやすい
- Zenn読者に刺さる: 「速い」の紹介は飽和している一方、`strict` 既定true・`types` 既定 `[]`・`rootDir` 既定 `./`・`baseUrl` 廃止という**設定側の破壊的変更**を実際に踏んだログは需要がある
- 半日〜1日で終わる: 最小プロジェクトの作成 → 移行 → 計測 → 併存確認で数時間
- 自分の文脈がある: 過去記事 `typescript7-tsc-bin-collision-log` はベータ時にbin衝突で検証が止まっている。GA＋`@typescript/typescript6` でその続きを書ける
- 完成イメージ: 「エラー全文 → 対処 → 直った」の対応表と、TS6/TS7 の型チェック時間比較表を中心にした移行ログ

### 最小検証プラン

1. `strict: false` / `baseUrl` / `target: es5` を含む TS6 の最小プロジェクトを作り、`tsc --noEmit` が通る状態にする
2. TS6 で型チェック時間を3回計測して記録する
3. `typescript@7` に上げ、エラー出力を全文保存する
4. tsconfig 側のエラー → コード側の型エラーの順に潰し、それぞれ件数と対処を対応表にする
5. TS7 で型チェック時間を3回計測し、TS6 と比較する
6. `@typescript/typescript6` を入れて6/7の併存とbin衝突の有無を確認する
