## 上位候補の詳細

### 1. Vitest 5 RC に上げて、4.1のテストが落ちる箇所を踏む

#### 概要

`vitest@4.1.10` で全部グリーンになる小さなテストfixtureを用意し、`vitest@rc`（5.0.0-rc.1）に上げて
**何が落ちるか / 落ちないか**を1項目ずつ確認する。公式移行ガイドが挙げる破壊的変更のうち、
「新人が普通に書いたテストが影響を受けるもの」に絞って踏む。

#### なぜ今よさそうか

- **2026-08-11 にRC到達**したばかり。安定版はまだ出ておらず、日本語記事は未確認
- 公式移行ガイドが破壊的変更を20項目以上、**理由つきで明文化済み** → 検証設計がそのまま作れる
- 「上げたら落ちた」は結論がはっきりし、落ちなくても「落ちなかった」が記事になる
- Vitest は日本語読者が非常に多く、5系は遅かれ早かれ全員が通る道

#### 新人が検証しやすい理由

- `npm i -D vitest@rc` で切り替えるだけ。ビルドも外部サービスも不要
- 検証対象が「テスト1本ずつ」なので、1項目=数行のfixtureで済む
- 失敗メッセージがそのまま記事の一次情報になる

#### 想定読者

Vitest を業務や個人開発で使っていて、メジャーアップデートの影響を先に知りたい新人〜2年目。

#### タイトル案

1. Vitest 5 RC に上げたら、4.1で通っていたテストが3種類落ちた
2. Vitest 5 の「awaitし忘れた assertion は失敗させる」を、実際に落として確かめた
3. Vitest 4.1 → 5 RC で新人が踏みそうな破壊的変更だけを1つずつ試した

#### 検証でやること

- 4.1 で全部グリーンになる fixture（非同期assertion / mock / `-t`フィルタ / 成果物出力）を作る
- `vitest@rc` に上げて、同じテストを再実行して差分を取る
- 落ちた項目ごとに「エラー全文」「原因」「移行ガイドの該当記述」「直し方」を対応づける
- 落ちなかった項目も「効かなかった/再現しなかった」として記録する

#### 検証手順

1. `npm i -D vitest@4.1.10` で fixture を作り、全部グリーンを確認・ログ保存
2. 検証項目を用意する:
   - `expect(promise).resolves.toBe(1)` を **await せずに** 書いたテスト（5では失敗するはず）
   - `beforeAll` でモックを呼び、`test` 内で `mock.calls.length` を検証（`clearMocks` 既定true で履歴が消えるはず）
   - `vitest -t "math adds"`（4.1）と `vitest -t "math > adds"`（5）でフィルタ結果を比較
   - `vi.mock` を関数の中に書いたテスト（5ではトップレベル必須でエラーになるはず）
   - `test.sequential`（5で削除）/ `toThrow('')`（5では全メッセージに一致）
   - JSON reporter の出力先が `.vitest/` に移るかをファイルパスで確認
3. `npm i -D vitest@rc` に上げ、`npx vitest --version` と Vite / Node のバージョンを記録（**Vite>=6.4, Node>=22.12 が必須**なので、ここで先に止まる可能性あり）
4. 同じコマンドを流し、失敗/成功をエラー全文つきで記録
5. 落ちた項目を移行ガイドどおりに直して再度グリーンにする
6. 「4.1 → 5 で自分のテストを直すときのチェックリスト」に落とす

#### 記事構成案

1. はじめに（Vitest 5 が RC になった）
2. なぜ RC のうちに踏んでおくのか

8. 4.1 と比べて感じたこと
9. どんな人が先に確認しておくべきか
10. まとめ（移行チェックリスト）

- 「新機能紹介」ではなく **自分のテストが落ちる/落ちない実測**。RCなので日本語の先行記事がない

### 2. vlt 1.0 を入れて `vlt query` で依存グラフを検索する

#### 概要

npm の作者陣が作った新パッケージマネージャ **vlt 1.0**（2026-08-06）をローカルに入れ、
小さなプロジェクトで `vlt install` → `vlt query` を試す。目玉は依存グラフを
**CSSセレクタ風に問い合わせる** クエリ言語（`:malware` `:cve` `:vuln` `:eval` `:host(local)` など60以上）。

#### なぜ今よさそうか

- 1.0 が 2026-08-06。Publickey も報じたが、**実際に触った日本語記事が見当たらない**
- `npm i -g vlt` で入り、公開レジストリを見るだけなら**アカウント不要**
- 「`npm ls` / `npm audit` では答えられない質問に答えられるか」という比較軸が明快

#### 新人が検証しやすい理由

- インストールとコマンド実行だけ。既存の `package.json` をそのまま使える
- クエリの結果は目で見て分かる（該当パッケージが出る/出ない）

#### 想定読者

npm / pnpm しか使ったことがなく、「依存の棚卸し」を手作業でやっている新人。

#### タイトル案

1. npmを作った人たちの新パッケージマネージャ vlt 1.0 を入れて、依存グラフをCSSセレクタで検索してみた
2. `npm ls` で調べていた依存の棚卸しを、vlt の `vlt query` に置き換えてみた
3. vlt 1.0 を触って分かった、npm と「同じところ・違うところ」

#### 検証でやること

- `npm i -g vlt` → `vlt --version` を記録し、npm 経由で入るか（install.vlt.sh を使わずに済むか）を確認
- 既存の小さなプロジェクトで `vlt install` を実行し、`node_modules` と lockfile の形を npm と比べる
- `vlt query ':malware'` `':vuln'` `':eval'` `':host(local)'` を実行して出力を記録
- 同じ問いを `npm ls` / `npm audit` で立てて、答えられる/答えられないを対照表にする
- クリーンインストール時間を npm と単純比較（公称 最大38%高速）

#### 検証手順

1. `npm i -g vlt` でインストールし、バージョンとサブコマンド一覧（`init`/`install`/`query`/`run`/`exec`/`pack`/`publish`/`view` など）を記録
2. 依存が数個の fixture プロジェクトを作る
3. `npm ci` と `vlt install` をそれぞれクリーン状態から実行し、所要時間と生成物を記録
4. `vlt query` の各セレクタを実行し、出力（と空だった場合の空も）を保存
5. `npm audit` / `npm ls` と対照表を作る
6. 詰まった点（未実装のサブコマンド、npmと違う挙動、アカウントを求められた箇所）をまとめる

#### 記事構成案

1. はじめに（vlt 1.0 が出た）
2. なぜ試すのか（npm/pnpm で困っていること）
3. 事前に調べたこと（vlt が何を売りにしているか）
4. 環境構築（`npm i -g vlt`）
5. 実際に試したこと（install / query）
6. 詰まった点
7. `npm ls` / `npm audit` と比べて分かったこと
8. どんな人に向いていそうか
9. まとめ

#### 差別化ポイント

- 国内で「触ってみた」記事がまだ無い。かつ**既出のパッケージ管理記事（npm12 / pnpm11 / pnpm12）とは対象ツールが違う**
- 「速い」より「これまで答えられなかった質問に答えられるか」を軸にする

#### 参考リンク

- https://www.vlt.io/blog/1-0
- https://www.npmjs.com/package/vlt
- https://www.infoq.com/news/2025/01/vlt-js-package-manager

#### 注意点

- 公開レジストリの読み取り・インストールに留める（**publish やアカウント作成はしない**）
- 「npmより速い」は公称値。自分の環境の実測値だけを書き、環境（OS/Node/回線）を明記する
- 1.0 直後なので未実装・不安定な部分は「そう見えた」と書く

### 3. 「`--ignore-scripts` を付けたから安全」を無害なfixtureで疑う

#### 概要

2026年8月に公開された PackageGate で、npm / pnpm / vlt / Bun の
「インストール時スクリプトを無効化する仕組み」に回避経路があることが報告された。
これを**攻撃再現ではなく防御確認**として扱い、
「無害なマーカーファイルを書くだけの lifecycle script」を持つローカルfixtureを作って、
自分の環境のパッケージマネージャが**修正済みバージョンかどうか**をコマンドとバージョンで確かめる。

#### なぜ今よさそうか

- 2026年8月公開で、pnpm は CVE-2025-69263 / 69264 として修正済み、vlt・Bun(1.3.5) も修正済み、**npm だけ "Works as expected" で未修正**という状況が明確
- 「`--ignore-scripts` を付ければ安全」は新人が持ちやすい思い込みで、揺さぶる価値がある

#### 新人が検証しやすい理由

- fixture は「`postinstall` でファイルを1つ書くだけ」のローカルパッケージ。外部に何も送らない
- 判定は「マーカーファイルができたか / できなかったか」だけで、極めて分かりやすい

#### 想定読者

`--ignore-scripts` や `ignore-scripts=true` を設定して安心している新人〜2年目。

#### タイトル案

1. `--ignore-scripts` を付けたのにスクリプトが動く場合がある、と聞いたので無害なfixtureで確かめた
2. 手元の npm / pnpm / Bun が PackageGate 修正版かどうか、マーカーファイル1個で確認した
3. 「インストール時スクリプトは切ってあるから安全」を新人が疑ってみた記録

#### 検証でやること

- `postinstall` で `MARKER.txt` を書くだけのローカルパッケージを作る（ネットワークアクセスなし）
- `npm install --ignore-scripts` / `pnpm install` / `bun install` の各条件でマーカーの有無を確認
- 各パッケージマネージャのバージョンを記録し、**修正が入ったバージョンと突き合わせる**
- 既出の `npm12-allowscripts-local-fixture` と重ならないよう、**「PMをまたいだ横断確認」と「修正版判定」**に軸を置く

#### 検証手順

1. `npm -v` / `pnpm -v` / `bun -v` を記録し、PackageGate の修正版バージョン（pnpm: CVE-2025-69263/69264 修正版、Bun: 1.3.5 以降）と照合
2. `postinstall` でマーカーファイルを書くだけのローカルパッケージ fixture を作る
3. ローカルパスの依存として各PMでインストールし、`--ignore-scripts`（および各PMの相当設定）ありなしでマーカーの有無を記録
4. 結果を「PM × 設定 × マーカー生成」の表にする
5. 「自分の環境で確認できたこと／確認できなかったこと」を分けて書く

#### 記事構成案

1. はじめに（PackageGate という報告があった）
2. なぜ自分で確かめるのか
3. 事前に調べたこと（何が問題とされたか、どのPMが修正済みか）
4. 無害なfixtureの作り方（ここを丁寧に）
5. 各PMでの実行結果
6. 詰まった点
7. 分かったこと（`--ignore-scripts` は何を守り、何を守らないか）
8. 今日からできる対策
9. まとめ

#### 差別化ポイント

- 既出の `npm12-allowscripts-local-fixture` は npm 単体・allowScripts の話。こちらは **PM横断＋修正版判定**という別の切り口
- 攻撃再現ではなく「自分の環境が安全側にいるかの確認手順」として書く

#### 参考リンク

- https://www.koi.ai/blog/packagegate-6-zero-days-in-js-package-managers-but-npm-wont-act
- CVE-2025-69263 / CVE-2025-69264
- https://docs.npmjs.com/cli/v12/using-npm/config#ignore-scripts

#### 注意点

- **攻撃の再現手順は書かない**。fixture は「ローカルにテキストファイルを1つ作るだけ」に限定し、外部通信・パストラバーサル・バイナリ上書きは一切扱わない
- 未修正とされる挙動については「報告ではこうされている」と出典を明示し、自分で再現できた範囲だけを事実として書く
- PM のバージョンは必ず全部記録する（結論がバージョン依存のため）

## 最初に試すべき1本

### 推奨テーマ

**Vitest 5 RC に上げて、4.1で通っていたテストが落ちる箇所を1つずつ踏む**

### 理由

- **トレンド性**: `v5.0.0-rc.1` は 2026-08-11 リリース、6日前。安定版はまだ無く、日本語記事も未確認
- **新人でも検証できる**: `npm i -D vitest@rc` に切り替えるだけ。1項目=数行のテストで再現でき、判定は「落ちた/落ちなかった」の二択
- **Zenn読者に刺さる**: Vitest 利用者は日本語圏に非常に多く、メジャー更新の破壊的変更は全員が通る
- **半日〜1日で検証できる**: fixture作成 → 4.1で緑 → RCで再実行 → 差分整理、で1日以内
- **完成イメージ**: 「4.1では全部緑 → 5 RCで N 個落ちた → エラー全文と移行ガイドの該当箇所を対応づけ → 直してまた緑」という、結論がはっきりした移行ログ
- **どちらに転んでも記事になる**: 落ちれば「移行チェックリスト」、落ちなければ「公式が挙げた変更のうち実際に効いたのはこれだけだった」という記事になる

### 最小検証プラン

1. `vitest@4.1.10` で fixture を作り、全テスト緑を確認してログを保存する
