## 上位候補の詳細

### 1. Node 26.7 の `--test-coverage-include-all` を付けたら、カバレッジ率が何%下がったか測ってみた

#### 概要

Node.js 26.7.0（2026-08-05リリース）で `node:test` に `--test-coverage-include-all` が入った。既定では、テスト実行中に一度も `import` / `require` されなかったソースファイルはカバレッジレポートに現れない。つまり「テストが1行も無いファイル」は集計から丸ごと消えていて、表示上のカバレッジ率が実態より高く見える。このフラグを付けると、未ロードのファイルも 0% として計上される。フラグの有無で同じプロジェクトのカバレッジ表がどう変わるかを実測する。

#### なぜ今よさそうか

- リリースから2日（2026-08-05 → 2026-08-07）で、日本語の解説記事がまだほぼ無い。
- 「カバレッジ率が高いのに実はテストされていない」は新人が最初に踏む誤解そのもので、数字で説明できる。
- 公式ドキュメントに既定値（`false`）と挙動が明記されており、検証設計が明確。

#### 新人が検証しやすい理由

Node 26.7 と小さなプロジェクトさえあれば完結する。追加の依存もツールも不要で、比較対象は `node --test --experimental-test-coverage` のフラグ1個の差でしかない。

#### 想定読者

テストを書き始めたが、カバレッジの数字の意味をまだ詰めていない新人〜実務2年目。

#### タイトル案

1. Node 26.7 の `--test-coverage-include-all` を付けたら、カバレッジ率が 92% から 41% になった
2. カバレッジ100%だと思っていたら、そもそも数えられていないファイルがあった話（Node 26.7）
3. `--test-coverage-include-all` を試して、node:test のカバレッジの「見えない分母」を確認した

#### 検証でやること

- Node 26.7.0 を用意し、`node --version` で確認する
- src配下に「テスト有りファイル3本 / テスト無しファイル3本」を持つ小さなプロジェクトを作る
- フラグ無しでカバレッジを取り、レポートに現れるファイル一覧と総合%を記録する
- `--test-coverage-include-all` を付けて同じことをし、差分（追加された行・下がった%）を記録する
- `--test-coverage-include-globs` / `--test-coverage-exclude-globs` と併用したときの絞り込み挙動を確認する
- `run()` API 側の `coverageIncludeAll: true` でも同じ結果になるか確認する

#### 検証手順

1. Node 26.7.0 をインストールし、バージョンを記録する（26.7未満だとフラグが無いので最初の詰まりポイントになりうる）
2. `src/` に計算・文字列整形・日付整形などの小さな関数を6ファイル作り、うち3ファイルだけ `test/` にテストを書く
3. `node --test --experimental-test-coverage` を実行し、出力テーブル全文と総合カバレッジを保存する
4. `node --test --experimental-test-coverage --test-coverage-include-all` を実行し、同様に保存する
5. 2つの出力を並べて差分を作り、「増えた行数」「下がったパーセンテージ」を表にまとめる
6. glob 併用・`run()` API 経由も試し、期待通りに絞れるか / 同値かを確認する

#### 記事構成案

1. はじめに
2. なぜこの機能を試すのか（カバレッジの分母問題）
3. 事前に調べたこと（公式ドキュメントの既定値と挙動）
4. 環境構築（Node 26.7 と最小プロジェクト）
5. フラグ無しのカバレッジ結果
6. `--test-coverage-include-all` を付けた結果
7. 詰まった点
8. glob と併用したときの挙動
9. どんなプロジェクトで効きそうか
10. まとめ

#### 差別化ポイント

リリース直後で日本語情報が無い。かつ「率が下がる」という数字の差分をそのまま見出しにできるので、機能紹介ではなく実測ログとして成立する。

#### 参考リンク

- Node.js v26.7.0 リリースノート: https://nodejs.org/en/blog/release/v26.7.0
- node:test ドキュメント（`--test-coverage-include-all`）: https://nodejs.org/api/test.html

#### 注意点

- カバレッジ機能自体がまだ experimental なので、出力形式が今後変わりうることを明記する。
- 数字は「この検証プロジェクトでの値」であり、一般化しないよう書く。
- 検証プロジェクトのファイル構成を記事に載せないと、下がった%の意味が読者に伝わらない。

### 2. TypeScript 6のプロジェクトを7（tsgo）に上げたら、tsconfigのどこが壊れたか

#### 概要

TypeScript 7.0 が2026-07-08に正式リリースされた。Go実装のネイティブコンパイラで8〜12倍高速になった一方、破壊的変更が多い。`target: es5` と `moduleResolution: node10` の廃止、`baseUrl` の廃止（`paths` へ移行）、`strict: true` 既定、`types` の既定が `[]`（必要な `@types` を明示列挙）、`esModuleInterop` を `false` にできない、など。小さなTS 6プロジェクトを用意して7に上げ、どのエラーがどの順で出るか、tsconfig をどう直したかを記録する。

#### なぜ今よさそうか

- 2026年のTypeScript最大のトピックで、正式リリースから1か月。移行の実測ログの需要が最も高い時期。
- 破壊的変更の一覧は英語記事が中心で、日本語の「実際に踏んで直した」記録はまだ手薄。
- 自分の過去記事は TS6 の tsconfig 非推奨（`typescript6-deprecated-tsconfig-already-error`）と TS7 併用時の bin 衝突（`typescript7-tsc-bin-collision-log`）で、いずれも「移行そのもの」は未達。今回は正式版での移行完遂という切り口で差がつく。

#### 新人が検証しやすい理由

`npm install -D typescript` でバージョンを切り替えるだけ。エラーが出るのが前提の検証なので、失敗自体が記事の中身になる。

#### 想定読者

TSを業務で使い始め、tsconfig をコピペで運用してきた新人〜実務2年目。

#### タイトル案

1. TypeScript 6のプロジェクトを7に上げたら、tsconfigが5箇所で止まった
2. `baseUrl` を消せと言われた — TypeScript 7 移行で新人が踏んだエラー全部
3. TypeScript 7（tsgo）に上げるまでにやったこと・詰まったこと

#### 検証でやること

- TS 6 で通る小さなプロジェクト（`baseUrl` + パスエイリアス、`target: es5`、暗黙の `@types` 依存を含む）を作る
- TS 7 に上げて `tsc` を実行し、出たエラーを全文記録する
- エラーを1つずつ潰し、tsconfig の before / after を並べる
- `tsc` のビルド時間を6と7で計測して比較する
- `ts-morph` など Compiler API 依存パッケージを1つ入れて、実際に壊れることを確認する

#### 検証手順

### 4. pnpm 11 の `minimumReleaseAge` で「昨日出たパッケージ」が入らない様子を再現してみた

#### 概要

pnpm 11.0（2026-04-28）から、サプライチェーン対策の既定が強化された。`minimumReleaseAge` が既定1日になり、公開から24時間経っていないバージョンは依存解決の対象外になる。あわせて `blockExoticSubdeps`（git/tarball 等の特殊プロトコルをブロック）と `strictDepBuilds`（未承認のビルドスクリプトをインストール失敗扱い）も既定ON。さらに設定の置き場が `.npmrc` から `pnpm-workspace.yaml` / `~/.config/pnpm/config.yaml` へ移動し、`package.json` の `pnpm` フィールドは設定として読まれなくなった。この「既定で止まる」挙動を実際に踏んで、エラーメッセージと回避方法を記録する。

#### なぜ今よさそうか

- npm v12 のインストールスクリプト既定無効化と合わせて、2026年は「パッケージマネージャが既定で厳しくなった年」。国内でもCI事故の報告が出ている。
- 「なぜか最新版が入らない」は原因が分かりにくく、記事の実用性が高い。

#### 新人が検証しやすい理由

pnpm を入れて `pnpm add` するだけ。公開レジストリのみで認証不要。失敗が期待される検証なので、詰まること自体が成果物になる。

#### 想定読者

pnpm を使っている新人、CIが急に落ちて原因を探している人。

#### タイトル案

1. pnpm 11 で最新バージョンが入らないのは仕様だった（`minimumReleaseAge` 既定1日）
2. pnpm 10 から 11 に上げたら設定が全部読まれなくなった話
3. pnpm 11 のセキュリティ既定3つを、わざと踏んで確認してみた

#### 検証でやること

- pnpm 10 と 11 を用意し、同じ `package.json` で挙動差を見る
- 公開直後のバージョンを持つパッケージを指定して `minimumReleaseAge` に引っかかる様子を再現し、エラー全文を記録する
- `minimumReleaseAge: 0` で解除できることを確認する
- ビルドスクリプトを持つ依存を入れて `strictDepBuilds` の失敗と `allowBuilds` での承認フローを確認する
- `.npmrc` に書いた設定が11で無視されることを確認し、`pnpm-workspace.yaml` へ移すと効くことを確かめる
- 移行codemod（`pnpx codemod run pnpm-v10-to-v11`）が何を書き換えるか差分を見る

#### 検証手順

1. Node 22以上を確認し、`corepack` などで pnpm 10 と 11 を切り替えられるようにする
2. ビルドスクリプト付き依存を1つ含む小さな `package.json` を作る
3. pnpm 10 でインストールし、成功ログを記録する
4. pnpm 11 に切り替えて同じインストールを実行し、失敗したものを全部記録する
5. `pnpm-workspace.yaml` に `minimumReleaseAge` / `allowBuilds` を書いて、1つずつ解除しながら通す
6. `.npmrc` に同じ設定を書いた場合は効かないことを対照実験として確認する
7. codemod を実行して生成される差分を記録する

#### 記事構成案

1. はじめに
2. pnpm 11 で何が既定変更されたか
3. 検証用プロジェクトの構成
4. pnpm 10 での結果
5. pnpm 11 で止まった3つのポイント
6. 設定ファイルの引っ越し（`.npmrc` → `pnpm-workspace.yaml`）
7. codemod は何を書き換えたか
8. 詰まった点
9. 実務でどう向き合うか
10. まとめ

#### 差別化ポイント

リリースノートの要約ではなく「わざと踏んで、エラー全文と解除手順を残す」形にする。設定ファイル移動は見落としやすく、対照実験の価値が高い。

#### 注意点
