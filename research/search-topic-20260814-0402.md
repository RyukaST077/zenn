## 上位候補の詳細

### 1. Deno 2.9の`Deno.test.each()`と`t.assertSnapshot()`を、node:testと書き比べてみた（28点）

#### 概要

Deno 2.9 で標準搭載されたパラメータ化テスト（`Deno.test.each()`）と組み込みスナップショット（`t.assertSnapshot()`）を、同じ対象コードに対する node:test 版と並べて書き、書き味・失敗時の出力・スナップショット更新フローの違いを記録する。

#### なぜ今よさそうか

- Deno 2.9 は 2026-06-25 リリースで直近3か月以内。日本語の実践記事がまだ少ない
- node:test にはパラメータ化テストの標準APIが無く、「標準だけでどこまで書けるか」の比較として成立する
- スナップショットは `-u` での更新まで含めて挙動が見える＝検証ログにしやすい

#### 新人が検証しやすい理由

`deno upgrade` と `deno test` だけで完結。外部サービス・認証・課金なし。ローカルは deno 2.8.3 のため 2.9 への更新が最初の一手になる（ここで詰まればそれ自体が記事の素材）。

#### 想定読者

テストを書き始めた新人〜2年目。node:test は触ったことがあるが Deno のテストランナーは知らない層。

#### タイトル案

1. `node:testしか知らない新人がDeno 2.9のtest.each()とスナップショットを試してみた`
2. `Deno 2.9のDeno.test.each()とt.assertSnapshot()を、node:testと書き比べてみた`
3. `パラメータ化テストとスナップショットを「標準機能だけ」で書く：Deno 2.9 vs node:test`

#### 検証でやること

- `deno upgrade` で 2.8.3 → 2.9 系へ更新し、バージョンを記録
- 同一の対象関数（例: `add()` とHTML断片を返す `renderHeader()`）を用意
- `Deno.test.each()` の配列ケース／オブジェクトケース、名前補間（`%i` `%s`）を確認
- node:test 側で同等のパラメータ化を `for...of` + `test()` で書き、行数と失敗時出力を比較
- `t.assertSnapshot()` で `__snapshots__/*.snap` が生成されることを確認し、出力を変えて失敗させ、`-u` で更新
- node:test 側は `--test-update-snapshots` 相当の挙動と比較（利用可否も含めて記録）

#### 検証手順

1. `deno --version` を記録 → `deno upgrade` → 再度記録
2. 検証用ディレクトリを作り、対象関数とテストを Deno/Node の両方で用意
3. `deno test` を実行してパス、失敗ケースも作って出力を全文保存
4. スナップショット生成 → 出力変更 → 失敗 → `deno test -u` → 再パス、の順に実行ログを保存
5. node:test 側を Node 26 系（`nvm install 26`）で同じシナリオ実行し、差分を表に整理

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（node:testで毎回forを書いていた）
3. 事前に調べたこと（Deno 2.9のリリースノート）
4. 環境構築（deno upgradeでの版数確認）
5. 実際に試したこと（test.each / assertSnapshot）
6. 詰まった点
7. 触ってみて分かったこと
8. node:testと比べて感じたこと
9. どんな人に向いていそうか
10. まとめ

過去記事の Deno 2.9 系2本は「lockfile seed」「task cache」で、テスト機能には触れていない＝切り口違い。日本語で `Deno.test.each()` の実行ログを載せた記事はほぼ無い。

### 2. TypeScript 7.0 正式版に上げて、`strict`既定ON・`types: []`既定で何が壊れるかを潰した記録（27点）

#### 概要

npm の `typescript@7.0.2`（実測で取得可能を確認済み）を小さな既存プロジェクトに入れ、正式版で既定値が変わった箇所──`strict` 既定ON、`types` 既定 `[]`、`target: es5` 廃止、AMD/UMD/SystemJS削除、`rootDir` 追加の必要──を順に踏み、エラー全文と修正手順を残す。

#### なぜ今よさそうか

- 2026-07-08 に正式リリース、直近1か月強
- 国内記事の多くは **プレビュー版（@typescript/native-preview の `tsgo`）** 前提で、正式版 `tsc` の実測記事がまだ薄い
- 「速さ」ではなく「壊れ方」に寄せることで既存記事と真正面から被らない

#### 新人が検証しやすい理由

`npm i -D typescript@7` と `npx tsc --noEmit` だけ。エラーが出ること自体が成果物になる。

#### 想定読者

TypeScriptを業務で使っていて、7への上げ方を知りたい新人〜2年目。

#### タイトル案

1. `TypeScript 7.0正式版に上げたら、まずtypes既定[]でグローバル型が消えた`
2. `TS6のプロジェクトをTypeScript 7.0に上げて、エラーを1つずつ潰した記録`
3. `tsgoプレビューではなく、正式版のtsc 7.0で移行してみた`

#### 検証でやること

- TS6構成の最小プロジェクト（Node型・テスト型を暗黙参照、`target: es5`、`baseUrl` あり）を用意
- `typescript@7.0.2` に上げて `tsc --noEmit` のエラー全文を採取
- `types: ["node"]` の明示、`target` 変更、`rootDir` 追加、`baseUrl` 代替（paths相対化）を1つずつ適用し、エラーが減る過程を記録
- Programmatic API 不在（7.1待ち）が影響するツール（ts-jest 等）が入っていた場合の挙動も確認

#### 検証手順

1. `npm init` → TS6構成の tsconfig と数ファイルを作成、`tsc --noEmit` が通ることを確認
2. `npm i -D typescript@7` → バージョン記録 → `tsc --noEmit` 実行、出力を全文保存
3. エラーを分類（既定値変更／削除機能／解決系）し、1つずつ修正してログを取る
4. 最終的に通る tsconfig の before / after を差分で提示
5. 余力があれば `--checkers` / `--singleThreaded` の実行時間も測る（候補2と統合）

1. はじめに
2. なぜこの技術を試すのか
3. 事前に調べたこと（公式アナウンスの破壊的変更一覧）
4. 環境構築
5. 実際に試したこと（エラーを1つずつ潰す）
6. 詰まった点
7. 触ってみて分かったこと
8. TS6と比べて感じたこと
9. どんな人に向いていそうか
10. まとめ

過去記事 `typescript7-tsc-bin-collision-log` はプレビュー版で bin 衝突により検証が止まった記録。今回は**正式版・別の壁**なので重複しない（記事内で前回との差を明示する）。`typescript6-deprecated-tsconfig-already-error` の続編としても読める。

### 3. Playwright 1.62の`retryStrategy: 'isolated'`を、わざとフレークするテストで試してみた（27点）

#### 概要

Playwright 1.62（2026-07-24）で入った `testConfig.retryStrategy: 'isolated'`（リトライを末尾でまとめて直列実行）を、確率的に落ちるテストを自作して既定のリトライと比較する。

#### なぜ今よさそうか

- 1.62 は3週間前のリリースで、日本語の実践記事がまだ少ない
- 「フレークテストが並列実行の巻き添えで落ちているのか」を切り分けられる機能で、実用価値が高い

#### 新人が検証しやすい理由

localhost の静的ページ＋わざと不安定なテストで完結。外部サイト不要、認証不要。

#### 想定読者

E2Eを書き始めて、たまに落ちるテストに悩んでいる新人。

#### タイトル案

1. `Playwright 1.62のretryStrategy: 'isolated'を、わざとフレークさせて試してみた`
2. `並列実行の巻き添えか本当のバグか：Playwrightの隔離リトライを試す`
3. `フレークテストをisolatedリトライで切り分けてみた`

#### 検証でやること

- 共有リソース（同一ポート／同一ファイル）を奪い合う「並列だと落ちる」テストを用意
- 既定リトライと `retryStrategy: 'isolated'` で結果・実行順・所要時間を比較
- レポート出力とワーカー割り当ての違いをスクリーンショット/ログで記録

#### 検証手順

1. `npm i -D @playwright/test@latest` → `npx playwright --version` を記録
2. localhost に静的サーバーを立て、フレークするテストを3〜5本用意
3. `retries: 2` の既定設定で複数回実行し、結果を集計
4. `retryStrategy: 'isolated'` に変更して同回数実行、結果と所要時間を比較
5. 差分を表にまとめる

### 4. npm 12で`--allow-git`既定noneになったので、ローカルgit依存を入れて怒られてみた（26点）

- 許可フラグを付けた場合の通り方、lockfile への影響を記録

### 推奨テーマ

**Deno 2.9の`Deno.test.each()`と`t.assertSnapshot()`を、node:testの同等コードと書き比べてみた**

### 理由

- **トレンド性**: Deno 2.9 は直近リリース（2026-06-25）。パラメータ化テストとスナップショットの標準搭載は他ランタイムに無い差分で、話題性の根拠が公式ブログという一次情報にある
- **新人でも検証できる**: `deno upgrade` と `deno test` だけ。認証・課金・外部サービスが一切不要で、AIエージェント単独で完走できる
- **Zenn読者に刺さる**: 「node:test では毎回 for で回していた」という具体的な痛みに対する比較で、読者の再現コストも低い
- **半日〜1日で終わる**: 対象関数は小さくてよく、失敗→`-u`更新までのサイクルが数分で回る
- **完成イメージ**: Deno版とNode版のコードを並べた比較表＋失敗時の出力全文＋スナップショット更新の実行ログ。分量・見どころともに1本として十分
- 上位候補の中で唯一「成功する検証」になる見込みが高く、過去記事に多い『〜で止まった記録』系と並べたときのバランスも良い

### 最小検証プラン

1. `deno --version` を記録し、`deno upgrade` で 2.9 系にしてから再記録（現状 2.8.3）
2. 対象コード（`add(a,b)` と `renderHeader({title})`）を用意し、Deno版テストを `Deno.test.each()` で書く
3. node:test 版を Node 26 系で同等に書き（`nvm install 26`）、行数・失敗出力を比較して表にする
4. `t.assertSnapshot()` を追加 → `__snapshots__` 生成を確認 → 出力を変えて失敗させ、全文を保存
5. `deno test -u` で更新 → 再パスまでのログを保存し、node:test 側の同等機能と比較して締める
