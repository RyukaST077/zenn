## 上位候補の詳細

### 1. node:testの`context.log()`と`test:log`イベントを試す

#### 概要

Node.js 26.6.0（2026-08-03）のtest runnerに追加された`context.log()`と、それが発火する`test:log`イベントを実際に使い、
従来の`console.log` / `t.diagnostic()` との違いを書き比べる。さらにカスタムreporterで`test:log`を購読し、
「どのテストのログか」が構造化されて取れることを確認する。

#### なぜ今よさそうか

- リリースから10日ほどの最新機能で、日本語の解説記事が見当たらない
- node:testで誰もが困る「テスト中の`console.log`がどのテストのものか分からない」に直接効く
- 追加APIが小さいので、半日で全体を検証しきれる

#### 新人が検証しやすい理由

- 依存パッケージゼロ。`node --test` と数十行のテストファイルだけで完結する
- 標準reporter（spec / tap / dot）で出力を並べれば、それ自体が記事の図表になる
- カスタムreporterもTransformStream相当を1つ書くだけ

#### 想定読者

node:testを使い始めた新人〜実務2年目。CIでテストログが読みづらいと感じている人。

#### タイトル案

1. Node 26.6の`context.log()`を`console.log`と書き比べて、テストログの迷子を直してみた
2. node:testの新しい`context.log()`と`test:log`イベントを初めて触ってみた
3. `console.log` / `t.diagnostic` / `context.log`、node:testのログ3種類を並べてみた

#### 検証でやること

- 3種類のログ出力（`console.log` / `t.diagnostic()` / `context.log()`）を同一テストに仕込み、reporterごとの出力差を取る
- 並行実行（`concurrency`）や`--test-force-exit`下でログの帰属がどうなるか確認する
- カスタムreporterで`test:log`と`test:diagnostic`を購読し、受け取れるフィールドをダンプする
- `TestStream`イベントの`entryFile`が何を指すか（テストファイルか、起点ファイルか）を確認する
- サブテスト（`t.test()`）内で呼んだときのネスト表現を見る

#### 検証手順

1. Node 26.6以上を用意し、`node -v` と `node --test --help` で該当フラグ・APIの有無を記録する
2. `context.log()` が実在するか、`test:log` がドキュメントに載っているかを公式APIドキュメントで確認する
3. 3種のログを含むテストファイルを作り、`--test-reporter=spec|tap|dot` で3回実行してログ全文を保存する
4. `test:log` を購読するカスタムreporterを書き、イベントオブジェクトをJSONで出力する
5. 並行実行・サブテスト・失敗テストの各パターンでログの帰属を確認し、表にまとめる

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（テストログが誰のものか分からない問題）
3. 事前に調べたこと（26.6のリリースノートとAPIドキュメント）
4. 環境構築（Nodeバージョンの確認）
5. 実際に試したこと（3種のログ比較・reporterごとの出力）
6. 詰まった点
7. 触ってみて分かったこと（カスタムreporterで取れる情報）
8. 既存技術と比べて感じたこと（`console.log` / `t.diagnostic`との使い分け）
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

日本語の先行記事がまだ無い。かつ「新機能の紹介」ではなく**既存3手段との書き比べ表**と**カスタムreporterで取れるフィールドの実ダンプ**まで出すことで、
リリースノートの翻訳では得られない情報になる。

#### 参考リンク

- https://nodejs.org/en/blog/release/v26.6.0
- https://github.com/nodejs/node/releases/tag/v26.6.0
- Node.js公式APIドキュメント `test` セクション

#### 注意点

- 手元のNodeが26.6未満だと機能自体が無い。最初にバージョンゲートを確認し、無ければその時点を記事の「詰まった点」にする
- `context.log()` はまだstability: experimental の可能性がある。ドキュメント上の安定度を必ず引用する
- リリースノートの記述だけを根拠に挙動を断定しない。必ず実行結果を貼る

### 2. Vite 8.1のBundled Dev Modeを有効化して起動時間とHMRを測る

#### 概要

Vite 8.1（2026-06-23）の実験機能 `experimental.bundledDev`（CLIは`--experimental-bundle`）を有効にし、
コンポーネントを機械的に大量生成したReactアプリで、devサーバの起動時間・フルリロード・HMR反映時間を測って比較する。

#### なぜ今よさそうか

- 公式は「10,000コンポーネントで起動15倍・フルリロード10倍」と主張しており、その数字を自分の環境で確かめる価値がある
- 実験機能なので「サードパーティプラグインが動かない」など、踏みに行けば必ず素材が出る
- 過去記事はVite 8の**本番ビルド時間**を測ったもので、今回は**開発サーバ**という別の切り口

#### 新人が検証しやすい理由

- `npm create vite@latest` から始められる
- コンポーネントはスクリプトで生成できるので、規模を100 / 1,000 / 3,000と段階的に振れる
- 計測はdevサーバのready時間ログとPlaywrightのナビゲーション時間で取れる

#### 想定読者

Viteを使っているが8系の実験機能は追えていない人。大きめのアプリで開発サーバが重いと感じている人。

#### タイトル案

1. Vite 8.1のBundled Dev Modeを1,000コンポーネントで試したら、起動は速くなったが○○が動かなかった
2. Vite 8.1の`experimental.bundledDev`を有効にして、devサーバの起動時間を測ってみた
3. 「起動15倍」を自分のマシンで確かめる — Vite 8.1 Bundled Dev Mode検証ログ

#### 検証でやること

- コンポーネント数を100 / 1,000 / 3,000と変えたアプリを生成する
- 各規模で `bundledDev` のon/offそれぞれのdevサーバ起動時間を複数回測って中央値を取る
- Playwrightで初回表示までの時間とネットワークリクエスト数を取る
- 1ファイルだけ書き換えてHMR反映までの時間を測る
- プラグイン（例: SVGR系やモック系）を足したときに壊れるかを確認する

#### 検証手順

1. `npm create vite@latest` でReact + TSアプリを作り、`vite --version` が8.1以上かを確認する
2. コンポーネント生成スクリプトを書き、規模別のアプリを用意する
3. `bundledDev: false` の状態で起動時間・リロード・HMRを計測してベースラインを取る
4. `experimental.bundledDev: true` に切り替えて同じ計測を行う
5. リクエスト数・ログの差分と、公式が挙げる制限に自分の構成が該当するかを突き合わせる

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（開発サーバが遅くなる理由）
3. 事前に調べたこと（Vite 8.1リリースノートとbundled dev modeの設計）
4. 環境構築（規模別アプリの生成）
5. 実際に試したこと（規模×on/offの計測結果）
6. 詰まった点（プラグイン非互換など）
7. 触ってみて分かったこと
8. 既存技術と比べて感じたこと（従来のunbundled devとの使い分け）
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

公式ベンチは10,000コンポーネントという極端な規模。**現実的な規模（100〜3,000）でどこから効き始めるか**という損益分岐点を出すと、
「うちで入れるべきか」の判断材料になり、紹介記事と差がつく。

- 計測は必ず複数回・中央値で。1回計測の数字を断定的に書かない
- マシンスペックとNode/Viteの正確なバージョンを明記する

### 3. oxlintの型認識lint（安定版）を既存TSプロジェクトに当てる

#### 概要

2026-07-22に安定版となったoxlintの型認識lint（tsgolint / typescript-go ベース）を既存TypeScriptプロジェクトに導入し、
typescript-eslintの型認識ルールと**検出結果と実行時間の両方**を突き合わせる。

#### なぜ今よさそうか

- 型認識lintが「試験的」から「安定」になった直後で、導入判断を迷っている人が多い
- typescript-eslintの型認識ルール61個中59個をカバーという具体的な数字があり、残り2個が何かを確かめる価値がある
- oxlintはVite 8の既定リンターにも採用され、触る機会が増えている

#### 新人が検証しやすい理由

- `pnpm add -D oxlint-tsgolint@latest` と `oxlint --type-aware` だけで動く
- 検出結果の突き合わせは、両者の出力をファイルに落としてdiffを取るだけ
- 「わざと型エラーになるコード」を用意すれば、検出できる/できないが明快に出る

#### 想定読者

ESLint + typescript-eslint を運用していて、CI のlint時間が気になっている人。

#### タイトル案

1. oxlintの型認識lintが安定版になったので、typescript-eslintと検出結果を突き合わせてみた
2. `oxlint --type-aware` を既存TSプロジェクトに当てて、拾えたルール・拾えなかったルールを数えた
3. ESLintの型認識ルールをoxlintに寄せたら、何が減って何が速くなったか

#### 検証でやること

- 型認識ルールが発火するサンプルコード群（floating promise、unsafe assignment など）を用意する
- typescript-eslint と oxlint --type-aware を同じコードに当て、検出件数とルール名を突き合わせる
- 未対応の2ルールが何かを特定する
- 実行時間を複数回計測して比較する
- 設定ファイル（`typeAware` / `typeCheck`）の書き方と、tsconfigの指定が必要かを確認する

#### 検証手順

1. TSプロジェクトを用意し、ESLint + typescript-eslint の型認識ルールを有効にした状態をベースラインにする
2. 型認識ルールが確実に発火するサンプルを10種類ほど書く
3. ESLint実行結果をJSONで保存する
4. oxlint-tsgolintを入れ、`oxlint --type-aware` の結果をJSONで保存する
5. ルール名でjoinして「両方検出 / oxlintのみ / ESLintのみ」に分類し、実行時間とあわせて表にする

## 最初に試すべき1本

### 推奨テーマ

**node:testの`context.log()`と`test:log`イベントを試す**（候補1）

### 理由

- **トレンド性**: Node.js 26.6.0は2026-08-03リリース。調査時点で9日前の機能で、日本語記事が見当たらない
- **新人でも検証できる理由**: 依存パッケージゼロ、`node --test` と数十行のテストファイルだけで完結する。AIエージェント単独・完全ローカルで最後まで走る
- **Zenn読者に刺さる理由**: 「テスト中の`console.log`がどのテストのものか分からない」はnode:testを使う全員が踏む問題で、既存3手段との比較表がそのまま実用情報になる
- **半日〜1日で検証できるか**: 検証対象のAPIが小さく、reporterごとの出力差分収集とカスタムreporter作成を含めても半日で足りる
- **記事の完成イメージ**: 3種のログ出力 × 3つのreporterの出力全文、`test:log`イベントのJSONダンプ、並行実行時の帰属を示した表を軸にした検証ログ記事

### 最小検証プラン

1. `node -v` でバージョンゲートを確認し、26.6未満なら入手手段（nvm等）を含めて記録する
2. 公式APIドキュメントで`context.log()`と`test:log`のstabilityを確認して引用する
3. `console.log` / `t.diagnostic()` / `context.log()` を含むテストを書き、spec / tap / dot の3reporterで実行してログ全文を保存する
4. `test:log`を購読するカスタムreporterを書き、イベントのフィールドをJSONでダンプする
5. 並行実行・サブテスト・失敗テストの3パターンでログの帰属を確認し、比較表にまとめる

### 想定タイトル

`Node 26.6の context.log() を console.log と書き比べて、テストログの迷子を直してみた`
