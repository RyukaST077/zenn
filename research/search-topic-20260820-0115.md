## 上位候補の詳細

### 1. `deno compile --engine quickjs` で単一バイナリのエンジンをV8からQuickJSに替えてみる

#### 概要

Deno v2.9.5（2026-08-06）で `deno compile` に実験的な `--engine` オプションが入り、生成する単一バイナリのJSエンジンを **V8（既定）と QuickJS** から選べるようになった。同じ小さなCLIツール（TypeScript製）を2回ビルドし、次の4点を実測して表にする。

1. 実行ファイルのサイズ
2. 起動時間（`--version` 相当の即終了処理を複数回計測）
3. 計算の重い処理の実行時間（QuickJSはJITなしのインタプリタなので遅くなるはず）
4. 挙動差（同じスクリプトで結果が変わる／エラーになる箇所があるか）

公式ドキュメントが明言しているトレードオフ（「小さい実行ファイル」「起動とメモリは軽い」「compute-heavyは遅い」「挙動差の可能性あり」「V8と同じセキュリティ更新は受けない」）が、**手元で本当にその通りの数字になるか**を確かめるのが芯。

#### なぜ今よさそうか

- 2026-08-06 リリースの機能で、日本語の検証記事がまだ見当たらない（差別化余地が最大）
- 「V8以外のエンジンを公式オプションで選べる」は Deno にとって初。話題性が高い
- サイズと時間という**数値が必ず出る**ので、記事が「触っただけ」で終わらない
- 過去記事の Deno 3本（`deno29-package-lock-seed-ci-check` / `deno29-task-cache-boundaries` / `deno29-test-each-snapshot`）とテーマが完全に別（配布・エンジン層の話）

#### 新人が検証しやすい理由

- 必要な操作は `deno compile` を2回叩くだけ。設定ファイルもほぼ不要
- 認証・課金・サインアップが一切不要。`denort-quickjs-<target>.zip` は自動ダウンロード
- 「サイズを `ls -l` で見る」「`time` で測る」という新人でも読める手段で結論が出る

#### 想定読者

- Deno / Node で作ったCLIツールを配布したい新人〜2年目
- 「単一バイナリが数十MBもあるのは何とかならないのか」と思ったことがある人
- JSエンジンの違い（JITの有無）が実行時間にどう出るのか見てみたい人

#### タイトル案

1. `deno compile --engine quickjs を試して、V8とバイナリサイズ・起動時間・計算速度を比べてみた`
2. `Denoの単一バイナリをQuickJSでビルドしたら、何が軽くなって何が遅くなったのか`
3. `deno compile のエンジンをV8からQuickJSに替えて、数字を4つ測ってみた`

#### 検証でやること

- Deno 2.9.5 以上を用意し、`--engine` オプションが実際に受け付けられるか確認する
- 小さなCLI（引数を受けて何か出力する程度）＋計算の重い関数（フィボナッチや素数列挙など）を1本用意する
- V8版・QuickJS版の2バイナリをビルドし、サイズ・起動時間・計算時間を複数回測って中央値を取る
- 同じスクリプトで挙動差が出る箇所を探す（`Intl`、正規表現、`Temporal`、`structuredClone` などモダンAPIの有無）
- クロスコンパイル（`--target`）でも QuickJS 版が作れるか1ターゲットだけ試す

#### 検証手順

1. `deno --version` でバージョンを確認し、2.9.5 未満なら `deno upgrade`
2. `main.ts`（CLI本体）と `bench.ts`（計算の重い処理）を作り、`deno run` で動くことを確認
3. `deno compile -o cli-v8 --engine v8 main.ts` と `deno compile -o cli-quickjs --engine quickjs main.ts` を実行し、ログを全文保存する
4. `ls -l` でサイズ比較、起動時間と計算時間をそれぞれ10回測ってスクリプトで集計する
5. モダンAPIを並べた `probe.ts` を両バイナリで実行し、差分（エラー・出力違い）を記録する
6. `--target aarch64-unknown-linux-gnu` などで QuickJS 版のクロスコンパイルを1回試す

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（単一バイナリのサイズと起動時間）
3. 事前に調べたこと（公式が挙げるトレードオフ）
4. 環境構築（Denoのバージョンと `--engine` の有無）
5. 実際に試したこと（4つの計測）
6. 詰まった点
7. 触ってみて分かったこと（公式の説明と実測の一致／不一致）
8. V8版と比べて感じたこと
9. どんな人に向いていそうか（配布サイズを削りたい人／計算重めの処理がある人）
10. まとめ

#### 差別化ポイント

- ニュース紹介ではなく**サイズ・時間の実測値の表**が主役になる
- 「速くなる」ではなく「**軽くなるが遅くなる**」という素直なトレードオフを数字で示せる
- 挙動差の探索（モダンAPIが使えるか）まで踏み込むと、実際に採用を検討する人に効く

- Deno v2.9.5 リリース: https://github.com/denoland/deno/releases/tag/v2.9.5

- Deno Releases.md: https://raw.githubusercontent.com/denoland/deno/main/Releases.md

### 2. Node 26.7 の `ModuleHooks` の `Symbol.dispose` で、loader hooks を `using` に閉じ込める

#### 概要

Node.js 26.7.0（2026-08-05）の Notable Changes に **`module`: implement `Symbol.dispose` in `ModuleHooks` (#63928)** がある。`module.registerHooks()` の戻り値が disposable になり、

```js
{
  using hooks = registerHooks({ load(url, ctx, next) { /* ... */ } });
  await import('./target.mjs');   // フックが効く
}
// ブロックを抜けた時点で自動的に deregister される
await import('./other.mjs');     // フックは効かない
```

と書けるようになった、という話。loader hooks はこれまで一度登録するとプロセス終了まで残るため、テストごとにフックを変えたいときは**プロセスを分けるしかなかった**。それがブロックスコープで閉じられるなら、モジュールモックのテストの書き方が変わる。

さらに、この検証には**面白い引っかかりがある**。`nodejs.org/api/module.html` の `registerHooks()` の項は `[Symbol.dispose]` に「added in v23.5.0, v22.15.0」と書いているのに、26.7.0 のリリースノートは同じ機能を26.7の SEMVER-MINOR として挙げている。**ドキュメントとchangelogが食い違っている**ので、複数バージョンで実際に動かして境界を確かめる価値がある。

#### なぜ今よさそうか

- 2026-08-05 の最新Currentの新機能で、日本語の解説がまだ無い
- 「テストごとにプロセスを分けなくてよくなる」は実務の痛みに直結する
- ドキュメントとchangelogの不一致という**調べる動機がはっきりした謎**がある。結果がどちらに転んでも記事になる
- 過去記事 `using-symbol-dispose-try-finally-compare` は「`using` を try/finally と書き比べた」記事で、**言語機能そのものの入門**。今回は「その `using` が実際のNode APIに載ったので、フックのスコープ問題が解けるか」という応用・境界検証で、切り口が明確に違う（記事内でも過去記事との違いを明示する）

#### 新人が検証しやすい理由

- 必要なのは小さな `.mjs` ファイル3〜4本と `node` コマンドだけ。依存パッケージ0
- 「フックが効いた／効かない」は `console.log` か import 結果で一目で分かる
- バージョン比較は公式Dockerイメージ（`node:22`, `node:24`, `node:26.6`, `node:26.7`）で機械的に回せる

#### 想定読者

- `node --import ./register.mjs` のような loader/hooks 設定でつまずいた新人
- テストでモジュールをモックしたいが、`vi.mock` の裏側が分からず不安な人
- `using` を「文法は知っているが使い所が分からない」段階の人

#### タイトル案

1. `Node 26.7のModuleHooksがusingで閉じられるようになったので、どのバージョンから効くのか確かめた`
2. `loader hooksをテストごとに閉じたい。using registerHooks() を22/24/26で試した記録`
3. `公式ドキュメントとchangelogでバージョンが食い違っていたので、ModuleHooksのSymbol.disposeを実測した`

#### 検証でやること

- `registerHooks()` の戻り値に `Symbol.dispose` があるかを実行時に確認する（`typeof hooks[Symbol.dispose]`）
- `using` ブロックの内と外で、同じモジュールの import 結果が変わることを確認する
- `deregister()` を明示的に呼んだ場合と `using` に任せた場合で挙動が同じか比べる
- Node 22 / 24 / 26.6 / 26.7 の4バージョンで同じスクリプトを流し、**どこから動くのか**を表にする
- フックを入れ子にした場合（LIFOチェーン）にスコープを抜ける順番が期待通りかを見る

#### 検証手順

1. `docker run --rm -v $PWD:/w -w /w node:26 node -e "..."` の形で複数バージョンを回せる土台を作る
2. `hooks.mjs`（load フックで特定モジュールの中身を差し替える）と `target.mjs` を用意する
3. `using` ブロック内で `await import('./target.mjs')`、ブロック外でもう一度 import し、結果の差をログに出す
4. 同じスクリプトを `node:22` / `node:24` / `node:26.6` / `node:26.7` で実行し、成功・失敗・エラー全文を保存する
5. `deregister()` 明示呼び出し版と入れ子版も同様に流し、結果を表にまとめる

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（loader hooksがプロセス全体に残る問題）
3. 事前に調べたこと（26.7のchangelogと公式ドキュメントの記述の食い違い）
4. 環境構築（Dockerで4バージョン並べる）
5. 実際に試したこと（`using` の内と外／バージョン別）
6. 詰まった点
7. 触ってみて分かったこと（結局どのバージョンから効くのか）
8. `deregister()` を手で呼ぶ書き方と比べて感じたこと
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

- 「新機能の紹介」ではなく **ドキュメントとchangelogの矛盾を実測で決着させる**構成
- バージョン境界の表が残るので、あとから同じ疑問を持った人にそのまま役立つ
- 筆者の過去記事（`using` 入門）からの自然な続き物として書ける

#### 参考リンク

- Node.js v26.7.0 リリースノート: https://nodejs.org/en/blog/release/v26.7.0
- PR #63928: https://github.com/nodejs/node/pull/63928
- `node:module` API ドキュメント: https://nodejs.org/api/module.html
- `module.registerHooks()` tracking issue: https://github.com/nodejs/node/issues/56241

#### 注意点

- `registerHooks()` は Stability 1.2（Release candidate）。安定APIとして紹介しない
- 22/24 でも動いてしまった場合は「26.7で何が変わったのか」をPR #63928 の差分から確認して補足する（結論を曲げない）
- `using` 構文自体が使えないバージョンだと構文エラーで落ちる。**エラーの種類（構文エラー／`Symbol.dispose` 不在）を区別して記録する**

### 3. Vitest 5 の `vi.when()` を、従来の書き方2通りと書き比べる

#### 概要

Vitest 5.0.0-beta.6 で `vi.when()`（PR #10174）が追加された。「引数がこれなら、この値を返す」という条件付きスタブを標準APIで書けるようになったもの。従来これをやるには（a）`mockImplementation` の中で `if` を書く、（b）サードパーティの `vitest-when` を入れる、の2択だった。同じテスト要件を3通りで書き、**行数・読みやすさ・型の効き方・失敗時のエラーメッセージ**を比べる。

#### なぜ今よさそうか

- Vitest 5 は RC 段階（rc.2 が 8月中旬）で、GA前に触った記事の価値が高い
- `vitest-when` という「これを入れて解決していた」既存パッケージがあるので、**比較対象が最初から用意されている**
- 公式ドキュメント（vitest.dev/api/vi）にはまだ `vi.when()` の記載がなく、リリースノートとPRを読んで書く必要がある＝一次情報を当たる記事になる
- 過去記事 `vitest5-rc-breaking-changes` は「5 RC に上げて壊れた箇所」の移行ログ。こちらは**新APIの使い勝手**で、切り口が別

#### 新人が検証しやすい理由

- テスト1本と関数1本があれば成立する。アプリを作る必要がない
- 3通りのコードを並べるだけで記事の骨格ができる
- `vitest --run` で結果が即出る

#### 想定読者

- Vitestでモックを書いていて `mockImplementation` の `if` が増えて困っている新人
- `vitest-when` を入れるか迷っている人
- Vitest 5 への移行を検討している人

#### タイトル案

1. `Vitest 5のvi.when()を、mockImplementationの分岐とvitest-whenと3通りで書き比べてみた`
2. `mockImplementationのifが増えてきたので、Vitest 5のvi.when()を試した`
3. `Vitest 5で入ったvi.when()は、vitest-whenの代わりになるのか書いて確かめた`

#### 検証でやること

- 「id によって返り値が変わる／404なら例外」程度の関数をスタブする要件を1つ決める
- 同じ要件を3通り（`mockImplementation` 分岐 / `vitest-when` / `vi.when()`）で実装する
- 想定外の引数で呼ばれたときの挙動とエラーメッセージを3通りで比べる
- 型（TypeScript）が引数・返り値にどこまで効くかを確認する

#### 検証手順

1. `vitest@rc` でプロジェクトを作り、`vitest --version` を記録する
2. 対象関数とテスト要件を決め、`mockImplementation` 版を書いて通す
3. `vitest-when` を入れて同じテストを書き、通す
4. `vi.when()` 版を書く（公式ドキュメントに無いのでリリースノートとPR #10174 のテストコードを参照する）
5. 3通りそれぞれで「未定義の引数で呼ぶ」テストを追加し、失敗時の出力を全文保存する

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（条件付きモックの書きづらさ）
3. 事前に調べたこと（`vi.when()` はまだ公式ドキュメントに無い）
4. 環境構築（`vitest@rc`）
5. 実際に試したこと（3通りの実装）
6. 詰まった点
7. 触ってみて分かったこと（行数・型・エラーメッセージの差）
8. `vitest-when` と比べて感じたこと
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

- 公式ドキュメント未掲載のAPIを、リリースノートとPRから読み解いて動かす
- 「新APIが便利」ではなく **既存の解決策2つとの比較**で判断材料を出す
- 失敗時のエラーメッセージ比較は、実際に使う人が一番知りたいのに記事が少ない部分

#### 参考リンク

- Vitest v5.0.0-beta.6 リリース: https://github.com/vitest-dev/vitest/releases/tag/v5.0.0-beta.6
- PR #10174（`vi.when()`）: https://github.com/vitest-dev/vitest/pull/10174

- Vitest `vi` API: https://vitest.dev/api/vi

#### 注意点

- RC段階のAPIなので、GAで名前や引数が変わる可能性を明記する
- 公式ドキュメントが無いため、**PRのテストコードを根拠として引用**し、推測で使い方を書かない
- `vi.when()` が rc.2 時点で存在しない／別名になっている可能性がある。まず `typeof vi.when` を確認してから進める

## 最初に試すべき1本

### 推奨テーマ

**`deno compile --engine quickjs` と `--engine v8` で同じCLIを2回ビルドし、バイナリサイズ・起動時間・計算速度・挙動差を測る**

### 理由

- **トレンド性**: 2026-08-06 の Deno v2.9.5 で入ったばかりの機能。「V8以外のエンジンを公式オプションで選べる」は Deno 初で、リリースノートの筆頭に挙がっている
- **新人でも検証できる理由**: やることは `deno compile` を2回叩き、`ls -l` と `time` で測るだけ。認証・課金・サインアップが一切なく、設定ファイルもほぼ不要
- **Zenn読者に刺さる理由**: 日本語の検証記事が見当たらない。かつ「単一バイナリが重い」は Deno / Bun でCLIを配る人が全員ぶつかる不満で、サイズと起動時間の実測値はそのまま判断材料になる
- **半日〜1日で検証できるか**: ビルド2回＋計測3種＋API差分の探索で1〜2時間。クロスコンパイルまで含めても半日以内
- **記事の完成イメージ**: 冒頭に4行の比較表（サイズ / 起動時間 / 計算時間 / 使えなかったAPI）を置き、「軽くなるが遅くなる」というトレードオフを数字で示す。最後に「配布サイズ重視ならQuickJS、計算があるならV8」という選び方に落とす
- **失敗しても記事になる**: 安定版で `--engine` が通らなければ「どのバージョンから使えるのか調べた記録」に切り替えられる（筆者の過去記事にある gate 記録シリーズと同じ形に着地できる）

### 最小検証プラン

1. `deno --version` を確認し、必要なら `deno upgrade`。`deno compile --help` の出力を全文保存して `--engine` の有無を確かめる
2. `main.ts`（引数を受けて出力するCLI）と `bench.ts`（フィボナッチなど計算の重い処理）、`probe.ts`（`Intl` / `Temporal` / `structuredClone` などモダンAPIの有無を出力）を作る
3. `deno compile -o cli-v8 --engine v8 main.ts` と `deno compile -o cli-quickjs --engine quickjs main.ts` を実行し、ビルドログとダウンロードされたランタイム名を記録する
4. サイズを `ls -l` で比較。起動時間と計算時間を各10回計測して中央値を出す。`probe.ts` を両方で流して差分を取る
5. 結果を4行の表にまとめ、詰まった点（フラグ名・ダウンロード・挙動差）を時系列で書き出す

### 想定タイトル

`deno compile --engine quickjs を試して、V8とバイナリサイズ・起動時間・計算速度を比べてみた`

### 書く前に用意するもの

- Deno 2.9.5 以上（`deno upgrade` で更新）
- `main.ts` / `bench.ts` / `probe.ts` の3ファイル
- 計測を10回回して中央値を出す簡単なシェルスクリプト
- `deno compile --help` とビルドログの全文（フラグ名の裏付けとして記事に載せる）
- Deno v2.9.5 リリースページと `deno compile` 公式ドキュメントのURL

### 記事化するときの注意

- 実験的機能（experimental）であることを冒頭で明示し、「2.9.5時点では」と条件を必ず添える
- 専門家として断定しすぎない。エンジンの内部実装の解説には踏み込まず、測った範囲だけを書く
- 「新人が試した範囲」を明示する（測った項目・測っていない項目を分けて書く）
- うまくいった点だけでなく詰まった点を書く（フラグが通らない、ランタイムのダウンロードで待つ、など）
- 公式情報（リリースページ・compileドキュメント）へのリンクを入れる
- 実行ログ、ビルド出力、計測結果の生データを残す。ベンチは回数と中央値を明記し、1回計測で結論を出さない
- 「QuickJSは古い／劣っている」という書き方はしない。公式が挙げるトレードオフ（セキュリティ更新の差、JITなし）を正確に引用する
