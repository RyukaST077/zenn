## 上位候補の詳細

### 1. TS7 GA で tsgo 移行に再挑戦し、壊れた tsconfig と bin 周りを直しきる

#### 概要

TypeScript 7.0 が 2026-07-08 に GA。過去記事 `typescript7-tsc-bin-collision-log` では TS7 と 6 の併用検証が `tsc` の bin 衝突で止まっている。GA 版で同じ構成を組み直し、(a) bin 衝突が解消したか、(b) 実プロジェクトの tsconfig が 7.0 でどこまで通るか、(c) 型チェック時間がどれだけ変わるか、を実測する。

#### なぜ今よさそうか

- GA 直後で情報が入れ替わるタイミング（beta/RC 前提の記事が古くなっている）
- 「10倍速い」記事は飽和している一方、**移行で実際に壊れた箇所の一次ログ**は少ない
- 7.0 は programmatic API 非搭載のため、ツール連携で詰まる人が実際に出ている

#### 新人が検証しやすい理由

`npm i -D typescript@7` と `npx tsc --noEmit` だけで着手できる。壊れるのは tsconfig のオプションであり、直し方も公式に明記されている。

#### 想定読者

TypeScriptを日常的に使うが、7.0 にはまだ上げていない新人〜2年目。

#### タイトル案

1. TypeScript 7 GA版で、前回bin衝突で止まった移行検証に再挑戦した
2. TypeScript 7に上げたら tsconfig のどこが壊れたかを全部記録した
3. 新人が TypeScript 6→7 移行を1日でやってみた（速度と壊れた設定）

#### 検証でやること

- TS6 と TS7 を同居させたときの `tsc` bin 解決の挙動を再確認（過去記事の続き）
- `moduleResolution: node10` / `classic`、`baseUrl` 暗黙解決、`outFile`、amd/umd/systemjs を使った最小プロジェクトを作り、7.0 で何がエラーになるか一つずつ確認
- 同一プロジェクトで TS6 と TS7 の `--noEmit` 実行時間を複数回測定して中央値を出す

#### 検証手順

1. 小〜中規模の TS プロジェクトを用意（依存の少ない自作コード＋型定義を数百ファイル生成して規模を作る）
2. TS6 で `tsc --noEmit` を3回計測、ベースライン記録
3. `npm i -D typescript@7` に上げ、`npx tsc --noEmit` を実行してエラー全文を保存
4. 破壊的変更ごとに最小再現 tsconfig を作り、エラーメッセージと修正前後を対にして記録
5. 修正後に再度3回計測し、TS6 との比較表を作る。あわせて `node_modules/.bin` の中身を確認して bin 衝突の有無を記録

#### 記事構成案

1. はじめに（前回bin衝突で止まった話の続き）
2. なぜ今 TS7 を試すのか（GAのタイミング）
3. 事前に調べたこと（破壊的変更一覧）
4. 環境構築（TS6ベースライン計測）
5. 実際に試したこと（7.0にしてエラーを潰す）
6. 詰まった点（bin / programmatic API / moduleResolution）
7. 触ってみて分かったこと（速度の実測値）
8. 既存（TS6）と比べて感じたこと
9. どんな人に向いていそうか（今上げるべきか）
10. まとめ

#### 差別化ポイント

- 自分の過去記事の「失敗の続き」という連続性がある（バージョン違い＝重複ではない）
- 速度ベンチではなく**壊れた設定の一次ログ**が主軸
- 数字は公称値の引用ではなく自分の環境の実測

#### 参考リンク

- TypeScript 7.0 GA 関連（InfoQ 2026-08 / Microsoft DevBlogs）
- 自分の過去記事 `articles/typescript7-tsc-bin-collision-log.md`, `articles/typescript6-deprecated-tsconfig-already-error.md`

#### 注意点

- 過去記事2本と地続きなので、**何が前回と違う条件なのか**を冒頭で明示する
- 「10倍速い」は自分の測定値で語る。公称値と違っても、そのまま書く
- 大規模リポジトリを clone してのベンチは時間が読めないので、生成した自作コードで規模を作る

### 2. Node 26.7 の `--test-coverage-include-all` で「テストされていないファイル」を炙り出す

#### 概要

Node 26.7.0（2026-08-05）で `--test-coverage-include-all` が semver-minor で追加された。従来のカバレッジ計測は**テスト実行中に一度も読み込まれなかったファイルが報告に出ない**ため、カバレッジ率が実態より高く見える。このフラグの有無で同じプロジェクトの数字がどう変わるかを実測する。

#### なぜ今よさそうか

- リリースから数日で、日本語の解説がまだ存在しない
- 「カバレッジ90%だと思っていたら未テストのファイルが数えられていなかった」という、読者の実務に直結する落とし穴

#### 新人が検証しやすい理由

Node 26.7 と `node --test` だけで完結。外部ライブラリもDockerも不要で、1〜2時間で終わる。

#### 想定読者

`node --test` でテストを書き始めた新人。c8/nyc から乗り換えを検討している人。

#### タイトル案

1. カバレッジ90%だと思っていたら、未テストのファイルが数えられていなかった（Node 26.7 --test-coverage-include-all）
2. Node 26.7 の `--test-coverage-include-all` を入れたらカバレッジが何%下がったか
3. `node --test` のカバレッジが実態より高く出る理由を、新人が確かめてみた

#### 検証でやること

- 「テストされているファイル」「importされているがテストがないファイル」「どこからもimportされていないファイル」の3種類を含む小さなプロジェクトを作る
- `--test-coverage-include` あり／なし、`--test-coverage-include-all` あり／なしの4パターンでカバレッジ出力を比較
- 出力に現れるファイル一覧と総カバレッジ率の差分を表にする

#### 検証手順

1. Node 26.7 を用意し `node -v` を記録
2. `src/` に3種類のファイルを配置した最小プロジェクトを作成、`test/` に一部だけテストを書く
3. `node --test --experimental-test-coverage` を実行して出力を保存
4. `--test-coverage-include='src/**'` を追加して再実行、出力を保存
5. `--test-coverage-include-all` を追加して再実行し、3つの出力を突き合わせて差分表を作る
6. ついでに Node 26.6 以前でも同じコマンドを叩き、フラグが無い旨のエラーを記録する

#### 記事構成案

1. はじめに
2. なぜこの技術を試すのか（カバレッジの見かけ倒し問題）
3. 事前に調べたこと（リリースノートと関連Issue）
4. 環境構築（最小プロジェクトの構成）
5. 実際に試したこと（4パターン比較）
6. 詰まった点
7. 触ってみて分かったこと（数字の差）
8. 既存技術と比べて感じたこと（c8 の `--all` との関係）
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

- 過去記事 `node-test-randomize-seed-extraction` とは同じ `node --test` でも扱う機能が別（順序ランダム化 vs カバレッジ）
- 日本語情報ゼロの新フラグを、数字の差分という具体で示せる

#### 参考リンク

- nodejs/node Release v26.7.0
- Node.js 公式 Learn「Collecting code coverage in Node.js」
- nodejs/node Issue #58887（このフラグが提案された経緯）

#### 注意点

- `--experimental-test-coverage` の要否をバージョンごとに実機確認する（記憶で書かない）
- カバレッジ率の差は自分のサンプル構成に依存するので、構成を全部記事に載せる

### 3. `field-sizing: content` と JS の auto-grow textarea を書き比べる

#### 概要

`field-sizing` が Firefox 152（2026-06-16）で全主要エンジンに揃い Baseline Newly available に。長年 JS で書かれてきた「入力に合わせて伸びる textarea」が CSS 1行になる。両方を実装して、挙動・行数制限・スクロールバー・リサイズ時の差を Playwright のスクリーンショットで比較する。

#### なぜ今よさそうか

- Baseline 入り直後で「もう使っていい」と言えるようになったタイミング
- auto-grow textarea は誰もが一度は書く定番ハックで、読者の実感に刺さる

#### 新人が検証しやすい理由

HTML/CSS 1ファイルと数行の JS だけ。Playwright で文字を入力してスクショを撮れば検証が完結する。

#### 想定読者

フォームを実装したことがあるフロントエンド新人。

#### タイトル案

1. auto-grow textarea を JS で書いていたが、`field-sizing: content` で1行になった
2. `field-sizing: content` と JSのauto-growを書き比べて、挙動の違いを全部撮った
3. Baseline入りした `field-sizing` を新人が触って、置き換えられるか確かめた

#### 検証でやること

- JS版（`scrollHeight` を読んで `style.height` を更新）と CSS版を並べたページを作る
- 入力・削除・貼り付け・改行連打・`max-height` 到達時のスクロールバー挙動を比較
- `input` / `select` など textarea 以外への効果も確認
- 各ステップで Playwright のスクリーンショットを取得

#### 検証手順

1. `field-sizing` 版と JS 版を左右に並べた静的HTMLを作る
2. Playwright で長文をタイプし、各段階でスクショを撮る
3. `max-height` / `min-height` を付けた場合の折り返し・スクロール発生点を比較
4. 貼り付け・全削除・IME想定の長文などエッジケースを流す

### 推奨テーマ

### 理由

- **トレンド性**: 2026-08-05 リリースの新フラグ。日本語情報が確認できず、先行者になれる
- **新人でも検証できる理由**: Node と標準テストランナーだけ。外部依存・Docker・認証すべて不要
- **Zenn読者に刺さる理由**: 「カバレッジの数字が実態より高く出る」は多くのプロジェクトに当てはまる実害で、しかも一次情報が薄い
- **半日〜1日で検証できるか**: 1〜2時間で終わる見込み。余った時間を候補#4（`context.log()`）の下調べに回せる
- **記事の完成イメージ**: 同一プロジェクトに対する4パターンのカバレッジ出力を並べ、「フラグを付けたら 92% が 61% になった」といった具体的な数字の落差で締める

（TS7 GA は評価点では同点だが、検証時間の振れ幅が大きい。まず短時間で確実に1本仕上げ、次に TS7 を丸1日で取りにいく順序を推奨する）
