## 上位候補の詳細

### 1. Hono 4.13 の `app.query()` でQUERYサーバーを立てて、クライアント側がどこで落ちるか確かめる

#### 概要

RFC 10008（2026-06-15）で標準化された HTTP QUERY メソッドを、2026-08-03 リリースの Hono v4.13.0 の `app.query()` でサーバー側に実装する。そのうえで **curl / Node の `fetch`（undici）/ Playwright 経由のブラウザ `fetch`** の3経路から同じリクエストを投げ、どれが通り、どれがどう失敗するかを記録する。

#### なぜ今よさそうか

- RFC 公開から約2か月、Hono 対応から約2週間という鮮度。
- undici の issue #5454（2026-06-27 起票、PR #5459 で対応）が示すとおり、**クライアント実装がまさに追いついている最中**で、手元の Node のバージョンによって結果が変わる。「仕様は出た／サーバーは書けた／でもクライアントは？」という空白が実際に存在する。
- QUERY は CORS safelisted method ではないため、ブラウザからはプリフライトが必要。ここも実測対象になる。

#### 新人が検証しやすい理由

`npm i hono` してハンドラを1つ書き、`curl -X QUERY` を叩くだけで最初の1歩が終わる。難しい概念は「safe / idempotent / cacheable」の3語だけで、あとは観察と記録。

#### 想定読者

- Web API を書き始めた新人〜実務2年目
- 「QUERYメソッドが標準化された」というニュースだけ見て、実務で使えるのか判断したい人

#### タイトル案

1. Hono 4.13 の `app.query()` でQUERYメソッドを試したら、サーバーより先にクライアントで詰まった
2. 新HTTPメソッドQUERYを、curl・Node fetch・ブラウザの3経路から叩いて通る順に並べてみた
3. RFC 10008 の QUERY を実装するのは簡単だった。送る側が難しかった

#### 検証でやること

- Hono v4.13.0 を固定インストールし、`app.query()` で JSON ボディを受けるエンドポイントを1つ作る
- `curl -X QUERY --data '...'` で疎通し、ステータス・レスポンス・受け取ったボディをログに残す
- Node の `fetch('...', { method: 'QUERY', body })` を実行し、成功／例外の全文を記録する（`node --version` と `require('undici/package.json').version` も残す）
- 同じことを `GET` + body / `POST` でも実行し、挙動差を表にする
- Method Not Allowed ミドルウェアを入れて、`POST` を投げたときの 405 と `Allow` ヘッダの実値を確認する
- Playwright で localhost のページを開き、ページ内 `fetch` から QUERY を送る。プリフライト（OPTIONS）の有無と CORS エラーの全文をキャプチャする
- ETag / Cache ミドルウェアを有効にして、QUERY レスポンスに ETag が付くか確認する

#### 検証手順

1. `mkdir` して `npm init -y`、`npm i hono@4.13.2 @hono/node-server` をバージョン固定で入れる
2. QUERY ハンドラ + Method Not Allowed ミドルウェア + ETag ミドルウェアを持つサーバーを1ファイルで書き、起動する
3. `curl -v -X QUERY` で叩き、リクエスト/レスポンス全文をログへ保存する
4. Node の `fetch` で同じリクエストを送り、結果（または例外全文）を保存する。バージョン情報も併記する
5. 静的HTMLを配って Playwright で開き、ページ内 `fetch` から QUERY を送ってネットワークログとコンソールエラーを保存、スクリーンショットも撮る
6. GET+body / POST / QUERY の結果を1つの表にまとめる

#### 記事構成案

1. はじめに
2. なぜQUERYメソッドを試すのか（RFC 10008 と「16年ぶり」の話）
3. 事前に調べたこと（safe/idempotent/cacheable、CORS safelisted ではない点、undici の対応状況）
4. 環境構築（Hono 4.13.2 / Node のバージョン）
5. 実際に試したこと（curl → Node fetch → ブラウザ fetch）
6. 詰まった点（クライアント側の未対応、プリフライト、キャッシュ）
7. 触ってみて分かったこと（3経路の結果表）
8. GET+body / POST と比べて感じたこと
9. どんな人に向いていそうか（今すぐ使えるのか、待ちなのか）
10. まとめ

#### 差別化ポイント

### 2. PostgreSQL 19 Beta の `ON CONFLICT DO SELECT` と `DO UPDATE` を、dead tuple の数で書き比べる

#### 概要

PostgreSQL 19 Beta 1（2026-06-04）で入った `INSERT ... ON CONFLICT DO SELECT ... RETURNING` を Docker 上の 19beta で動かし、従来の get-or-create 定番だった `DO UPDATE SET id = excluded.id` と比較する。比較軸は「結果が同じか」ではなく **`pg_stat_user_tables` の `n_dead_tup`**（無駄な更新が起きていないか）に置く。

#### なぜ今よさそうか

- Beta 1 から2か月半、GA前という「今のうちに触れる」タイミング。
- 国内の `ON CONFLICT` 記事は `DO UPDATE` / `DO NOTHING` 止まりで、`DO SELECT` を実測した日本語記事が見つからなかった。
- get-or-create は新人でも必ず書く処理で、実用性が高い。

#### 新人が検証しやすい理由

Docker で1コンテナ起動し、psql で SQL を数本流すだけ。アプリコードは不要。

#### 想定読者

- SQL で upsert / get-or-create を書いたことがある新人
- `DO UPDATE` を「とりあえず」で使っている人

#### タイトル案

1. PostgreSQL 19 Beta の `ON CONFLICT DO SELECT` を、`DO UPDATE` と dead tuple の数で比べてみた
2. get-or-create のために `DO UPDATE SET id = id` を書いていた新人が、PG19 の `DO SELECT` を試した
3. PostgreSQL 19 Beta を Docker で立てて、新しい upsert を1本ずつ踏んでみた

#### 検証でやること

- Docker で PostgreSQL 19 Beta を起動し、`SELECT version()` でバージョンを固定記録する
- `DO NOTHING` / `DO UPDATE` / `DO SELECT` の3パターンで get-or-create を実装し、RETURNING が返る／返らないを確認する
- 同じキーへの重複 INSERT を N回（例: 1000回）流し、`pg_stat_user_tables` の `n_tup_upd` / `n_dead_tup` を3パターンで比較する
- `DO SELECT` に `RETURNING` を付けない場合や、ロック挙動（別セッションからの同時実行）を確認する
- 参考として PG18 コンテナでも同じSQLを流し、構文エラー全文を記録する

#### 検証手順

1. `docker run` で PostgreSQL 19 Beta のイメージを起動する（タグを確認。無ければ 19 系の最新タグ or ビルド手順に切り替える）
2. スキーマ（一意制約付きテーブル）を作る
3. 3パターンのSQLをそれぞれ実行し、返り値をログに残す
4. `pg_stat_reset()` → N回ループ実行 → `pg_stat_user_tables` を取得、を3パターン繰り返す
5. PG18 で同じ `DO SELECT` を流し、エラー全文を残す
6. 結果を表にまとめる

#### 記事構成案

1. はじめに
2. なぜこの機能を試すのか（`DO UPDATE SET id = id` という定番の気持ち悪さ）
3. 事前に調べたこと（PG19 Beta 1 のリリースノート、DO SELECT の定義）
4. 環境構築（Docker / バージョン記録）
5. 実際に試したこと（3パターンの結果と RETURNING）
6. 詰まった点
7. dead tuple の数で見えたこと
8. `DO UPDATE` と比べて感じたこと
9. どんな人に向いていそうか（GA前に知っておく価値）
10. まとめ

#### 差別化ポイント

「新機能を紹介する」ではなく **`n_dead_tup` という数値で差を出す**。国内に実測記事がない領域で、かつ新人が必ず書く処理を扱う。

#### 参考リンク

- https://www.postgresql.org/about/news/postgresql-19-beta-1-released-3313/
- https://www.postgresql.org/docs/19/sql-insert.html
- https://neon.com/postgresql/postgresql-19/on-conflict-do-select

#### 注意点

- **PostgreSQL 19 Beta の Docker イメージタグが利用可能かを最初に確認する**。入手できない場合はその時点の事実（試したタグとエラー）を記録し、PG18 との構文差の確認までで記事を成立させる（既出の「〜で止まった記録」形式にフォールバックできる）。
- Beta である点を明記し、GA で挙動が変わる可能性に触れる。
- `n_dead_tup` は autovacuum の影響を受けるため、検証中は autovacuum を止めるか、計測タイミングをログに残す。

### 3. SQLite 3.53 の `ALTER COLUMN DROP NOT NULL` を試して、`node:sqlite` 同梱版で通るか確かめる

#### 概要

SQLite 3.53.0（2026-04-09）で `ALTER TABLE ... ALTER COLUMN SET/DROP NOT NULL` が入った。従来は「12ステップのテーブル再作成」が公式推奨だった作業である。これを `sqlite3` CLI と Node 26 の `node:sqlite` の両方で試し、**同梱されている SQLite のバージョン差でどちらが通るか**を確認する。

#### なぜ今よさそうか

- 地味だが、マイグレーションを書く人には毎回刺さる変更。
- ランタイム同梱ライブラリのバージョン差という、既出記事（tsc bin衝突、pnpm store gate 等）と同じ得意パターンに乗る。

#### 新人が検証しやすい理由

`sqlite3` CLI と `node --version` があれば始められる。SQLも1行。

#### 想定読者

- SQLite でマイグレーションを書いている新人
- `node:sqlite` を使い始めた人

#### タイトル案

1. SQLite 3.53 の `ALTER COLUMN DROP NOT NULL` を試したら、`node:sqlite` の同梱版で止まった
2. 12ステップのテーブル再作成が1行になったので、CLI と node:sqlite の両方で試した
3. SQLite の NOT NULL を後から外せるようになったか、手元のバージョンで確かめた

#### 検証でやること

- `sqlite3 --version` / `node:sqlite` の `sqlite_version()` を取得して並べる
- 3.53 未満・以上のそれぞれで `ALTER TABLE t ALTER COLUMN c DROP NOT NULL` を実行し、成功／エラー全文を記録する
- 既存行が NULL を含む状態で `SET NOT NULL` を実行し、どう失敗するかを確認する
- 従来の12ステップ手順と行数・所要時間を比較する
- CHECK 制約の追加/削除も同様に試す

#### 検証手順

1. `sqlite3` CLI と Node の `node:sqlite` でそれぞれ `select sqlite_version()` を実行しログに残す
2. テーブルを作り NOT NULL 列を用意する
3. `ALTER COLUMN DROP NOT NULL` を両方で実行し、結果を記録する
4. `SET NOT NULL` を、NULL を含む行がある状態／ない状態で実行して比較する
5. 従来の12ステップ版スクリプトも書き、同じ結果になるか確認する
6. バージョンと結果の対応表を作る

#### 記事構成案

1. はじめに
2. なぜこれを試すのか（12ステップ手順のつらさ）
3. 事前に調べたこと（3.53.0 releaselog / lang_altertable.html）
4. 環境構築とバージョン確認
5. 実際に試したこと
6. 詰まった点（同梱バージョン差）
7. 分かったこと（バージョン対応表）
8. 従来手順と比べて感じたこと
9. どんな人に向いていそうか
10. まとめ

#### 差別化ポイント

新機能紹介ではなく「**自分の実行環境で本当に使えるのか**」に焦点を当てる。ランタイム同梱ライブラリのバージョン差は日本語記事が薄い。

#### 参考リンク

- https://sqlite.org/releaselog/3_53_0.html
- https://sqlite.org/lang_altertable.html

#### 注意点

- CHECK 制約の削除は公式ドキュメントでも扱いが限定的（`PRAGMA writable_schema` 等の回避策に言及あり）。**ドキュメントの記述と実際の挙動を混ぜず、実行結果として書く**。
- どのバイナリの SQLite を触っているかを常に明示する（CLI / node:sqlite / better-sqlite3 で別物）。

## 最初に試すべき1本

### 推奨テーマ

**Hono 4.13 の `app.query()` でQUERYサーバーを立てて、curl / Node fetch / ブラウザ fetch のどこで落ちるかを確かめる**

### 理由

- **トレンド性**: RFC 10008 は2026-06-15公開、Hono の QUERY 対応は2026-08-03。どちらも直近2か月以内の一次情報がある。
- **新人でも検証できる**: サーバーはハンドラ1つ、クライアントは `curl` と `fetch` 数行。概念も safe/idempotent/cacheable の3語で足りる。
- **Zenn読者に刺さる**: 国内記事は「実装して動いた」で止まっており、「じゃあ実務で使えるの？」に答えていない。undici issue #5454 という一次情報を根拠に、そのギャップを埋められる。
- **半日〜1日で終わる**: インストール・実装・3経路の実行・ログ整理で収まる。Docker もクラウドも不要。
- **どちらに転んでも記事になる**: クライアントが通らなければ「詰まった点」記事、通れば「プリフライトとキャッシュの実測」記事になる。
- **既出記事と重複しない**: `articles/` に Hono も HTTP プロトコル層の記事も存在しない。

### 最小検証プラン

1. `npm i hono@4.13.2 @hono/node-server` をバージョン固定で入れ、`app.query()` のエンドポイントを1つ作って起動する
2. `curl -v -X QUERY --data '{"q":"hello"}'` で疎通させ、リクエスト/レスポンス全文をログに残す
3. Node の `fetch(..., { method: 'QUERY', body })` を実行し、成功時のレスポンスまたは例外全文を、`node --version` と undici のバージョンとともに記録する
4. Method Not Allowed ミドルウェアを入れ、`POST` を投げて 405 と `Allow` ヘッダの実値を確認する
5. Playwright でページを開き、ページ内 `fetch` から QUERY を送って OPTIONS プリフライトの有無・CORS エラー全文・スクリーンショットを取得する
6. GET+body / POST / QUERY × curl / Node fetch / ブラウザ の結果を1つの表にまとめる

### 想定タイトル

「Hono 4.13 の `app.query()` でQUERYメソッドを試したら、サーバーより先にクライアントで詰まった」

### 書く前に用意するもの

- Node.js（バージョンを控える。undici の同梱バージョンも取得する）
- Hono v4.13.2 を固定インストールした最小プロジェクト
- Playwright（既存環境があれば流用。ブラウザ起動が失敗した場合は、その事実と切り分けをログに残す）
- 実行ログの保存先（curl の `-v` 出力、Node の例外全文、ブラウザのコンソール/ネットワークログ、スクリーンショット）

### 記事化するときの注意

- 専門家として断定しすぎない（「QUERYを使うべき」ではなく「今の手元ではここまで通った」）
- 「新人が試した範囲」を明示する（プロキシ・CDN・HTTP/2以降の中継は未検証であることを書く）
- うまくいった点だけでなく詰まった点を書く（クライアント未対応、プリフライト、キャッシュ）
- 公式情報へのリンクを入れる（RFC 10008、Hono リリースノート、undici issue）
- 実行ログ、スクリーンショット、コード、**すべてのバージョン番号**を残す
