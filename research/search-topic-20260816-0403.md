## 上位候補の詳細

### 1. pnpm 12 RC（Rustリライト）の「5つの差分」を実際に踏む

#### 概要

pnpm 12 は pnpm 11 のRustリライトで、公式が「コマンド・フラグ・設定・lockfile形式は据え置き、実質的な差分はこの5点」と明言している。その5点を、自作の小さなワークスペースfixtureで1つずつ再現し、pnpm 11 と結果を並べる。

#### なぜ今よさそうか

- pnpm 12 は2026年8月時点でRC。GA前に踏んでおくと「移行前に読める記事」になる
- 公式が差分を5点に限定しているので、**検証項目がそのまま章立てになる**（記事が薄くなりようがない）
- 日本語の実測記事はまだ見当たらない

#### 新人が検証しやすい理由

`npm i -g pnpm@next-12` 相当で入り、既存fixtureに対してコマンドを叩くだけ。壊れても fixture を捨てれば戻せる。

#### 想定読者

pnpm を使っているが11→12の移行判断がまだの人、新人でロックファイル差分の読み方を知りたい人。

#### タイトル案

1. pnpm 12（Rustリライト）RCに上げて、公式が挙げた5つの差分を全部踏んでみた
2. pnpm 11しか知らない新人がpnpm 12 RCを触って、壊れたのは1つだけだった話
3. `pnpm install --resolution-only` が消えた——pnpm 12の差分5点を手元で確かめた記録

#### 検証でやること

- pnpm 11 と pnpm 12 RC を同居させ、同じ fixture に両方を当てる
- `--resolution-only` 廃止 → `pnpm peers check` への置き換えを確認（11でのエラー文言と12での出力を並べる）
- Git依存（`github:user/repo` / `git+ssh://...` / フルHTTPS）の3表記でlockfileにどう記録されるかをdiffで見る
- `pnpm add -g yarn` が Yarn Classic ではなく現行Yarnを入れるかを確認
- 循環依存を含むfixtureで、インストール順を変えてlockfileがbyte-identicalになるかを`sha256sum`で検証
- `devEngines.runtime` を書いたプロジェクトで global node のバージョンが切り替わるかを確認

#### 検証手順

1. `mkdir pnpm12-fixture` でワークスペース（ルート＋packages/a, packages/b）を作る。循環依存を1組仕込む
2. pnpm 11 で `pnpm install` → lockfile と `pnpm install --resolution-only` の出力を保存
3. `corepack` あるいは `npm i -g pnpm@next-12` で pnpm 12 RC を入れ、`pnpm --version` を記録
4. 同じfixtureで `pnpm install` → lockfile を保存し、11版と `diff` を取る
5. 差分5点を1つずつ実行し、コマンド・出力・エラー全文を残す
6. `rm -rf node_modules pnpm-lock.yaml` → 依存の記述順を入れ替えて再インストールし、lockfileのハッシュを比較
7. 失敗した項目は、公式ドキュメントの記述と実際の挙動のズレとして記録する

#### 記事構成案

1. はじめに（pnpm 12 は「Rustになっただけ」なのか）
2. なぜこの技術を試すのか
3. 事前に調べたこと（公式が挙げる差分5点）
4. 環境構築（11と12 RCの同居、fixtureの構成）
5. 実際に試したこと（差分5点を1つずつ）
6. 詰まった点
7. 触ってみて分かったこと（lockfileの決定性は本当に効いたか）
8. pnpm 11と比べて感じたこと
9. どんな人に向いていそうか（移行を待つ判断材料）
10. まとめ

#### 差別化ポイント

過去記事 `pnpm11-minimum-release-age-ci-only-failure` はpnpm 11のセキュリティ既定値の話で、本テーマはバージョン違い＋切り口違い（移行差分の実測）。「公式の5点をそのまま検証項目にした」構成は日本語記事でまだ見ない。

- https://pnpm.io/blog/whats-different-in-pnpm-12
- https://pnpm.io/blog/releases/11.0

#### 注意点

- RCなので挙動が変わりうる。**検証日と `pnpm --version` の実出力を必ず記事に貼る**
- グローバルインストールを伴うので、既存のpnpm環境を壊さないよう `PNPM_HOME` を分けるか、Dockerの `node:24` イメージ内で完結させる
- 「Rustだから速い」を測りに行くと Vite 8 記事と同じ構図になる。**速度ではなく差分の再現に絞る**

### 2. Bumblebee でローカル依存資産を棚卸しする

#### 概要

Perplexityが2026年5月にOSS化した read-only サプライチェーンスキャナ Bumblebee を、意図的に「古い/怪しい」依存を仕込んだfixtureに当て、`baseline` / `project` / `deep` の3プロファイルで何が拾えるかを確かめる。NDJSON出力を `jq` で整形し、`npm ls` との見え方の違いまで見る。

#### なぜ今よさそうか

- 2026-05-22 公開でまだ新しく、日本語記事がほぼ無い
- **完全オフライン・アカウント不要・Apache-2.0**。AIエージェント単独検証の条件に完璧に合う
- npm/pnpm だけでなく **MCP設定ファイルやエディタ拡張** まで走査対象に含む点が、いまのエージェント時代の話題性と噛み合う

#### 新人が検証しやすい理由

読み取り専用（設計上、書き込みも任意コード実行もしない）なので、手元を壊す心配が要らない。出力がNDJSONなので `jq` で機械的に確認できる。

#### 想定読者

「勧告が出たけど自分の環境に入ってるのか分からない」新人、npm audit しか知らない人。

#### タイトル案

1. `npm audit` しか知らない新人が、Perplexity製Bumblebeeで手元の依存を棚卸ししてみた
2. MCP設定もエディタ拡張も見てくれるスキャナBumblebeeを、わざと汚したfixtureに当ててみた
3. Bumblebeeのbaseline / project / deep で、拾えるものがどれだけ変わるか比べた

#### 検証でやること

- Go 1.25+ を用意して `go install github.com/perplexityai/bumblebee/cmd/bumblebee@latest`（不可ならGitHub Releasesのビルド済みバイナリ、それも不可なら `golang:1.25` Dockerイメージ）

- `bumblebee roots` で走査対象パスを先に確認する
- `--profile baseline` / `project` / `deep` を順に実行し、検出パッケージ数と所要時間を比較
- 自作の `--exposure-catalog` JSON を書いて、仕込んだバージョンが finding として出るかを確認
- 同じfixtureに `npm ls --all` / `npm audit --json` を当てて、見えるものの違いを表にする

#### 検証手順

1. Goの用意（`go version` を記録。無ければDocker `golang:1.25` で代替し、その経緯も記事の素材にする）

6. `npm ls` / `npm audit` との比較表を作る
7. 検出漏れ・誤検出・所要時間の差を記録する

### 3. GAしたTypeScript 7を小さなfixtureに当てる

#### 概要

2026-07-08にGAしたTypeScript 7（Goネイティブ、tsgo）を、あえて「TS 5世代の書き方」で作った小さなfixtureに当て、報告されている3つの壁（strict既定化 / `baseUrl` 廃止 / `--outFile` 廃止・Compiler API未対応）を自分の手元で再現する。

#### なぜ今よさそうか

- GA直後で「上げていいか」の判断需要が最大
- 日本語でも移行記事は出始めているが、**エラーコードの内訳まで自分のfixtureで数えた**記録は少ない
- 過去記事 `typescript7-tsc-bin-collision-log` は bin衝突で検証が止まった記録なので、**その続き**として自然に書ける

#### 新人が検証しやすい理由

npm install と `tsc` / `tsgo` を叩くだけ。fixtureが小さければエラー全件を目視できる。

#### 想定読者

TypeScriptを実務で使っている新人〜2年目、TS 7移行を検討中のチーム。

#### タイトル案

1. TS7のbin衝突で止まった続き——GA版TypeScript 7を小さなfixtureに当て直した
2. `strict: false` で書いたコードをTypeScript 7に通したら、エラーが何件出るか数えてみた
3. 新人が「TS7に上げていいか」を、壊れたところだけ数えて判断してみた

#### 検証でやること

- `strict: false` / `baseUrl` + `paths` / `outFile` を使った意図的に古いfixtureを作る
- TS 6 と TS 7 の両方で `--noEmit` を実行し、エラーコード別に件数を集計（`grep -o 'TS[0-9]*' | sort | uniq -c`）
- `baseUrl` 廃止によるパスエイリアス解決エラーを再現し、`paths` 書き換えで解消するまでを記録
- `--outFile` を指定して、TS 7 で実際にどんなメッセージで拒否されるかを確認
- 過去記事で踏んだ bin衝突（`tsc`）を、今回はどう回避したかを明記する

#### 検証手順

1. fixture作成（意図的に `strict: false`・`baseUrl`・`outFile` を使う。ファイルは10〜20個程度）
2. TS 6 で `npx tsc --noEmit` → エラー0件になるまで整えて基準を作る
3. TS 7 を導入（過去記事のbin衝突を避ける導入手順を記録）
4. TS 7 で型チェックし、エラー全文を保存してコード別に集計
5. 壁を1つずつ潰す（strictを戻す／pathsを相対に書き換える／outFileをバンドラに寄せる）
6. 各段階で残エラー件数を表にする
7. 「そのまま上げられるか / 段階移行が要るか」を自分のfixture基準で結論づける

#### 記事構成案

1. はじめに（前回bin衝突で止まった話の続き）
2. なぜこの技術を試すのか
3. 事前に調べたこと（GAの経緯・報告されている3つの壁）
4. 環境構築（TS 6 / TS 7 の入れ方とbin衝突の回避）
5. 実際に試したこと（エラーコード別の集計）

### 推奨テーマ

**pnpm 12 RC（Rustリライト）に上げて、公式が挙げた「5つの差分」を実際に踏んでみた**

### 理由

- **トレンド性**: 主要パッケージマネージャのフルリライトが、2026年8月時点でRC。GA前に出せば先行記事になる
- **新人でも検証できる**: 追加ツール不要。`pnpm@next-12` を入れて既存fixtureにコマンドを当てるだけ
- **Zenn読者に刺さる**: 「上げたら何が壊れるか」は移行判断に直結する。pnpm利用者は日本語圏でも多い
- **半日〜1日で終わる**: 公式が差分を5点に限定しているので検証範囲が固定されている。1点あたり15〜30分
- **記事の完成イメージ**: 差分5点それぞれについて「公式の記述 → 実行コマンド → 実出力 → 11との差分」が並ぶ表形式の検証ログ。lockfileのdiffと `sha256sum` の一致確認が図として入る
- **gateリスクが最も低い**: 上位3候補のうち、候補2はGo 1.25+、候補3はbin衝突という既知のgateを抱える。本候補はnpm経由のインストールだけで始められる

### 最小検証プラン

1. `node:24` Docker コンテナ内に、ルート＋`packages/a`＋`packages/b` の pnpm ワークスペースfixtureを作る（循環依存を1組、Git依存を3表記ぶん仕込む）
2. pnpm 11 で `pnpm install` → `pnpm-lock.yaml` と `pnpm install --resolution-only` の出力を退避
3. pnpm 12 RC（`next-12` タグ）を導入し、`pnpm --version` を記録
4. 同じfixtureで `pnpm install` → lockfile を 11版と `diff`。Git依存の記録形式の変化を確認
