### Interpretation and alternative explanations

## Editorial brief

### Reader and situation

One reader: a CI, evaluation, or local-automation maintainer running `codex exec --ignore-user-config --ignore-rules` on a developer workstation, self-hosted runner, or reused container home while expecting checked-in instructions and the explicit prompt to be the only task inputs (reader definition: `practice/agent/agent-practice-codex-ignore-config-user-skills-20260815-0504.md`).

### Reader problem

The two visible flags remove user `config.toml` and execpolicy `.rules`, but they do not tell the maintainer whether a personal skill under the inherited `HOME` remains model-visible and explicitly invocable. A successful process exit cannot prove the skill catalog was absent (documented boundary and uncertainty: `research/agent/agent-knowhow-codex-ignore-config-user-skills-20260815-0504.md`; observed control/treatment distinction: `logs/agent/run-codex-ignore-config-user-skills-20260815-0504-20260815-051331/work/matched-home-skill-boundary/probe-result.json`).

### One-sentence article promise and takeaway

For Codex CLI `0.147.0`, this article will show that a treatment-only skill under disposable `$HOME/.agents/skills` returned its body-only marker even with both ignore flags, while the empty-home control failed closed, and will turn that observation into one rule: separately control or test the user skill catalog before calling an automation run skill-hermetic (evidence: `logs/agent/run-codex-ignore-config-user-skills-20260815-0504-20260815-051331/work/matched-home-skill-boundary/probe-result.json`; decision rule: `practice/agent/agent-practice-codex-ignore-config-user-skills-20260815-0504.md`).

### Coverage gap filled

Official documentation separately defines the two ignore flags and user-skill discovery, while existing reproducibility guidance discusses other ambient inputs. The missing coverage is a retained, version-pinned control/treatment run that combines both flags with a disposable `HOME`, keeps the random marker out of shared inputs, proves full treatment skill-body consumption, and yields a machine-checkable decision for CI and evaluation wrappers (source-gap analysis: `research/agent/agent-knowhow-codex-ignore-config-user-skills-20260815-0504.md`; current primary evidence: `logs/agent/run-codex-ignore-config-user-skills-20260815-0504-20260815-051331/execution-log.md`).

### Why the result matters in real work

A runner can correctly use both documented flags and still inherit a separate model-context input from its home directory. In the recorded case, the only fixture difference was the treatment skill, and the marker known only to its body appeared only in the treatment output; therefore wrappers that require checked-in-only instructions need a separate skill-catalog boundary rather than a flag-presence check (evidence: `logs/agent/run-codex-ignore-config-user-skills-20260815-0504-20260815-051331/work/matched-home-skill-boundary/probe-result.json`; exact setup: `logs/agent/run-codex-ignore-config-user-skills-20260815-0504-20260815-051331/work/matched-home-skill-boundary/ambient-skill-wrapper.mjs`).

### Practical decision rule and mapping

Decision rule: do not label a Codex automation invocation skill-hermetic merely because it includes `--ignore-user-config --ignore-rules`. For a pinned CLI environment, run a harmless empty-home/treatment hidden-marker probe. If the treatment returns the skill-body marker while the control does not, reject the two flags as a sufficient boundary and run production automation with a separately controlled user home/catalog. If both cleanly return unavailable, describe only that pinned non-reproduction. Treat marker leakage, inventory drift, tool use, version mismatch, malformed output, or incomplete execution as inconclusive (registered outcomes: `practice/agent/agent-practice-codex-ignore-config-user-skills-20260815-0504.md`; confirmed branch: `logs/agent/run-codex-ignore-config-user-skills-20260815-0504-20260815-051331/work/matched-home-skill-boundary/probe-result.json`).
