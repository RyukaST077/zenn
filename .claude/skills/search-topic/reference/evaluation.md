# 候補選定・変換・評価基準

`search-topic` の Step 5（変換）/ Step 6（評価）で使う。

## Candidate Selection Rules

候補にする技術は、以下を満たすものを優先する。

* 最近話題になっている
* 公式ドキュメントやチュートリアルがある
* 無料または低コストで試せる
* ローカル環境または無料枠で検証できる
* 半日〜1日程度で最小検証できる
* 新人エンジニア目線で学びが出せる
* Zenn読者が興味を持ちやすい
* 既存記事と差別化できる
* 小さな成果物を作れる
* 詰まった点も記事の価値にできる
* AIエージェント（Claude Code等）が単独でCLI・コード実行だけで最後まで検証できる
* 完全無料・認証不要・ローカルで完結する（またはトークン不要の公開API）
* ブラウザ操作が要る場合も Playwright で自動化・スクリーンショットできる

避けるもの。

* 大規模な本番環境が必要
* 高額なクラウド費用が発生しやすい
* 専門知識が重すぎる
* 検証に数日以上かかる
* 公式情報が少なすぎる
* セキュリティリスクが高い
* 規約やライセンス面が不明確
* 単なるニュース紹介で終わりそう
* 新人が実践するには難しすぎる
* 課金が必要なAPIキー／クレジットカード登録が前提（用意する人がいない）
* 人手のサインアップ・メール/電話認証・手動OAuthログインが必要
* 外部SaaSダッシュボードでの手動トークン発行や手動デプロイが必要
* GUI専用アプリ・実機・ハードウェア・有料クラウドの本番リソースが必要

## AI Agent Executability（AIエージェント単独実行の足切り）

検証・実践するのはAIエージェント単独で、人手を介さない。人手が要るテーマは**採点前に除外**する。
「ローカルCLI・コード・Playwright だけで最後まで完結できるか？」で判定する。

### OK（採用してよい）

* ローカルで動くライブラリ・CLI・フレームワーク（npm / pip / cargo 等でインストール）
* トークン不要の公開API、ローカルで動くモデル・DB（Docker / SQLite / ローカルLLM 等）
* `wrangler dev` / `supabase start` など**ローカルで完結する範囲**のクラウド系ツール
* Webアプリの表示・操作確認（localhost を Playwright で操作しスクリーンショットで確認）

### NG（除外する）

* 利用に課金APIキー／クレジットカードが必要（OpenAI等の有料キー前提 など）
* 鍵やアカウントの取得に人手のサインアップ・メール/電話認証・手動OAuthが必要
* SaaSダッシュボードでの手動設定・手動デプロイ・手動トークン発行が必要
* CAPTCHAやログイン壁でブラウザ自動化がブロックされる
* 実機・ハードウェア・GUI専用アプリ・有料クラウドの本番環境が必要

### 判定のコツ

* クラウド/BaaS/デプロイ系は「ローカルCLI・Dockerで完結する部分」に限定すれば採用可。
  デプロイやダッシュボード操作を含む検証は除外、またはローカル完結の記事に絞る。
* 「無料枠」でも登録に人手が要るなら不可。**登録・認証が不要か**で判断する。
* NGに1つでも該当したら候補から外す。迷ったら「人が一度でも手を動かす必要があるか」で切る。

## Past Article De-duplication（過去記事との重複除外）

Step 6 の足切り②で使う。`articles/` にある自分の過去記事と**実質同じ内容**の候補は除外する。
「同じ技術 × 同じ検証内容 × 同じ条件」なら焼き直しとみなす。判定は Step 1 で読んだ
既出テーマ一覧（title / topics / 検証内容）との照合で行う。

### 重複とみなす（除外）

* 対象技術が同じで、検証する内容・切り口もほぼ同じ
* バージョンも検証条件（対象アプリ・比較対象・OS/ランタイム等）も過去記事とほぼ同じ

### 重複とみなさない（採用可）

以下のいずれかで過去記事と明確に差がつくなら採用してよい。記事側で違いを明示すること。

* **バージョン違い**: 対象ツールのメジャー/マイナー更新後に再検証する（例: Vite 8 → Vite 9）
* **検証条件違い**: 比較対象・対象アプリ・データ規模・OS/ランタイムを変える
* **切り口違い**: 同じ技術でも別テーマ（例: ビルド速度 → プラグイン移行/設定移行/ハマり所）

### 例（現状の過去記事基準）

| 候補 | 判定 | 理由 |
|------|------|------|
| Vite 8/Rolldown のビルド時間を測ってみた | ❌ 除外 | `vite8-rolldown-build-benchmark-log` と実質同一 |
| Vite 9 が出たので同じアプリで再計測してみた | ⭕ 採用可 | バージョン違い（差分を明示） |
| Rolldown と Turbopack のビルド速度を比較してみた | ⭕ 採用可 | 比較対象＝検証条件が違う |
| Vite 8 移行で壊れた設定・プラグインを直した記録 | ⭕ 採用可 | 切り口が違う（速度ではなく移行ハマり所） |
| ZennとGitHubを連携して自動公開する | ❌ 除外 | `zenn-github-integration-auto-publish` と実質同一 |

## Topic Conversion

調査した技術は、そのまま出さず、Zenn記事として書ける形に変換する。
変換のゴールは「試した記録」ではなく、**読者が持ち帰る物がある形**にすること。

### Bad（技術名のまま）

* Bun
* Cloudflare Workers
* AIエージェント
* Drizzle ORM
* Playwright

### Bad（記事の形にはなっているが持ち帰りが無い）

読者が読み終わって手元に何も残らない型。過去57本がここに集中していた。

* Bunを初めて触って、Node.jsとの違いを小さなAPIで試してみた
* Playwrightで初めてE2Eテストを書いてみた
* Read()のdenyは許可リスト外コマンドへのリダイレクトも塞ぐか検証した
* Node 26で既定になったTemporalを、Dateと同じ処理で書き比べてみた

### Good（読者が持ち帰る物がある）

| 変換後 | 読者が持ち帰る物 | 型 |
|---|---|---|
| Bunに寄せて壊れた6箇所と、Nodeと両対応で通した package.json | そのまま使える設定 | `asset` |
| Playwrightの待ち方を5パターン測って、flakyが消えた書き方だけ残した | 判断表と使える書き方 | `decision` |
| Claude Codeのdeny設定はどこまで信用できるか、5経路試して残った穴と使える設定 | settings.json 全文と穴の一覧 | `asset` |
| Dateのままでよい処理とTemporalに移すべき処理の境界を、7パターン測って決めた | 移行判断の基準 | `decision` |
| Drizzleに移して詰まった5箇所と、Prismaのスキーマを機械的に置き換えた手順 | 移行手順と落とし穴一覧 | `migration` |

判定のしかた: 変換後のタイトルを見て「読者は何を持ち帰るか」を1文で言えるか。
言えないなら、まだ変換できていない。

## Evaluation Criteria

配点は `strategy/topic-selection-policy.json` の `scoring.weights` が権威。
ここは各軸の**判断のしかた**を書く。合計100点で採点し、高い順に並べる。

方針が更新されたら配点はそちらが変わる。ここの説明と配点が食い違ったら policy 側を採る。

### Reader Demand（30点）— 読者母数と需要

「その問いを実際に検索する人が何人いるか」。この軸が最重要なのは、
過去57本の低反応の主因が**対象読者が極小だったこと**だと診断されているため。

根拠の作り方（推測で埋めない）:

* `analytics/topic-feedback.md` の「2. 市場ベースライン」で、そのトピックの
  新着記事のいいね分布（p75 / p90 / 5+到達率）を見る
* 同トピックの上位記事が実際に何いいね付いているかを見る
* トピックの `taggings_count`（例: ai 34095 / typescript 17454 / claudecode 13545 / nodejs 3929）は
  **市場規模の弱い代理値**として使う。読者数そのものではない

| 点 | 目安 |
|---|---|
| 26-30 | 同トピックの上位記事が50いいね超。多くの人が同じ問題に当たっている |
| 16-25 | 上位記事が10いいね帯。トピックに一定の読者がいる |
| 6-15 | 検索する人はいるが少ない |
| 0-5 | 誰も検索しない問い（特定バージョンの特定フラグの挙動など） |

### Reader Problem / Decision（25点）— 読者の問題・判断

「今まさに詰まっている」か、「言われてみれば気になる」か。

| 点 | 目安 |
|---|---|
| 21-25 | 読者が今詰まっていて、読めば手が動く |
| 11-20 | 近い将来必ず当たる問題 |
| 6-10 | 知っておくと得だが急がない |
| 0-5 | 筆者しか気にしていない |

判定のコツ: その問いを検索する人が、**何をしようとしていて詰まったのか**を1文で書けるか。
書けないなら低得点。

### Transferability（15点）— 転用可能性

結果が読者の別の場面にも使えるか。

| 点 | 目安 |
|---|---|
| 13-15 | 一般的な原則やそのまま使える成果物が残る |
| 8-12 | 同種のツール・同種の作業に応用できる |
| 4-7 | 同じバージョン・同じ構成でのみ有効 |
| 0-3 | 特定バージョンの特定フラグ限定 |

### Trend Strength（15点）— 話題性

一次情報の日付で裏づける。直近1〜3か月を優先。

| 点 | 目安 |
|---|---|
| 13-15 | 直近で複数コミュニティが取り上げている |
| 8-12 | 一定の注目がある |
| 4-7 | ややニッチ |
| 0-3 | 話題性の根拠が出せない |

### Differentiation（10点）— 差別化

既存の**日本語**記事に対して何が新しいか。

| 点 | 目安 |
|---|---|
| 9-10 | 日本語で誰も書いていない切り口で、需要はある |
| 5-8 | 既存記事はあるが、検証条件・比較対象・粒度で差がつく |
| 2-4 | 既存記事と似る |
| 0-1 | 焼き直し |

注意: 差別化だけが高くて需要が0点の候補が、旧6軸では上位に来ていた。
**ニッチさは差別化ではない。** 需要と両立して初めて点になる。

### Verification Cost（5点）— 検証コスト

AIエージェントが半日〜1日で検証を終えられるか。

| 点 | 目安 |
|---|---|
| 5 | 1〜2時間 |
| 3-4 | 半日〜1日 |
| 1-2 | 数日 |
| 0 | 重すぎる |

## Value Archetype（価値型の選択）

候補には必ず1つ、`strategy/topic-selection-policy.json` の `valueArchetypes[].id` を割り当てる。
これが改善ループが学習する単位。

| id | 読者が持ち帰るもの | 現在の stage |
|---|---|---|
| `asset` | コピーして使える設定・コード・自作ツール | provisional |
| `migration` | 移行で踏む落とし穴の一覧と回避策 | provisional |
| `quantified` | 施策の前後の数値（桁が変わる効果） | provisional |
| `mental-model` | 他の場面にも当てられる理解のモデル | candidate |
| `decision` | 迷う選択への条件つきの答え | candidate |
| `boundary-verification` | （単一の境界条件の検証報告） | **deprecated** |
| `incident-log` | （時系列の詰まった記録） | **deprecated** |

stage の最新は必ず policy 側を見る。`deprecated` は選べない（gates で落ちる）。

### 旧型から新型への言い換え例

deprecated の型で思いついた候補は、捨てずに**束ねて格上げする**。

| deprecated な候補 | 格上げ後 | 型 |
|---|---|---|
| Read()のdenyはsortへのリダイレクトも塞ぐか検証した | Claude Codeのdeny設定はどこまで信用できるか、5経路試して残った穴と使える設定 | `asset` |
| claude --debug apiでcache_controlが見えなかった話 | Claude Codeのプロンプトキャッシュが効いているかを確認する3つの方法と、当てにならない指標 | `decision` |
| codex doctorのTERM=dumb直しではCIゲートの赤は消えない | CodexをCIで動かすときに踏む5つの環境差分と、そのまま使えるworkflow | `asset` |
| Node 26で既定になったTemporalをDateと書き比べてみた | Dateのままでよい処理とTemporalに移すべき処理の境界を、7パターン測って決めた | `decision` |

要点は、**検証を1件から3〜5件に増やし、読者が持ち帰る実物を1つ用意する**こと。
検証内容そのものを変える必要はない。
