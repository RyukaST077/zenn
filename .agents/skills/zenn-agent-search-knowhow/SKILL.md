# Search AI coding-agent know-how

1. Read `strategy/topic-selection-policy.json` first and abort when it is missing; it is the authority on gates, weights, and which value archetypes are still allowed. Then follow explicit topic and product constraints from the prompt. Otherwise consider Claude Code and Codex practices broadly. When `analytics/topic-feedback.md` exists, read it per [analytics-feedback-loop.md](../../../docs/analytics-feedback-loop.md); it is observation, not policy.
2. Inspect `articles/*.md` and prior `research/agent/` reports to exclude substantively duplicated topics. Identify what current official documentation and strong existing articles already answer so the proposed article has a specific remaining gap.
3. Use live web search. For product behavior, prefer current official documentation, release notes, and primary engineering sources. Community sources may supply hypotheses, but never relabel them as official recommendations.
4. Select one concrete reader and one practical decision that reader has to make, then choose **three or more** falsifiable claims that together answer it and can be checked locally with the authenticated `claude` or `codex` CLI. A single boundary claim is not an article: that archetype is `deprecated` in the policy after 57 articles produced no article above four likes. Bundle the boundary checks as evidence under an `asset`, `migration`, `decision`, or `quantified` archetype instead. Supported experiment modes remain `smoke`, `recipe`, `ablation`, `boundary`, `workflow`, `failure`, and `comparison`, but a mode describes one case, not the article.
5. Name the takeaway the reader copies away: a full configuration, a runnable script, a checklist, or a decision table. Reject a topic when no such artifact exists, when the likely article would only restate documentation, or when it would present a toy result with no credible practical mapping. Reject it too when the audience is only the author: the policy scores reader demand highest because tiny audiences, not wrong categories, caused the past low reach.
6. Choose the likely article type: `how-to`, `practice-validation`, `failure`, `new-feature`, `configuration-harness`, or `comparison`. Comparison is optional and must not be selected merely because two providers are available.
7. Reject topics that require exposing credentials, modifying production systems, unbounded spend, manual CAPTCHA, or evidence the local environment cannot produce.
8. Create `research/agent/agent-knowhow-<topic>-YYYYMMDD-HHMM.md` using [report-template.md](references/report-template.md). Record URLs, publication or update dates, access dates, exact claim wording or a clearly marked paraphrase, competing guidance, reader problem, article promise, coverage gap, likely article type, practical mapping, and a minimal verification idea. End the report with a `## 記事契約` heading and one ```json block per [article-contract.md](../../../strategy/article-contract.md), with an explicit `experimentId` and `arm` and a `primaryTopic` the feedback report marks measurable, then run `node scripts/analytics/register-article.mjs --from-research <report>` to pre-register it before any publication; fix the reported fields or replace the topic if it exits 2.
9. Do not execute the practice, create a plan, or draft an article.
10. End with only the pipeline result object. Set `artifact` to the report path. Abort rather than inventing a source, testable claim, or reader need.
