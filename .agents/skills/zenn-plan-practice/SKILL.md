# Plan the practice

1. Use only the research report path explicitly supplied by the prompt. Abort if it is missing, outside `research/`, or does not identify one selected topic. Read its `## 記事契約` json block; abort and ask for a fresh `zenn-search-topic` run when absent rather than inventing a contract. See [analytics-feedback-loop.md](../../../docs/analytics-feedback-loop.md).
2. Inspect local tool availability and project constraints without installing dependencies or performing the verification.
3. The run stage executes inside the Codex `workspace-write` sandbox. Do not assume a browser, container, package manager, or system install is usable: add a bounded capability gate before relying on it, and stop rather than infer results when the gate fails. `brew`, system-level installs, and mutations outside the run workspace are unavailable. When a specific runtime version is required, prefer an already-installed binary, an official container image after a Docker gate, or an official release archive downloaded into the run workspace.
4. Design a small reproducible experiment with success criteria, failure criteria, exact commands, expected evidence, cleanup, security limits, timebox, and fallback scope. Expand every contract `verificationItems` entry into a case and keep all of them: three or more checks are what separates this from the deprecated single-boundary report. Make producing the contract `takeaway` (the artifact the reader copies) an explicit task, not a by-product. If the checks cannot reach three or the takeaway cannot be produced, stop and request a topic replacement instead of planning a smaller article.
5. Require all work to occur under a new `logs/run-<topic>-<timestamp>/work/` directory. Before the first invocation of a tool that can persist telemetry, update checks, preferences, caches, or browser state, require its documented product-specific opt-out and redirect supported writable paths beneath the run workspace. Never change `HOME` or `CODEX_HOME`. The automated Codex pipeline supplies `ASTRO_TELEMETRY_DISABLED=1`; every Astro plan must explicitly verify or set that value in the run shell before the first Astro command and must not run `astro telemetry disable`, which would persist a user preference.
6. For background servers and other lifecycle-managed CLIs, derive start/status/log/stop syntax from the pinned local `--help` output after installation and before the main experiment. Record that output as evidence. For Astro 7.2 background preview, use positional `astro preview status`, `astro preview logs`, and `astro preview stop`; do not invent `--status`, `--logs`, or `--stop` flags.
7. Create `practice/practice-<topic>-YYYYMMDD-HHMM.md` using [plan-template.md](references/plan-template.md). Preserve the source report path and relevant official URLs.
8. Do not run the experiment or write article prose.
9. End with only the pipeline result object; set `artifact` to the plan path and metadata values to `null`. Abort rather than guessing material missing inputs.
